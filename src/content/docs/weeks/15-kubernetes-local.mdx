### From Compose to a Cluster

Compose starts containers on one machine and restarts the ones that exit. **Kubernetes** runs containers on a **cluster**: a set of machines, called **nodes**, managed as one. You never tell Kubernetes to start a container. You send it **objects**, YAML documents that describe what you want to run, called **manifests**. Kubernetes stores them and works, without end, to make the cluster match them.

That work is a **control loop**: compare what you asked for with what runs, act on the difference, repeat. Your scheduler from <a href={weekHref(9)}>Week 9</a> is one: every five seconds it compares the due monitors with the queue and adds the missing jobs. Kubernetes runs dozens of these loops. When a node fails or a container exits, the next pass of a loop sees the difference and repairs it.

**kind**, short for Kubernetes in Docker, makes each node a Docker container. Inside that container run the same programs as on a real server. The diagram shows the parts that act when you apply a manifest:

### Pods, Deployments and Labels

A **pod** is the unit Kubernetes runs: one or more containers that share an IP address and can share volumes. Every program of the monitor runs one container per pod. Pods are disposable. A replaced pod gets a new name and a new IP address, and nothing on its filesystem survives.

You do not create pods yourself. A **Deployment** holds a pod template and a number of copies, called **replicas**. Its control loop keeps that many pods running from the template. When you change the template, it replaces the pods a few at a time: a **rolling update**. A Deployment finds its pods by **labels**, key and value pairs on every object, such as `app.kubernetes.io/name: api`. Its **selector** is a query on those labels. A selector that matches no pod template is a classic Kubernetes typo, and this week's tests check for it.

### Services: A Stable Name for Changing Pods

The web container sends `/api/` requests to `http://api:8080`, as in Compose. In Kubernetes, `api` is the name of a **Service**: a stable virtual IP address, the **ClusterIP**, plus a DNS name. The Service selects pods by label and keeps the list of the ready ones in **EndpointSlice** objects. On every node, `kube-proxy` turns that list into rules that send each connection for the ClusterIP to one ready pod. Pods come and go. The name and the address stay.

A **namespace** is a named group of objects inside one cluster. Everything of the monitor lives in `your-monitor`. CoreDNS, the DNS server of the cluster, answers for names of the form `api.your-monitor.svc.cluster.local`, and the search list of every pod makes the short name `api` work inside the same namespace.

Three Service types matter this week. **ClusterIP**, the default, answers inside the cluster only. **NodePort** also opens one port, from `30000` to `32767`, on every node. **Headless**, with `clusterIP: None`, has no virtual address at all: its name resolves straight to the addresses of the ready pods. Postgres uses one.

### Probes: Ready, and Alive

For each probe a container defines, the kubelet runs it every 10 seconds by default, with a timeout of one second. A container without probes is never probed. An HTTP probe passes on any status from `200` to `399`.

- **Readiness** asks: can this pod take requests now? While it fails, the pod stays out of its Service, and a rolling update waits for it. The container keeps running.
- **Liveness** asks: is this container stuck for good? After `failureThreshold` failures in a row, three by default, the kubelet restarts the container.

The api answers `/healthz` from its HTTP handler: when it answers at all, it can take requests. The worker, the scheduler and the alerter run a loop, and their HTTP server keeps answering while that loop hangs. A `/healthz` that always says ok proves only that the server runs. This week, their `/healthz` reports whether the loop has made a pass lately.

Keep liveness cheap and narrow. A liveness probe that checks Postgres restarts every api pod when Postgres goes down, and the restarts fix nothing.

### Requests, Limits and the Container User

Each container states **requests** and **limits** for CPU and memory. The scheduler places a pod only on a node with the requested amount unreserved. A limit is a ceiling the kernel enforces: above its CPU limit, a container is slowed down, and above its memory limit, the kernel stops it and the container shows `OOMKilled`. CPU counts in millicores: `100m` is a tenth of one core. Memory counts in bytes with binary suffixes: `64Mi` is 64 mebibytes. Write `Mi`, not `M`, and never `m`, which means millibytes.

A **security context** sets who the container runs as. The Go images from <a href={weekHref(6)}>Week 6</a> run as user `65532` and write no files, which makes five settings free: refuse root, forbid privilege escalation, drop every Linux capability, apply the default **seccomp** profile of the container runtime, which blocks rare and risky system calls, and mount the image read-only. The `restricted` Pod Security Standard demands the first four. A label on the namespace makes the API server refuse any pod that breaks them. The read-only image is a rule of this repository, on top of the standard, and the manifest tests of Step 9 enforce it.

### State: StatefulSet, Volumes, ConfigMap and Secret

Postgres needs a disk that survives its pod, and a stable name. A **StatefulSet** gives each pod a fixed name, `postgres-0`, and a **PersistentVolumeClaim** (PVC) of its own, `data-postgres-0`. A claim asks for storage. The cluster answers it with a **PersistentVolume**, which kind creates as a folder inside the node container. Delete the pod, and the StatefulSet makes a new `postgres-0` that mounts the same claim.

A **ConfigMap** holds settings, and a **Secret** holds passwords and keys. Containers read both as environment variables. A Secret is not encrypted: etcd stores it as it is, and the API shows its values in base64, which anyone can decode. What protects it is who can read it, and the <a href={trackHref('kubernetes')}>Kubernetes track</a> covers that access control.

### Kustomize: A Base and an Overlay for Each Cluster

Your laptop and the server of Week 16 run the same programs with different images, passwords and ways in. **Kustomize**, built into `kubectl`, keeps the shared manifests in a **base** and the differences in one **overlay** per cluster. `kubectl kustomize DIR` prints the merged objects, and `kubectl apply -k DIR` sends them. The `deploy.yml` from Week 14 already relies on it: it writes a small overlay that swaps each image name for a GHCR image.

### Step 1: Install the Tools

You need three programs: kind, `kubectl`, and `kubeconform`, which checks manifests against the Kubernetes schemas. The Docker you installed in <a href={weekHref(0)}>Week 0</a> runs the node.

The node image this page pins, Kubernetes 1.36, comes from the release notes of kind `v0.33.0`, which list one image for each supported minor version, pinned by digest. kind itself defaults to a newer Kubernetes. Install that release with Go:

```sh
go install sigs.k8s.io/kind@v0.33.0
go install github.com/yannh/kubeconform/cmd/kubeconform@latest
kind version
```

`kind version` prints a line such as `kind v0.33.0 go1.27.2 darwin/arm64`. When a newer kind exists, its release notes list the 1.36 image to pin instead.

`kubectl` talks to clusters at most one minor version away from its own. Homebrew installs the newest release, 1.37 at the time of writing, which still fits a 1.36 cluster. Homebrew moves on to 1.38 when it ships, and that `kubectl` no longer fits. Download the newest 1.36 release from the Kubernetes release server instead, check its checksum, and install it:

```sh
os=$(uname -s | tr '[:upper:]' '[:lower:]')
arch=$(uname -m | sed 's/x86_64/amd64/; s/aarch64/arm64/')
version=$(curl -fsSL https://dl.k8s.io/release/stable-1.36.txt)
curl -fsSLO "https://dl.k8s.io/release/$version/bin/$os/$arch/kubectl"
curl -fsSLO "https://dl.k8s.io/release/$version/bin/$os/$arch/kubectl.sha256"
echo "$(cat kubectl.sha256)  kubectl" | shasum -a 256 --check
sudo install -m 0755 kubectl /usr/local/bin/kubectl
rm kubectl kubectl.sha256
kubectl version --client
```

`shasum` prints `kubectl: OK`, and the last command prints `Client Version: v1.36` followed by the patch number. When it names another version, an older `kubectl` comes first on your `PATH`: `which -a kubectl` lists every copy.

### Step 6: Describe the Other Programs

Create `worker.yaml`, `scheduler.yaml`, `alerter.yaml` and `web.yaml` in `deploy/k8s/base/` on the pattern of `api.yaml`. Each one differs in a few lines:

- **worker**: two replicas, which the `SKIP LOCKED` queue of Week 9 keeps from taking the same job. `args: ["-workers", "$(WORKERS)", "-debug-addr", ":6060"]`, a port named `debug`, and probes on it. No Service, because nothing calls the worker. The address `:6060` means every interface of the pod, because the kubelet probes the pod IP, not `127.0.0.1`. That server holds `/metrics` and `/healthz` only. pprof stays off, and Observe It turns it on, on the loopback address of the pod.
- **scheduler** and **alerter**: one replica, `args: ["-metrics-addr", ":2112"]`, a port named `metrics`, and `strategy: type: Recreate`. With the default rolling update, the new pod starts before the old one stops, and for a few seconds two schedulers queue jobs and two alerters send notifications. `Recreate` stops the old pod first. The alerter gets no `ALERT_WEBHOOK_URL` and writes alerts to its log, as in Compose without one.
- **web**: one replica, no environment, and a Service named `web` on port `8080`. nginx writes its PID file and buffers under `/tmp`, which the read-only root filesystem forbids. An `emptyDir` volume, an empty folder that lives as long as the pod, mounted at `/tmp`, fixes that.

Three choices here come from how the `postgres:17` image works:

### Step 9: Check the Manifests Before the Cluster Does

`kubectl apply` refuses an object with an unknown field, such as a misspelled `readinesProbe`. It finds out only when a cluster answers, and it still applies every other object, which leaves the cluster half changed. Catch the error on your laptop and in CI, with no cluster. `make k8s-check` renders the overlay and validates every object against the schemas of Kubernetes 1.36. `-strict` rejects unknown fields:


## Observe It

<ObserveIt>

Four commands answer most questions about a cluster: `kubectl get` lists objects, `kubectl describe` explains one with its recent events, `kubectl logs` prints the output of a container, and `kubectl get events --sort-by=.lastTimestamp` shows what the cluster did, newest last.

**The first start, in the events.** Run the events command after a fresh `make kind-deploy`. Between the `Scheduled` and `Started` lines of each Go pod, you find `BackOff` lines: the program starts before Postgres is ready, exits, and the kubelet waits 10, then 20, then 40 seconds before the next try. Compose waited for a healthy Postgres through `depends_on`. Kubernetes has no such ordering: programs retry until what they need answers. `kubectl logs --previous` shows the log of the run before the restart. The output is an example:

```txt wrap
$ kubectl logs --previous deploy/worker
{"time":"2026-10-11T09:12:03.418Z","level":"ERROR","msg":"fatal","service":"worker","err":"connect to database: failed to connect to `user=monitor database=monitor`: hostname resolving error: lookup postgres on 10.96.0.10:53: no such host"}
```

The Service `postgres` is headless: until `postgres-0` is ready, its name has no address at all. `10.96.0.10` is CoreDNS.

**Probes in the api log.** `kubectl logs deploy/api | grep healthz | tail -3` shows a `request` line for `/healthz` every 5 seconds from the readiness probe and every 10 seconds from the liveness probe. That noise is the price of a probe that crosses your whole handler chain. The worker, the scheduler and the alerter do not log their probes.

**Which pods a Service sends to.** `kubectl get endpointslices -l kubernetes.io/service-name=api` lists the addresses of the ready api pods. The output is an example:

```txt
NAME        ADDRESSTYPE   PORTS   ENDPOINTS                 AGE
api-8xk2p   IPv4          8080    10.244.0.12,10.244.0.13   6m
```

Compare the addresses with `kubectl get pods -o wide`. Operate It makes a pod unready and keeps it out of this list.

**Metrics without Prometheus.** The cluster runs no Prometheus or collector this week, and tracing stays off because `OTEL_EXPORTER_OTLP_ENDPOINT` is unset. Each program still serves `/metrics`. `kubectl port-forward` opens a tunnel from your laptop to one pod:

```sh
kubectl port-forward deploy/scheduler 2112:2112
curl -s 127.0.0.1:2112/metrics | grep '^monitor_jobs'
```

Run `curl` in a second terminal, and press Ctrl-C in the first when you are done. `monitor_jobs_queued` stays at or near `0` while two workers keep up.

**pprof, on the loopback of one pod.** The worker serves no pprof by default, and no Service, probe or port of the manifests exposes it. To profile in the cluster, add the Go command-line flag `-pprof-addr 127.0.0.1:6061` to the worker, then open a tunnel. `kubectl port-forward` connects to the loopback address inside the pod, which nothing else in the cluster reaches:

```sh
kubectl patch deployment worker --type json -p '[{"op": "add", "path": "/spec/template/spec/containers/0/args/-", "value": "-pprof-addr"}, {"op": "add", "path": "/spec/template/spec/containers/0/args/-", "value": "127.0.0.1:6061"}]'
kubectl port-forward deploy/worker 6061:6061
curl -s '127.0.0.1:6061/debug/pprof/goroutine?debug=1' | head -1
```

In the second terminal, `curl` prints `goroutine profile: total` and a count. `go tool pprof http://127.0.0.1:6061/debug/pprof/profile?seconds=10` takes a CPU profile, as in <a href={weekHref(12)}>Week 12</a>. Press Ctrl-C in the first terminal, and run `make kind-deploy` to remove `-pprof-addr` again.

**What the node has promised.** `kubectl describe node your-monitor-control-plane` ends with **Allocated resources**: the sums of the requests and limits of every pod on the node, the system pods included. The monitor alone requests 475 millicores and 608 MiB. Compare that with the CPUs and memory you give Docker.

</ObserveIt>

## Operate It

<OperateIt>

Break the cluster on purpose, one failure at a time, and restore it with `make kind-deploy`, which applies the manifests again.

**A readiness probe that fails.** Point the api readiness probe at a path that answers `404`:

```sh
kubectl patch deployment api --type json -p '[{"op": "replace", "path": "/spec/template/spec/containers/0/readinessProbe/httpGet/path", "value": "/nope"}]'
kubectl get pods -l app.kubernetes.io/name=api
```

The patch changes the pod template, which starts a rolling update. The new pod runs but stays `0/1` ready, and `kubectl describe` shows `Readiness probe failed: HTTP probe failed with statuscode: 404`. With two replicas, the rolling update takes no ready pod away before a new one is ready: the two old pods keep serving, and the status page keeps working. Readiness has just stopped a broken release.

**A liveness probe that fails.** Run the same patch against `deployment web`, with `livenessProbe` in the path. The new pod turns ready, the old one goes, and the events show `Liveness probe failed: HTTP probe failed with statuscode: 404` for every failed probe, every 10 seconds. After three failures in a row, about every 30 seconds, `Container web failed liveness probe, will be restarted` follows. The `RESTARTS` column climbs. The restarts change nothing, because the probe is wrong, not nginx.

**ErrImageNeverPull.** `kubectl set image deployment/worker worker=your-monitor-worker:v2` names an image the node does not have. The new pod shows `ErrImageNeverPull` at once, because the kind overlay sets `imagePullPolicy: Never`. Without that setting, the kubelet tries Docker Hub, fails, and shows `ErrImagePull`, then `ImagePullBackOff`.

**Pending.** `kubectl set resources deployment/worker --requests=cpu=64 --limits=cpu=64` asks for 64 cores. The new pod stays `Pending`, and `kubectl describe` shows a `FailedScheduling` event that starts with `0/1 nodes are available: 1 Insufficient cpu.` No node can take it, and nothing starts.

**Data that outlives its pod.** Run `kubectl delete pod postgres-0`. The StatefulSet creates a new `postgres-0` within seconds. For those seconds, the api answers reads with `500`, and the workers log `job failed`. Once it is ready, reload the status page: your monitors and their history are there, on the claim `data-postgres-0`, which `kubectl get pvc` lists as `Bound`. `kubectl delete -k deploy/k8s/overlays/kind` deletes the data: the overlay holds the Namespace, and deleting a namespace deletes every claim in it, and the StorageClass of kind, `standard`, sets the reclaim policy `Delete`: its local-path provisioner deletes the volume of a claim once the claim goes. To remove the monitor and keep the data, run `kubectl delete -k deploy/k8s/base`: the base names the namespace but holds neither the Namespace nor the claim. `make kind-down`, which deletes the node container, deletes the data too.

| What you see | What it points to |
| --- | --- |
| `0/1` ready, `Running`, no restarts, `Readiness probe failed` events | The pod runs but fails its readiness check: a wrong path or port, or the program cannot serve yet |
| `RESTARTS` climbing, `Liveness probe failed` events | The kubelet restarts a container that answers its liveness probe wrongly or too slowly |
| `CrashLoopBackOff`, `logs --previous` shows `password authentication failed for user "monitor" (SQLSTATE 28P01)` | `postgres.env` changed after Postgres first started. Restore the old password, or set the new one with `ALTER ROLE` in `psql` |
| `CrashLoopBackOff`, `logs --previous` shows `lookup postgres on 10.96.0.10:53: no such host` for minutes | `postgres-0` is not ready, the postgres Service is missing, or the program runs in another namespace |
| `ErrImageNeverPull` | The image with that tag is not in the node: run `make kind-load` |
| `Pending`, `Insufficient cpu` or `Insufficient memory` | The requests exceed what the node has unreserved |
| `OOMKilled` in `Last State`, exit code `137` | The container used more memory than its limit, and the kernel stopped it |
| `CreateContainerConfigError` | A ConfigMap or Secret the pod names does not exist, such as one you deleted by hand |
| `kubectl apply` warns `would violate PodSecurity "restricted:v1.36"`, and the Deployment gets no pods | The pod template breaks the restricted standard. `kubectl describe replicaset` shows the `FailedCreate` event |

</OperateIt>

## Side Lab

<SideLab title="Follow a Service into the iptables rules and DNS of the node">

A Service is not a program, and no process listens on its ClusterIP. Find out what does the work. The outputs are examples.

**1. The address.** `kubectl get service api` prints its `CLUSTER-IP`, such as `10.96.112.45`, from the service range `10.96.0.0/16` that kind uses. Pod addresses come from `10.244.0.0/16`.

**2. The rules.** kind runs `kube-proxy` in iptables mode. iptables is the packet filter of the Linux kernel. `kube-proxy` writes rules that rewrite the destination of each packet sent to a ClusterIP. Read them inside the node container:

```sh
docker exec your-monitor-control-plane iptables-save -t nat | grep 'your-monitor/api'
```

```txt wrap
-A KUBE-SERVICES -d 10.96.112.45/32 -p tcp -m comment --comment "your-monitor/api:http cluster IP" -m tcp --dport 8080 -j KUBE-SVC-NWV5X2332I4OT4T3
-A KUBE-SVC-NWV5X2332I4OT4T3 -m comment --comment "your-monitor/api:http -> 10.244.0.12:8080" -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-WNBA2IHDGP2BOBGZ
-A KUBE-SVC-NWV5X2332I4OT4T3 -m comment --comment "your-monitor/api:http -> 10.244.0.13:8080" -j KUBE-SEP-X3P2623AGDH6CDF3
-A KUBE-SEP-WNBA2IHDGP2BOBGZ -p tcp -m comment --comment "your-monitor/api:http" -m tcp -j DNAT --to-destination 10.244.0.12:8080
-A KUBE-SEP-X3P2623AGDH6CDF3 -p tcp -m comment --comment "your-monitor/api:http" -m tcp -j DNAT --to-destination 10.244.0.13:8080
```

Read them from the top. A packet for `10.96.112.45:8080` jumps to the chain of the Service. That chain picks the first pod with probability one half, and otherwise the second. The pod chain rewrites the destination to the pod address: DNAT, destination network address translation. Your chain names and the extra rules for marking packets differ. Scale the api to three replicas with `kubectl scale deployment api --replicas 3` and read the rules again: the probabilities become one third, then one half. Scale back to two.

**3. The names.** Start a throwaway pod with DNS tools. It runs in the `default` namespace, because the restricted label on `your-monitor` refuses a pod without a security context:

```sh
kubectl run dns --rm -it --restart=Never -n default --image=busybox:1.36 -- sh
```

At its prompt, run `nslookup api.your-monitor.svc.cluster.local`: one address, the ClusterIP. Then `nslookup postgres.your-monitor.svc.cluster.local`: the address of `postgres-0`, because the Service is headless. Then `cat /etc/resolv.conf`: the `search` line starts with `default.svc.cluster.local`, which is why a short name finds Services in the same namespace only. Type `exit`, and `--rm` deletes the pod.

The <a href={trackHref('networking')}>Networking track</a> covers NAT, and the <a href={trackHref('kubernetes')}>Kubernetes track</a> compares the iptables mode with the nftables and IPVS modes.

</SideLab>
