A team tracks its work in **tickets**: one record per piece of work, with a title, a description, an owner and a status, kept in a tool such as Jira, Linear or GitHub Issues. You know tickets from QA, short for quality assurance, as the bug reports you write. As a full-stack engineer, you also write them, split them, pick them up and close them, and the ticket becomes the thread that ties a request to the code, the review and the deploy that answer it.

## What It Is

### Tickets and Their Types

A **ticket**, also called an issue or a work item, describes one piece of work small enough for one person to finish in a few days. Most trackers sort tickets by type:

- A **bug**: the system does something wrong. It needs the steps to reproduce, what you expect and what happens instead, the version or commit, and any log lines or screenshots.
- A **feature** or **story**: a new behavior someone needs. A **user story** phrases it from the point of view of the person who benefits: as an on-call engineer, I get one notification per incident, not one per failed check.
- A **task** or **chore**: work with no visible behavior change, such as upgrading Go or rotating a certificate.
- An **epic**: a large goal that groups many tickets, such as alerting. Jira calls it an epic, and Linear calls it a project.

Each ticket gets a **key** that names it everywhere. Jira and Linear write the key as a project prefix, a hyphen and a number: `MON-42` in the project `MON`. GitHub Issues numbers issues per repository and writes `#42`. The key is what you type into branch names, commit messages and pull request titles.

### Writing a Ticket Someone Else Can Finish

A good ticket answers four questions before anyone starts:

- **Why**: the problem, from the point of view of the person who has it. With a second worker running, the monitor checks every site twice: that is a problem. Adding a queue is a solution, and it belongs in the ticket only once the team agrees on it.
- **What done means**: the **acceptance criteria**, a list of observable facts that must hold when the work is complete. Write them the way you write test cases: given four workers and 200 jobs, no job runs twice.
- **What is out of scope**: the related work that this ticket does not cover, which keeps it small.
- **Where to start**: links to the code, the log line, the dashboard or the decision record that the work touches.

A team also agrees on a **definition of done**: the checks every ticket passes on top of its own criteria, such as tests written, continuous integration (CI) green, documentation updated and the change deployed. The **Done When** list on each week of this course is a definition of done for that week.

Split a ticket that takes longer than a few days. Split it by behavior, not by layer: one ticket for creating a monitor through the api, page included, beats one ticket for the database and one for the page, because each split ticket delivers something a person can use and test on its own.

### Backlogs and Boards

The **backlog** is the ordered list of tickets nobody has started. The order is the priority: the top ticket is the next one to pick up. **Refinement**, also called grooming, is the regular meeting where the team rewrites the top tickets until each one has clear acceptance criteria and a size.

A **board** shows the tickets in flight as cards in columns, one column per **status**: Backlog, Ready, In progress, In review and Done is a common set. A card moves right as the work moves. A card stuck in one column for days is a signal: the work is blocked, too large, or waiting for a review nobody gives.

Two ways to run a board dominate:

- **Scrum** works in **sprints**, fixed periods of one month or less, two weeks on many teams. At the start, the team commits to a set of tickets from the top of the backlog. At the end, it reviews what shipped and how it worked.
- **Kanban** has no sprints. Work flows continuously, and each column has a **work-in-progress limit**, or WIP limit: a maximum number of cards. When In review holds its limit, nobody starts a new ticket. Everyone reviews instead. The limit keeps work from piling up half-finished.

### Status Is a Promise

The status on a ticket tells the team what to expect. Move the card when the work moves, not at the end of the week. When you are blocked, say on the ticket what blocks you and who can unblock it. When you stop working on a ticket, unassign yourself and write down how far you got. A ticket that says In progress for two weeks with no comment costs the team more than a ticket that says blocked.

### Linking Work End to End

The value of a ticket key grows with every place it appears:

- **The branch**: name it after the ticket, such as `MON-42-retry-once`. GitHub can also create the branch from the issue page.
- **The commits**: start the subject with the key: `MON-42: Retry a failed check once`.
- **The pull request**: put the key in the title. On GitHub, a closing keyword in the description, such as `Closes #42`, links the pull request to the issue and closes the issue when the pull request merges into the default branch. GitHub accepts `close`, `fix` and `resolve` in all their forms.
- **The deploy**: the image carries the commit SHA, short for Secure Hash Algorithm, the hash that names the commit. The commit carries the key.

With the links in place, you walk from any end to any other. During an incident, the deploy names the commit, the commit names the ticket, and the ticket explains why the change exists and who asked for it.

Tools find ticket keys in text with a regular expression, and you write the same function the first time you build a check that every pull request title names a ticket, or a script that lists the tickets in a release. `TicketRefs` returns every key in a piece of text, in order, each once:

<CodeFrom file="go/tracks/worktracking/refs.go" region="refs" lang="go" title="refs.go" />

The pattern reads from left to right: `[A-Z]` is one uppercase letter, `[A-Z0-9]+` one or more uppercase letters or digits, then a literal hyphen and `[0-9]+`, one or more digits. That shape rules out a one-letter prefix such as `A-1`, and allows a digit inside the prefix, as in `K8S-14`. `\b` is a **word boundary**: the point between a letter, digit or underscore and anything else, or the start or end of the text. With one on each side, `MON-42` inside `XMON-42a` does not count, while `MON-42` inside `feature/MON-42-retry-once` does, because `/` and `-` are not word characters.

`regexp.MustCompile` compiles the pattern once, when the package loads, and panics on a bad pattern: a typo fails at startup instead of at the first call. `FindAllString` with `-1` returns every match. The map remembers which keys the loop has already appended.

The function starts from `[]string{}`, not from a nil slice. Both have length zero in Go, but `encoding/json` writes a nil slice as `null` and an empty one as `[]`, and a TypeScript client that calls `.map` on `null` throws.

## Common Mistakes

- **A ticket with a title and nothing else.** The person who picks it up guesses what done means, and the review turns into an argument about scope. Write the why and the acceptance criteria before the ticket leaves the backlog.
- **A solution disguised as a problem.** Add Redis tells the engineer what to build and hides why. The engineer cannot find a simpler fix, such as a table in the existing Postgres. Describe the problem and let the solution come in refinement.
- **A ticket that takes three weeks.** Nobody can tell whether it is on track, and the pull request at the end is too big to review well. Split it by behavior into tickets of a few days each.
- **A board that nobody updates.** The status lies, and the team asks in chat instead of reading the board, which defeats the point of having one. Move the card when the work moves, and write a comment when you are blocked.
- **Starting new work while reviews pile up.** Five tickets sit in review, none ships, and every branch drifts further from `main`. Finish before you start: review first, as a WIP limit enforces.
- **No key in the branch, the commits or the pull request.** Six months later, `git blame` shows a line and nobody knows why it exists. Put the key in the branch name and the pull request title every time.
- **Closing keywords on a pull request into a non-default branch.** GitHub ignores the keywords there, and the issue stays open after the merge. Close the issue by hand, or merge into `main`.

## Going Deeper

- **Estimation**: story points, t-shirt sizes and why many teams count tickets instead. Read about it before your first sprint planning.
- **Flow metrics**: cycle time, the time from In progress to Done, and throughput, the tickets finished per week. They measure a team better than estimates do.
- **GitHub Projects**: boards, tables and custom fields on top of GitHub Issues, enough for a small team without a separate tool.
- **Autolinked references**: GitHub turns `MON-42` in issues, pull requests and commit messages into a link to your tracker once you configure the prefix in the repository settings.
- **Incident tickets and postmortem actions**: every action item from a postmortem becomes a ticket with an owner and a date. The <TrackLink slug="sre">site reliability engineering (SRE) track</TrackLink> covers postmortems.
