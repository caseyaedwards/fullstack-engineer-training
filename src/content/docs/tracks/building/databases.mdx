A database keeps the data of an app through restarts and crashes, and answers questions about it while many programs read and write at once. The uptime monitor keeps every monitor, every check and every incident in Postgres 17. This page covers the three ideas behind most database bugs in backend code: transactions, isolation between concurrent transactions, and indexes.

## What It Is

### Tables, Keys and SQL

Postgres is a **relational database**: it stores data in **tables** of **rows**, and every row has the same named, typed **columns**. A **primary key** names each row. A **foreign key** is a column whose value must exist as the primary key of another table: every check names a monitor that exists. You ask questions in SQL, a declarative language: you describe the rows you want, and the **planner** inside Postgres works out how to find them. <WeekLink n={8} anchor="tables-rows-and-constraints">Week 8</WeekLink> introduces the types and the four constraints of the monitor schema.

Each program talks to Postgres over a network connection, and Postgres serves each connection with its own operating-system process. Go programs borrow connections from a **connection pool**, `pgxpool`, instead of opening one per query.

### Transactions and ACID

A **transaction** is a group of statements that Postgres treats as one unit. It starts with `BEGIN` and ends with `COMMIT`, which applies every change, or `ROLLBACK`, which discards every change. Any error inside the transaction makes the commit fail and turns it into a rollback. A statement outside `BEGIN` runs as a transaction of its own.

Transactions give four promises, named ACID (atomicity, consistency, isolation, durability):

- **Atomicity**: all the changes of a transaction land, or none of them does. A crash halfway through leaves nothing behind.
- **Consistency**: every constraint holds after each transaction. A transaction that breaks a foreign key or a check constraint fails as a whole.
- **Isolation**: concurrent transactions do not see the unfinished work of each other. The isolation level decides how much of the finished work of others they see, as the next section explains.
- **Durability**: once `COMMIT` returns, the change survives a crash. Postgres appends the change to the **write-ahead log**, or WAL, and flushes that log to disk with `fsync` before it answers. The WAL lives in the `pg_wal` folder and records every change before the table files get it.

Atomicity matters whenever one fact lives in two places. In the example on this page, a check result goes into the `checks` table, and the status of the monitor goes into `monitors.last_status`. Without a transaction, a failure between the two writes leaves a monitor that says `up` with no check to back it.

### Concurrency: MVCC and Row Locks

Postgres runs many transactions at once with **multiversion concurrency control**, or MVCC. An `UPDATE` does not overwrite a row: it writes a new version of the row and marks the old version as replaced. Each transaction reads from a **snapshot**, a view of the versions that have committed by one moment. Readers see the versions in their snapshot and never wait for writers. Writers never wait for readers. `VACUUM` later removes the old versions that no snapshot needs.

Two writers to the same row do wait. `UPDATE`, `DELETE` and `SELECT ... FOR UPDATE` take a **row lock** that lasts until the transaction ends. A second transaction that wants to change the same row waits for the first to commit or roll back. Two transactions that each wait for a row the other holds form a **deadlock**: Postgres detects the cycle after one second, the default `deadlock_timeout`, and cancels one of them.

### Isolation Levels

The **isolation level** of a transaction decides when it takes its snapshot and what happens when a row it reads changes underneath it. Postgres 17 has three levels that behave differently:

| Level | Snapshot | When another transaction changes a row you then update |
| --- | --- | --- |
| Read Committed, the default | A new one for each statement | Your `UPDATE` waits for the other to commit, then applies to the newest version |
| Repeatable Read | One for the whole transaction, taken at its first query | Your `UPDATE` fails with `could not serialize access due to concurrent update` |
| Serializable | As Repeatable Read, plus tracking of what each transaction reads | Postgres cancels one transaction when it detects reads and writes that no one-at-a-time order produces |

Postgres accepts Read Uncommitted as a name and runs it as Read Committed: no level in Postgres ever shows uncommitted data. Both stricter levels report a conflict with the error code `40001`, a **serialization failure**. SQLSTATE is the name of these five-character codes, which the SQL standard defines. The fix for that error is to run the whole transaction again from `BEGIN`, which makes every transaction under those levels a candidate for a retry loop such as the one in the <TrackLink slug="system-design" anchor="example">System and Software Design track</TrackLink>.

### Lost Updates

Read Committed does not stop one bug: the **lost update**. Two transactions read the same value, each computes a new value in application code, and each writes it back. The second write replaces the first, and one change disappears without an error. The [lost update diagram](#lost-update) below shows it with a counter of consecutive failures.

Four fixes exist, from the simplest:

- **Compute in SQL.** `update monitors set failures = failures + 1 where id = $1` reads and writes in one statement. Under Read Committed, the second `UPDATE` waits for the row lock, then adds one to the committed value.
- **Lock on read.** `SELECT ... FOR UPDATE` takes the row lock at the read. When both transactions read with `SELECT ... FOR UPDATE`, the second waits at its read until the first commits, then reads the new value. A plain `SELECT` in the other transaction still reads without waiting.
- **Detect and retry.** Under Repeatable Read, the second write fails with `40001`, and the code retries the transaction.
- **Check a version.** Add a `version` column and write `update ... set version = version + 1 where id = $1 and version = $2`. Zero rows affected means someone else got there first. This is **optimistic locking**: nothing holds a lock between the read and the write, which suits an edit form that stays open for minutes.

### Indexes and the Planner

Without help, Postgres answers `where monitor_id = 42` with a **sequential scan**: it reads every page of the table and keeps the matching rows. A **page** is the 8 kB block that Postgres reads and writes as a unit. The cost of a sequential scan grows with the table.

An **index** is a separate structure, sorted by the columns you name, that points at rows in the table. The default kind is a **B-tree**, a balanced tree: the root page and the branch pages under it hold ranges of keys, and the leaf pages hold every key in order, each with the location of its row. Finding one key costs one page read per level. The Week 8 index over two million checks is three levels deep: a root, one level of branch pages and the leaves. From the first match, the scan walks forward through the leaves in order, which is why an index on `(monitor_id, checked_at desc)` also returns the newest checks first with no sort.

The planner picks between the two plans from **statistics**, a summary of each column that `ANALYZE` collects. On a table of a few pages, it picks the sequential scan even when an index exists, because one page read beats a walk down a tree. `EXPLAIN` prints the chosen plan, and `EXPLAIN ANALYZE` runs the query and adds real times.

Every index costs a write on each `INSERT` and disk space. Add an index for a query that runs, with the columns in the order the query filters and sorts.

## Common Mistakes

- **Reading a value into Go, changing it and writing it back.** Two requests at once lose one of the changes, with no error. Compute the new value in the `UPDATE` itself, or lock the row with `SELECT ... FOR UPDATE` before the read.
- **Calling the pool inside a transaction.** A `db.Exec` inside `BeginFunc` runs on a second connection: its write commits on its own, it does not see the uncommitted rows of the transaction, and a pool with every connection inside a transaction blocks forever waiting for a free one. Pass `tx` to every statement inside the transaction.
- **Beginning a transaction by hand without a deferred rollback.** A path that returns early leaves the connection `idle in transaction`, holding its row locks until the connection closes. Use `pgx.BeginFunc`, or write `defer tx.Rollback(ctx)` on the line after `Begin`: after a successful `Commit`, the deferred rollback does nothing.
- **Holding a transaction open across slow work.** An HTTP call inside a transaction holds every row lock it took for the length of the call, and other writers to those rows wait. Do the slow work first and open the transaction for the writes, unless the lock is the point, as in the Week 9 queue.
- **Treating `40001` as a crash.** Under Repeatable Read and Serializable, a serialization failure is a normal outcome under contention. Retry the whole transaction a few times, from `BEGIN`.
- **Trusting a plan from an empty table.** On a development database with ten rows, Postgres picks a sequential scan, and a missing index looks harmless. Check plans with `EXPLAIN ANALYZE` against realistic row counts.
- **Putting index columns in the wrong order.** An index on `(checked_at, monitor_id)` sorts by time first and spreads one monitor across the whole tree. Lead with the column the query filters on with `=`, then the column it sorts or ranges on.

## Going Deeper

- **VACUUM and table bloat**: MVCC leaves old row versions behind, and knowing how autovacuum reclaims them explains slow tables after mass deletes.
- **Serializable Snapshot Isolation**: the algorithm behind the Serializable level in Postgres shows how it detects conflicts without locking every row it reads.
- **Table partitioning**: splitting `check_results` by month turns deleting old checks into dropping a whole partition, which frees disk space at once.
- **Replication and read replicas**: a streaming replica copies the write-ahead log to a second server, and its lag decides what a read from it can miss.
- **Other index types**: a block range index, or BRIN, stores one summary per range of pages and suits an append-only time column such as `checked_at` at a fraction of the B-tree size.
- **Connection poolers**: PgBouncer sits between many app processes and Postgres, and its transaction mode changes what session settings and prepared statements can do.
