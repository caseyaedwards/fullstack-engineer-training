Git is the version control system that records every change to your project as a snapshot, on your laptop and on GitHub. Every pull request, every continuous integration (CI) run and every container image tag on this course names a Git commit. Once you know the handful of objects Git stores and that a branch is only a name pointing at one of them, commands such as `merge`, `rebase` and `reset` stop being spells and become moves on a graph you can draw.

## What It Is

### Objects and Content Addressing

Git keeps your history in an **object database** under `.git/objects`. It stores four kinds of object:

- A **blob** holds the bytes of one file, and nothing else: no name, no permissions, no date.
- A **tree** is one directory: a list of entries, each with a mode, a type, an object ID and a name. A tree points at blobs for files and at other trees for subdirectories.
- A **commit** points at one tree, the snapshot of the whole project, and at its **parent** commits. It adds an author, a committer, two times and a message. The first commit has no parent. A merge commit has two.
- An **annotated tag** names one object, such as a commit, and adds a tagger, a date and a message.

Every object gets an ID that Git computes from its content with a **hash function**: a calculation that turns any number of bytes into a fixed-size fingerprint. The same bytes always give the same ID, and changing one byte gives a different one. Git calls that property **content addressing**: Git finds an object by what it holds, not by where it sits.

Git 2.x hashes with SHA-1, short for Secure Hash Algorithm 1, which gives 40 hexadecimal characters. Researchers produced two different files with the same SHA-1 in 2017, and Git now uses a hardened SHA-1 that detects that attack. A repository that `git init --object-format=sha256` creates uses SHA-256 and 64-character IDs instead. The Git project plans to make SHA-256 the default for new repositories in Git 3.0, which has no release date yet.

Content addressing gives Git three properties you rely on every day:

- **Integrity**: a commit ID covers its tree, which covers every blob, and its parent, which covers the whole history before it. Change one old file, and every later commit ID changes. Nobody can rewrite history quietly.
- **Deduplication**: a file that stays the same between commits keeps the same blob ID, and Git stores it once.
- **Cheap comparison**: two trees with the same ID hold the same files. Git compares directories by comparing IDs, without reading the files.

### Branches, HEAD and Tags

A **branch** is a name that points at one commit. Git stores it as a small file such as `.git/refs/heads/main` that holds a commit ID, or as a line in `.git/packed-refs`. A new commit on a branch moves the name forward to the new commit. Creating a branch writes one ID and copies no files, which is why branches cost nothing.

**HEAD** names where you are. On a branch, `.git/HEAD` holds `ref: refs/heads/main`: you are on `main`, and your next commit moves `main`. When HEAD holds a commit ID instead, Git calls it a **detached HEAD**: new commits belong to no branch, and switching away leaves them with no name.

A **tag** is a name that never moves. A **lightweight tag** is a name file, as a branch is. An annotated tag is a full object with its own ID. `git ls-remote` shows an annotated tag twice: the tag object, and a second line ending in `^{}` that **peels** the tag to the commit it names.

### The Working Tree, the Index and Commits

Three places hold versions of your files:

- The **working tree**: the files you edit.
- The **index**, also called the staging area: the snapshot your next commit records. `git add` copies a file from the working tree into the index.
- The **repository**: the commits. `git commit` turns the index into a tree, then writes a commit that points at it.

`git diff` compares the working tree with the index. `git diff --staged` compares the index with the last commit. `git status` summarizes both.

### Remotes, Fetch and Push

A **remote** is another copy of the repository, such as the one on GitHub that `git clone` names `origin`. Git keeps a local record of each remote branch, such as `origin/main`, which `git fetch` updates. By default, `git pull` is `git fetch` followed by a merge of the remote branch into yours. `git push` sends your commits and asks the remote to move its branch to your commit. Without `--force`, the remote accepts only a **fast-forward**: a move where the old commit is an ancestor of the new one, which loses nothing.

`git push --force` skips that check, and the remote branch drops every commit that only it holds. `git push --force-with-lease` refuses when the remote branch has moved since your last fetch, which makes it the safe form for your own branches. Never force-push `main`.

### Merge, Rebase and Squash

Three ways bring the commits of a branch into `main`:

- A **merge** writes a merge commit with two parents: the tip of `main` and the tip of the branch. History keeps every commit as it happened. When `main` has not moved since the branch started, Git fast-forwards instead and writes no merge commit.
- A **rebase** replays each commit of the branch on top of the new tip of `main`. Each replayed commit gets a new parent, and with it a new ID: the old commits stay in the database with no branch name. Rebase only commits that nobody else has.
- A **squash merge**, a GitHub option, writes one new commit on `main` with the combined change. The branch commits never join the history of `main`.

When both sides change the same lines, Git stops with a **merge conflict** and writes both versions into the file between `<<<<<<<`, `=======` and `>>>>>>>` markers. Edit the file to the version you want, remove the markers, `git add` it and continue with `git commit`, or `git rebase --continue` during a rebase.

### Nothing Is Lost Until Garbage Collection

`reset`, `rebase` and `branch -D` move or delete names, and none of them deletes an object. The **reflog** records every position of HEAD and of each branch on your laptop: `git reflog` lists them. By default, Git keeps an entry for 90 days, and for 30 days when no branch reaches its commit any more. After a bad `reset` or `rebase`, find the commit ID in the reflog and point a branch at it with `git branch rescue <id>`. Only `git gc` removes objects that nothing points at, and only once their reflog entries expire. After commands such as `git commit` and `git fetch`, Git runs `git maintenance run --auto`, which by default calls `git gc --auto`. That packs and prunes only once the loose objects pass a threshold, `6700` by default.

The exception is work you never committed or staged: `git reset --hard` and `git restore` overwrite it, and no Git command brings it back.

`sha1.New` returns a hash that accepts bytes in pieces: the header first, then the content, without joining them into one slice. `h.Sum(nil)` returns the 20 bytes of the result, and `hex.EncodeToString` writes them as the 40 characters Git prints. `crypto/sha1` is in the standard library. Use SHA-1 here only because Git does: for anything new, `crypto/sha256` is the right choice.

```txt
$ printf 'hello\n' | git hash-object --stdin
ce013625030ba8dba906f756967f9e9ca394464a

```

`git cat-file -p` prints any object by ID. Each line of the tree is a mode, a type, a blob ID and a name: the name lives in the tree, which is why renaming a file leaves its blob ID unchanged.

## Common Mistakes

- **Committing on `main` by accident.** GitHub rejects the next push, or your change skips review. Run `git status` before every commit. To move the commit, run `git branch week-01` to keep it, then `git reset --hard origin/main` on `main`, as Week 0 shows.
- **Force-pushing a shared branch.** The remote drops the commits that others pushed, and their next pull fails or loses work. Never force-push `main`. On your own branch, use `git push --force-with-lease`.
- **Rebasing commits that someone else has.** The rebased commits get new IDs, and anyone who built on the old ones now has two copies of the same change. Rebase only commits that exist on your laptop or on a branch nobody else uses.
- **Committing a secret, then deleting it in the next commit.** The blob stays in history, and anyone who clones the repository can read it. Revoke the secret at its service, issue a new one, and add the file to `.gitignore`.
- **Running `git reset --hard` with uncommitted work.** Git overwrites the files, and that work never reached the object database. Commit or stash first: `git stash push -m "before reset"` keeps a named copy.
- **Panicking after a bad rebase or reset.** The old commits still exist. Run `git reflog`, find the line before the mistake, and run `git branch rescue <id>`.
- **Writing messages such as `fix` or `wip`.** `git log` and `git blame` then tell you nothing six months later. Write what the commit changes in a subject line of 50 characters or fewer, and why in the body below it.
- **Committing generated files.** `bin/`, `node_modules/` and coverage profiles bloat every clone and conflict on every merge. List them in `.gitignore` before the first commit.

## Going Deeper

- **git bisect**: a binary search through history for the commit that broke a test. With `git bisect run go test ./...`, Git finds it without you.
- **Packfiles**: Git stores new objects as single compressed files, then `git gc` packs them into one file with deltas between similar objects. This explains why a clone downloads much less than the sum of all snapshots.
- **Signed commits and tags**: `git commit -S` and `git tag -s` add a signature that proves who created the object. GitHub shows a **Verified** badge for them.
- **Worktrees**: `git worktree add` checks out a second branch in another folder from the same object database, to work on two branches at once without cloning twice.
- **The SHA-256 transition**: how Git plans to move repositories from SHA-1 to SHA-256, and how a repository maps between the two while the ecosystem catches up.
