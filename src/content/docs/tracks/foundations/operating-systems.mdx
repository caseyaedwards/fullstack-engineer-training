Every program in the uptime monitor runs as a Linux process: on your laptop, in a container and on the server. The operating system decides when it runs, how much memory it gets, which files and sockets it can touch, and how it stops. When a service hangs at shutdown, runs out of memory or leaks connections, the answer sits in this layer, and this page gives you the words and the tools to find it.

## What It Is

### The Kernel and System Calls

The **kernel** is the core of the operating system. It runs with full access to the hardware, in **kernel space**. Your programs run in **user space**, where they cannot touch a disk, a network card or another program directly. To do any of that, a program asks the kernel through a **system call**, or syscall: `openat` opens a file, `read` and `write` move bytes, `connect` opens a TCP connection, `clone` starts a process or a thread.

Every Go function that talks to the outside world ends in system calls. `fmt.Println` ends in `write(1, ...)`, a write to file descriptor `1`. `strace -f ./your-monitor` on Linux prints every system call the monitor makes, with its arguments and its result, which makes it the tool of choice when a program fails with no useful log line.

### Processes

A **process** is one running copy of a program, together with everything the kernel tracks for it: its memory, its open files, its user, its current folder and its environment variables. The kernel gives each process a number, its **process ID** or PID. `/proc/<pid>/` on Linux shows that state as files.

A process starts a program in two steps. **fork** copies the calling process into a child, which then calls **exec** to replace its own program with a new one. The child keeps what it inherited: open file descriptors, environment variables and current folder. That inheritance is how a redirect in the shell reaches the program: the shell points file descriptor `1` of the child at the file between fork and exec. Go on Linux uses a variant of fork that shares memory until exec, which avoids copying a large parent, but the two steps stay the same.

A process ends by calling **exit** with an **exit status**, a number from `0` to `255`, where `0` means success. A signal can also end it. Either way, the kernel keeps a small record until the parent collects it with a **wait** system call. Until then, the dead child is a **zombie**: it holds no memory, only its PID and its status, and `ps` shows it with the state `Z` and the word `<defunct>`. A parent that never waits leaks zombies, and a machine that runs out of PIDs cannot start new processes. When a parent exits first, its children become **orphans**, and PID 1 adopts them and waits for them.

### Threads and Scheduling

A **thread** is one line of execution inside a process. All threads of a process share its memory and its file descriptors. The kernel **scheduler** picks which thread runs on each core of the CPU, short for central processing unit, and for how long. Since Linux 6.6, that scheduler is EEVDF, short for Earliest Eligible Virtual Deadline First, which replaced the older Completely Fair Scheduler. Switching a core from one thread to another is a **context switch**: the kernel saves the registers of one thread and loads those of the next, at a cost of a few microseconds.

A Go program runs several kernel threads from the start: `ps` marks it with `l` in the `STAT` column. The Go runtime runs its goroutines on those threads with a scheduler of its own, and `GOMAXPROCS` sets how many threads run Go code at the same instant. Week 5 covers the Go side of that split.

### Memory

Each process sees its own **virtual address space**: addresses that the kernel maps to real memory in **pages** of 4 KiB on x86-64 Linux. Two processes can use the same address and see different data. The kernel hands out pages only when the program first touches them, which is why a Go program can reserve far more address space than it uses. The number that matters is the **resident set size**, or RSS: the memory a process holds right now, in the `RSS` column of `ps`.

When the machine runs out of memory, or a container reaches the memory limit of its **cgroup**, short for control group, the kernel feature that caps the memory and CPU time of a group of processes, the kernel **out-of-memory killer** picks a process and ends it with `SIGKILL`. No handler runs and no log line appears from the process. The only traces are a kernel message in `dmesg`, exit code `137`, and `OOMKilled` in Docker or Kubernetes.

### Signals

A **signal** is a short notice the kernel delivers to a process. `SIGTERM` asks a process to exit, and a program can catch it and clean up first. `SIGKILL` ends a process at once, and nothing can catch, block or ignore it. `SIGINT` comes from Ctrl+C. `SIGCHLD` tells a parent that a child has changed state, which is the cue to wait for it. A process can also set a signal to be ignored, and that setting survives exec: a child started with `SIGTERM` ignored ignores it too.

Every service manager stops a program the same way: `SIGTERM`, a grace period, then `SIGKILL`. systemd waits 90 seconds by default, Docker 10 and Kubernetes 30. A program that handles `SIGTERM` finishes its current work and exits cleanly. A program that ignores it loses its in-flight work when the `SIGKILL` arrives.

`exec.CommandContext` ties the child to a context. When the context ends, the command calls its `Cancel` function. The default `Cancel` sends `SIGKILL`, which gives the child no chance to clean up, and `Run` replaces it with a `SIGTERM`. `WaitDelay` bounds what happens next: one second after the context ends, `Wait` sends `SIGKILL` to a child that still runs, and closes any pipes the child holds open.

A child that exits with a non-zero status returns an `*exec.ExitError`, and `Run` turns it into a plain exit code with a `nil` error: for a caller that runs a health script, exit code `3` is an answer, not a failure of `Run`. A timeout is a failure, and `Run` returns an error that wraps the context error, which callers test with `errors.Is`. A child that a signal ends has no exit code. When the signal does not come from `Run`, as with a `SIGKILL` from the out-of-memory killer or a `SIGSEGV`, the signal for an invalid memory access, `Run` returns `-1` and an error that wraps the `*exec.ExitError`, with a message such as `signal: killed`.

## Common Mistakes

- **Running a service behind a shell that swallows signals.** A container that starts `sh -c "./migrate && ./worker"` makes `sh` PID 1, with the worker as its child. `sh` does not pass `SIGTERM` on. The worker never hears it, and every stop takes the full grace period and ends in `SIGKILL`. Start the program directly, or put `exec` in front of the last command: `sh -c "./migrate && exec ./worker"`.
- **Never waiting for a child.** A program that calls `cmd.Start` and forgets `cmd.Wait` leaves a zombie per child. Over weeks, the process table fills. Pair every `Start` with a `Wait`, or call `Run`, which does both.
- **Using `exec.CommandContext` without `WaitDelay`.** When a child starts a grandchild that inherits its stdout pipe, `Wait` blocks until that pipe closes, long after the child has exited. Set `WaitDelay` to bound the wait.
- **Treating every non-zero exit as an exception.** `grep` exits `1` when it finds nothing. A health script exits `2` for a warning. Read `ExitCode()` and decide what each code means for your program.
- **Reading a memory limit from the host.** Inside a container, `free` and `/proc/meminfo` show the memory of the whole machine, not the cgroup limit. A program that sizes its caches from them grows past the limit, and the out-of-memory killer ends it with `SIGKILL`. Read `/sys/fs/cgroup/memory.max`, or set `GOMEMLIMIT` for a Go program.
- **Catching `SIGTERM` and then doing nothing.** A handler that only logs the signal keeps the program running until `SIGKILL`. The handler has to cancel the work and return from `main`.

## Going Deeper

- **Process groups and sessions:** the terminal sends Ctrl+C to a whole process group, which explains why one Ctrl+C stops every command of a pipeline, and why `nohup` keeps a program alive after you close the terminal.
- **cgroups v2:** the kernel feature that limits CPU time, memory and disk traffic for a group of processes, and the base of every container limit in Weeks 6 and 15.
- **Namespaces:** they give a process its own view of PIDs, the network and the filesystem. A container is a process in its own set of namespaces.
- **Virtual memory and the page cache:** knowing how the kernel maps files into memory explains RSS numbers, slow first reads and why `fsync` exists.
- **eBPF, short for extended Berkeley Packet Filter:** small programs that run inside the kernel and trace system calls, scheduling and network events with little overhead.
