In <a href={weekHref(12)}>Week 12</a>, you found a bug with a debugger and a profiler on your own laptop. A program in production gives you neither: you cannot pause it, and you did not see the request that failed. You get only what the program writes down while it runs. **Observability** is how well you can answer a new question about a running system from that output alone, without shipping new code first. This week, every program of your monitor learns to explain itself in three ways: JSON logs, Prometheus metrics and OpenTelemetry traces. Compose gains the tools that collect and show them.

## Goals

- Tell logs, metrics and traces apart, and pick the one that answers a given question.
- Log one JSON object per event with the Go `log/slog` package, with the trace ID on every line logged inside a span.
- Count and time requests and checks with Prometheus counters, gauges and histograms, with labels that stay few.
- Trace one request and one job through the api, the worker and Postgres with OpenTelemetry, and send the spans through a collector to Jaeger.
- Run Prometheus, Grafana, the collector and Jaeger in Compose, and read a dashboard built from your own metrics.

## Concepts

### Three Signals

Each type of output, called a **signal**, answers a different question:

- A **log** line records one event: a request answered, a check that failed, a login refused. Logs answer what happened to this one thing.
- A **metric** is a number measured over time: requests per second, checks that failed in the last five minutes, jobs in the queue. Metrics answer how much and how fast, for the whole system, and stay cheap at any traffic.
- A **trace** follows one unit of work, such as one request or one job, through every step and every program it touches, with the time of each step. Traces answer where the time went.

A metric tells you that the 95th-percentile latency of the api doubled at 14:02. A trace of one slow request shows that the time goes to one SQL query. The log lines of that request, found by its trace ID, show the monitor ID and the error. Each signal hands you to the next.

### Structured Logs

Up to now, your programs log lines such as `check url=https://example.com status=503 dns_ms=1.2 connect_ms=10.3 tls_ms=20.1 first_byte_ms=41.0`. A person reads that line well. A program that wants every check of one monitor has to parse it, finds no monitor ID in it, and a URL with a space in it breaks the parser. A **structured log** writes each event as named fields in a format that machines read, here JSON:

```txt wrap
{"time":"2026-10-11T09:44:04.927988165Z","level":"INFO","msg":"check","service":"worker","job_id":1,"monitor_id":2,"url":"http://127.0.0.1:8080/api/monitors/999","up":false,"status":404,"dns_ms":0,"connect_ms":0.1,"tls_ms":0,"first_byte_ms":2.3,"trace_id":"1f24d735cb586a737084b322d85c39f7","span_id":"31411bfea1b02637"}
```

The Go standard library has a structured logger, `log/slog`, since Go 1.21. Every line carries a **level**, which says how much the event matters: `DEBUG`, `INFO`, `WARN` or `ERROR`. Log aggregation tools, such as Grafana Loki or the log viewer of a cloud provider, filter on any field: `monitor_id == 2 and level == "ERROR"`. JSON also escapes a newline inside a value, which keeps an attacker from forging a whole second line through a crafted email address.

A filter works only when every program spells a field the same way. This week, while every line moves to `slog`, the field names get one spelling across all four programs: `err` for an error, and `job_id`, `monitor_id`, `incident_id` and `user_id` for IDs. In the text lines, the alert line of Week 9 names `incident=` and `monitor=`, and the check line carries no IDs at all; in JSON, it gains `job_id` and `monitor_id`. The `trace_id` field ties a log line to a trace. One rule keeps the log useful and safe: log IDs, causes and durations, never passwords, session tokens or full request bodies.

### Metrics: Counters, Gauges and Histograms

A Prometheus metric has a name and a set of **labels**, key-value pairs that split it into parts. Each distinct set of label values is one **time series**: a list of timestamped values, one per scrape. `http_requests_total{route="/healthz",code="200"}` and `http_requests_total{route="/healthz",code="500"}` are two series of one metric. Three types cover this week:

- A **counter** only goes up, and starts again at zero when the program restarts. `monitor_checks_total{result="error"}` counts failed checks since start. The raw number means little; its rate of increase is the signal. In PromQL, `rate(monitor_checks_total[5m])` is the increase per second over the last five minutes, with restarts accounted for.
- A **gauge** goes up and down, and holds a current value: `monitor_jobs_queued`.
- A **histogram** counts observations, such as request durations, into **buckets** by upper bound. The series `http_request_duration_seconds_bucket{le="0.1"}` counts every request that took 0.1 seconds or less; `le` stands for less than or equal. `_sum` and `_count` hold the total and the number of observations. From the buckets, `histogram_quantile` estimates a **percentile**: the 95th percentile, or p95, is the duration that 95% of requests stay under.

An average hides the slow requests that users notice. Take twenty requests: nineteen take 10 ms, one takes 3 seconds. The average of 160 ms looks acceptable, yet it hides that one request in twenty takes 3 seconds. The p99 shows the 3 seconds.

Every label value multiplies the number of series, and Prometheus keeps each series in memory. The number of series is the **cardinality** of a metric. A `route` label with eight routes is cheap. A `path` label makes one series per monitor ID, and one more for every path a scanner tries. Label only by values from a short, fixed list: route patterns, status codes, results.

### Traces, Spans and Context

A **trace** is a tree of **spans**. A span is one timed step: it has a name, a start time, a duration, **attributes** (key-value details such as the status code), a status, and the ID of its parent span. The first span of a trace, the **root span**, has no parent. A **trace ID** is 16 random bytes, written as 32 hexadecimal characters; a span ID is 8 bytes.

In Go, the current span travels in the `context.Context` that every function already passes along. A child span starts from the context of its parent. That is why a log line written with `slog.InfoContext(ctx, ...)` finds the trace ID: it is in `ctx`.

Between programs, the trace travels in the W3C `traceparent` HTTP header: `00-<trace ID>-<parent span ID>-01`, where the final `01` sets the **sampled** bit: the caller records this trace, and asks the next program to record its part too. A program that reads the header joins the trace of the caller. This is called **propagation**.

### Why a Collector

Jaeger accepts OTLP itself, and the Go programs reach it without help. The **OpenTelemetry Collector** sits in between anyway, for three reasons:

- **Change one file, not every program.** The programs speak OTLP to the collector. To send traces to Grafana Tempo or a cloud vendor instead of Jaeger, you change the exporter in `otel-collector.yaml`.
- **Batching and retries.** When Jaeger restarts, the collector keeps the spans in a queue and retries, which keeps the programs fast and simple.
- **Processing.** The collector can drop, thin out or redact spans in one place before they leave your network.

OpenTelemetry, OTel for short, is the vendor-neutral standard for traces, metrics and logs: an API, SDKs for each language, the OTLP wire format and the collector. This week uses OTel for traces and Prometheus for metrics, the most common pairing.

### Step 6: Start Tracing

<CodeFrom file="go/week13/your-monitor/internal/obs/trace.go" region="tracing" lang="go" title="internal/obs/trace.go" />

`OTEL_EXPORTER_OTLP_ENDPOINT` is the standard variable for the collector address; the exporter appends `/v1/traces` to it. Without it, OTel keeps its default **no-op** tracer: spans go nowhere and cost a few nanoseconds, which keeps the tests and `go run` free of setup. `WithBatcher` sends finished spans in batches every 5 seconds. `service.name` labels every span with the program it comes from. The api and the worker call it in `main` after the logger, as the worker setup above shows, and defer the shutdown.

**Sampling** decides which traces get recorded. Without `sdktrace.WithSampler`, the SDK reads `OTEL_TRACES_SAMPLER` and defaults to `parentbased_always_on`: a request without a `traceparent` starts a recorded trace, and a request with one follows the sampled bit of the caller. Every request becomes a trace, the Compose healthcheck on `/healthz` every 10 seconds included. On a busy service, keep a share: `OTEL_TRACES_SAMPLER=parentbased_traceidratio` with `OTEL_TRACES_SAMPLER_ARG=0.1` starts a recorded trace for one request in ten. A caller that sends `00` in place of `01` switches off the api span: the log line still carries the trace ID, and Jaeger never receives the trace. Your api trusts the header of any caller, which Step 10 uses. An api open to the internet removes `traceparent` at its edge proxy and starts its own traces, which keeps strangers from deciding what gets recorded.

<CodeFrom file="go/week13/your-monitor/internal/api/trace.go" region="trace" lang="go" title="internal/api/trace.go" />


```txt wrap
{"time":"2026-10-11T09:44:16.372942589Z","level":"INFO","msg":"request","service":"api","method":"GET","route":"/api/monitors","path":"/api/monitors","status":200,"bytes":348,"duration_ms":0.454,"trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","span_id":"1f9508dbbf8ea346"}
```

## Observe It

<ObserveIt>

Read the dashboard from the top. The queries are the ones in `your-monitor.json`; paste any of them into `localhost:9090/query` to see the raw numbers.

| Panel | Query | What healthy looks like |
| --- | --- | --- |
| Checks per second, by result | `sum by (result) (rate(monitor_checks_total[5m]))` | Flat lines: monitors divided by their intervals |
| Check duration, 50th and 95th percentile | `histogram_quantile(0.95, sum by (le) (rate(monitor_check_duration_seconds_bucket[5m])))` | Well under `-timeout`; the panel draws the same query with `0.5` as well |
| Jobs queued | `monitor_jobs_queued` | At most one per monitor |
| Oldest queued job | `monitor_jobs_oldest_seconds` | Under a few seconds |
| API requests per second, by route and status | `sum by (route, code) (rate(http_requests_total[5m]))` | `200` on every route; `401` and `404` only where you expect them |
| API latency, 95th percentile, by route | `histogram_quantile(0.95, sum by (le, route) (rate(http_request_duration_seconds_bucket[5m])))` | Single-digit milliseconds on a laptop |
| API share of 5xx answers | `(sum(rate(http_requests_total{code=~"5.."}[5m])) or vector(0)) / sum(rate(http_requests_total[5m]))` | 0 |

`sum by (result)` adds up the series of every worker container and keeps only the `result` label. `or vector(0)` matters in the last query: with no 5xx answer since start, no 5xx series exists, and a division by nothing draws nothing.

Watch for these patterns:

- **The `error` line rises for every monitor at once.** The worker lost its network or its DNS resolver, not the sites. Compare with the `down` line, which moves per site.
- **Check p95 sits at or above `-timeout`.** More than one site in twenty never answers, and each of its checks takes the full 5 seconds. The worker histogram has bounds at 5 and 6 seconds for this reason: a timed-out check lands between them. Find it with the `check` spans in Jaeger: search the `worker` service for the tag `check.result=error`.
- **API p95 rises on one route only.** Open a slow trace of that route in Jaeger: the SQL span inside it shows whether Postgres takes the time.
- **`monitor_jobs_oldest_seconds` grows round after round.** The workers fall behind. See [Operate It](#operate-it).

Week 18 turns these queries into recording rules and burn-rate alerts.

</ObserveIt>

## Operate It

<OperateIt>

**The worker stops.** Run `docker compose stop worker` and wait 90 seconds. At its next scrape, Prometheus marks the `worker` target down, and `up{job="worker"}` drops to `0`: the target is a fixed name in `prometheus.yml`, and a failed scrape of a fixed target sets `up` to `0`, which an alert on `up == 0` catches. The checks panel goes blank: no worker, no series. The scheduler keeps queuing, and the queue gauges 90 seconds after the stop read:

```txt
monitor_jobs_queued          3
monitor_jobs_oldest_seconds  40.002386
```

`monitor_jobs_queued` stays at the number of monitors, three here, because the `NOT EXISTS` of Week 9 queues at most one job per monitor. The age is the honest number: it counts from the run_at of the oldest waiting job, not from the stop, and climbs by 5 seconds each round until a worker returns. Alert on the age, not on the count.

**The collector is down.** The programs keep serving and checking. Spans pile up in the batch of each program, and each failed export becomes one `WARN` line, until the batch gives up and drops those spans. In Compose, a stopped container loses its name in the Docker DNS server at `127.0.0.11`, and the line reads, for example:

```txt wrap
{"time":"2026-10-11T08:06:39.43797788Z","level":"WARN","msg":"tracing","service":"api","err":"traces export: Post \"http://otel-collector:4318/v1/traces\": dial tcp: lookup otel-collector on 127.0.0.11:53: no such host"}
```

Tracing never takes a program down with it, and traces for that window are lost. Metrics and logs still cover it.

**Jaeger is down.** The collector queues the spans and logs `Exporting failed. Will retry the request after interval.` Its own metrics show the queue: `otelcol_exporter_queue_size{exporter="otlp_grpc/jaeger"}` grows, and `otelcol_exporter_sent_spans` stops. When Jaeger returns, the collector sends the queue. Jaeger in this setup keeps traces in memory, which means a restart of Jaeger itself loses every trace it held.

**A scrape target is down.** `localhost:9090/targets` shows the target as `DOWN` with the scrape error, for example `Get "http://scheduler:2112/metrics": dial tcp: lookup scheduler on 127.0.0.11:53: no such host`. At the first failed scrape, Prometheus marks every series of that target stale, and its metrics vanish from queries at once, which leaves the queue panel blank.

**A label explodes.** Someone labels requests with `r.URL.Path`. Every monitor ID, and every path a scanner tries, becomes a new series that stays in Prometheus memory for hours. Count the series of a metric with `count(http_requests_total)`: it must stay near routes times methods times status codes, a few dozen here.

| What you see | What it points to |
| --- | --- |
| `up{job="worker"}` is `0` and the checks panel is blank | The worker is down or its `-debug-addr` is wrong |
| `monitor_jobs_oldest_seconds` climbs, `monitor_jobs_queued` flat | No worker claims jobs |
| `WARN` lines with `msg` `tracing` in the program logs | The collector is down or unreachable |
| `otelcol_exporter_queue_size` grows | Jaeger is down: the collector holds the spans |
| `count(http_requests_total)` keeps growing | A label takes values from user input |
| Jaeger shows no traces, logs have no `trace_id` | `OTEL_EXPORTER_OTLP_ENDPOINT` is not set for that program |

</OperateIt>

## Side Lab

<SideLab title="Compute a percentile from histogram buckets by hand and check it against Prometheus">

`histogram_quantile` does not know the real durations, only the bucket counts. It assumes the observations spread evenly inside a bucket and interpolates. Repeat its work once by hand.

**1. Read the buckets.** In `localhost:9090/query`, run `monitor_check_duration_seconds_bucket` and note each `le` with its value. Without `rate`, the counts cover every check since the worker started. The steps below use these counts as an example; yours differ:

```txt
le=0.01   9
le=0.025  9
le=0.05   9
le=0.1    12
le=0.25   12
... every bucket up to +Inf: 12
```

Twelve checks: nine took 10 ms or less, and three between 50 and 100 ms, such as lookups of `no-such-host.example` that wait for an answer from a DNS server.

**2. Find the rank.** The p95 is the duration below which 95% of the twelve checks fall: rank 0.95 × 12 = 11.4. The first bucket with a count of 11.4 or more is `le=0.1`, with 12. The bucket below it, `le=0.05`, holds 9.

**3. Interpolate.** Inside the bucket from 0.05 to 0.1, the rank 11.4 sits at (11.4 − 9) / (12 − 9) = 0.8 of the way: 0.05 + 0.8 × 0.05 = 0.09 seconds.

**4. Check.** Run `histogram_quantile(0.95, monitor_check_duration_seconds_bucket)`. On the counts above, Prometheus returns `0.08999999999999998`, the 0.09 from step 3 with floating-point rounding. Do the same for p50: rank 6 falls in the first bucket, between 0 and 0.01, at 6/9 of the way: Prometheus returns `0.006666666666666666`. Then repeat both on your own counts. When every check lands in the first bucket, as on a laptop with the DNS answers cached, the p95 reads 0.95 × 0.01 = `0.0095`, whatever the real durations.

**5. Think about the error.** The real p95 of those twelve checks lies anywhere from 50 to 100 ms; the estimate says 90. Buckets set the precision. Suppose two of the three slow checks took under 75 ms. With an extra bound at 0.075, that bucket holds 11, and the rank 11.4 falls between 0.075 and 0.1: 0.075 + 0.4 × 0.025 = 0.085. More bounds, a narrower range for the answer, and one more series per bound.

</SideLab>
