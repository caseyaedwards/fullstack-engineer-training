Kubernetes runs containers on a set of machines and keeps them running the way you describe. You never tell it to start a container. You store a description of what you want, and a set of control loops works, without end, to make the cluster match it. As a full-stack engineer, you write those descriptions for every program you ship, and when a pod does not start, you read the cluster state to find which loop is stuck and why. Facts on this page are for Kubernetes 1.36.

## What It Is

### Objects, Desired State and Control Loops

Everything in Kubernetes is an **object**: a Deployment, a Pod, a Service, a Secret. You write objects as **manifests**: documents in YAML, an indented text format for data, and `kubectl apply` sends them to the cluster. `kubectl` is the command-line client of Kubernetes. Most objects have two halves. The **spec** is the desired state, which you write. The **status** is the observed state, which the cluster writes.

A **controller** is a program that runs a **control loop** for one type of object: read the spec, read what exists, act on the difference, and repeat. The loop is **level-triggered**: it acts on the state it finds now, not on a list of events it missed. A controller that restarts after a crash reads the current state and carries on, with no history to replay. A node that dies, a pod that exits, a `kubectl scale`: each one shows up as a difference on the next pass of some loop, and the loop repairs it.

Controllers never talk to each other. Each one watches the objects it cares about through the API server, and writes the objects that the next controller watches. A Deployment controller writes ReplicaSets, a ReplicaSet controller writes Pods, the scheduler writes a node name into each Pod, and the kubelet on that node starts the containers. Each loop is small and does one job.

A small cluster such as k3s on one virtual private server (VPS) runs all of these on one machine, and the node is its own control plane. k3s keeps the cluster state in SQLite by default, in place of etcd. kind runs each node as a Docker container on your laptop.

### Workloads

| Object | Runs | Use it for |
| --- | --- | --- |
| Pod | one or more containers that share an IP address and volumes | nothing directly: a controller creates pods for you |
| ReplicaSet | a number of identical pods from one template | nothing directly: a Deployment manages its ReplicaSets |
| Deployment | ReplicaSets, one per template revision, with rolling updates | stateless programs such as the api, the worker and the web server |
| StatefulSet | pods with stable names, such as `postgres-0`, and one volume each | databases and other programs that keep state on disk |
| DaemonSet | one pod on every node | log collectors and node agents |
| Job, CronJob | pods that run to completion, once or on a schedule | migrations and backups |

A Deployment finds its pods by **labels**, key and value pairs such as `app.kubernetes.io/name: api`, through a **selector**. When you change the pod template, such as the image tag, the Deployment controller creates a new ReplicaSet and moves pods from the old one to the new one a few at a time: a **rolling update**. `maxSurge` and `maxUnavailable` bound each step, and the old ReplicaSet stays at zero pods as a revision that `kubectl rollout undo` returns to.

### Services and Proxy Modes

Pods come and go, and each new pod gets a new IP address. A **Service** gives a set of pods one stable virtual address, the ClusterIP, and a DNS name such as `api.your-monitor.svc.cluster.local`. No process listens on a ClusterIP. kube-proxy on each node writes kernel packet rules that rewrite each connection to that address into a connection to one ready pod. It has three modes on Linux:

- **iptables**: the default in Kubernetes 1.36. One chain of rules per Service, and one rule per pod, which the kernel walks in order. kind uses it, and the <WeekLink n={15} anchor="side-lab">Week 15 side lab</WeekLink> reads its rules.
- **nftables**: uses nftables, the successor to iptables in the Linux kernel, which looks up a Service in a map instead of walking a list. It handles endpoint changes faster, and the gap grows with the number of Services. It needs kernel 5.13 or newer, and the Kubernetes documentation names it as the future default.
- **IPVS**: uses the kernel load balancer, IP Virtual Server, with hash tables and several balancing algorithms. Kubernetes 1.35 deprecates it, 1.40 turns it off by default and 1.43 removes it. Do not start a new cluster on it.

Set the mode explicitly in the kube-proxy configuration. A cluster that relies on the default changes its packet path on the upgrade that changes the default.

### Configuration, Secrets and RBAC

A **ConfigMap** holds settings, and a **Secret** holds passwords and keys. Both reach a container as environment variables or as files. A Secret is not encrypted by default: etcd stores it as plain bytes, and the API returns its values in base64, which is an encoding, not encryption. Turn on **encryption at rest** in the API server, as the k3s setting `secrets-encryption` does in Week 16, and the datastore holds only ciphertext.

What protects a Secret is who can read it, and **RBAC**, role-based access control, decides that:

- A **ServiceAccount** is an identity for a program, such as a continuous integration (CI) pipeline or a pod.
- A **Role** lists **verbs**, such as `get`, `list`, `watch`, `create` and `patch`, on **resources**, such as `deployments` or `secrets`, in one **namespace**, a named group of objects inside the cluster. A **ClusterRole** does the same across the cluster.
- A **RoleBinding** grants a Role to users, groups or ServiceAccounts, and a **ClusterRoleBinding** grants a ClusterRole everywhere.

RBAC only adds permissions, and the API server refuses anything no rule allows. The <TrackLink slug="iam">identity and access management (IAM) track</TrackLink> draws the `deployer` ServiceAccount of Week 16 with its Role and RoleBinding. Three details catch people. `list` and `watch` on `secrets` return every value in full, the same as `get`. Permission to create pods in a namespace is permission to read its Secrets, because a pod can mount any Secret of its namespace. And `kubectl auth can-i get secrets --as=system:serviceaccount:your-monitor:deployer` answers what an identity can do before you hand it out.

### Versions and Skew

Kubernetes ships three minor releases a year, and each one gets patches for about 14 months. The project patches the newest three minor versions, and a cluster more than two minor versions behind the newest release runs without security fixes. `kubectl` works with an API server one minor version older or newer: `kubectl` 1.36 talks to 1.35, 1.36 and 1.37. The course pins `kubectl` and the cluster to 1.36.

- The first loop sorts the pods into `current`, made from the desired template, and `outdated`, made from any other. It also records every name in use.
- `want` treats a negative replica count as zero. `missing` counts the pods to create, and each one gets the first name of the form `<template>-<n>` that no pod holds.
- Every outdated pod gets a delete. When more current pods run than wanted, the ones after the first `want`, in name order, get a delete too.
- Creates come before deletes, the way a rolling update with `maxUnavailable: 0` starts a new pod before it stops an old one.

The real controllers differ in the details. A Deployment names each ReplicaSet after a hash of its pod template, and records that hash in a `pod-template-hash` label on every pod. A pod name ends in five random characters. The rolling update creates and deletes a few pods per step, bounded by `maxSurge` and `maxUnavailable`, and waits for each new pod to become available. The shape stays the same: compare, act on the difference, repeat.

## Common Mistakes

- **A selector that matches no pods.** The API server refuses a Deployment whose selector does not match its own template labels. It accepts a Service whose selector matches no pod labels, and that Service sends every connection nowhere, with no error anywhere. Keep the selector labels and the template labels in one place, and check them with a test, as Week 15 does.
- **`replicas` in a manifest that an autoscaler scales.** Every `kubectl apply` resets the count, and the autoscaler scales back up a moment later. Remove `replicas` from every Deployment that a HorizontalPodAutoscaler manages.
- **A liveness probe that checks a dependency.** The kubelet restarts a container whose liveness probe fails. When Postgres goes down, the kubelet restarts every api pod, and the restarts fix nothing. Keep liveness to the process itself, and put dependencies in readiness, which only takes the pod out of its Service.
- **No requests on a container.** The scheduler places the pod as if it needs nothing, and the node runs out of memory under load. Set processor and memory requests on every container, and a memory limit.
- **A Secret treated as encrypted.** base64 is an encoding, and anyone with `get`, `list` or `watch` on Secrets, or permission to create pods in the namespace, reads every value. Encrypt etcd at rest and grant Secret access to as few identities as possible.
- **The `latest` image tag.** With `latest`, the default pull policy is `Always`: each new pod pulls whatever the tag points at that moment, and two pods of one Deployment run two versions under one name. A push of a new `latest` changes no pod template, which means no rollout starts, and a rollback has no older name to return to. Tag images with the commit SHA, the Git hash of the commit.
- **Changes made with `kubectl edit` in production.** The next `kubectl apply` from Git overwrites them, or keeps a change nobody reviewed. Change the manifests in Git and apply them.

## Going Deeper

- **Server-side apply:** the API server tracks which client owns each field, which ends the fights between `kubectl`, controllers and autoscalers over the same object.
- **Operators and custom resources:** your own object types with your own control loop, built on the same pattern as `Reconcile` with a library such as controller-runtime.
- **NetworkPolicy:** firewall rules between pods. Until a policy selects a pod, it accepts traffic from every other pod, and a policy works only when the network plugin of the cluster enforces it.
- **Pod Security Standards and admission control:** the API server checks each pod against a profile, such as `restricted`, before it stores it, but only in a namespace labeled to enforce one. Without the label, the level is `privileged`, which allows everything. Your own policies run as admission control too.
- **Gateway API:** the successor to Ingress for routing HTTP traffic into the cluster, with roles split between cluster operators and application teams.
- **Cluster upgrades:** one minor version at a time, control plane first, then the nodes, with the deprecated API versions removed from every manifest before the upgrade.
