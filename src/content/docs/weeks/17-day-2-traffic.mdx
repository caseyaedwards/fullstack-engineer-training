## Concepts

### Scaling Out with the HorizontalPodAutoscaler

**Scaling out** adds copies of a program; **scaling up** gives one copy a bigger machine. A **HorizontalPodAutoscaler**, HPA for short, scales a Deployment out and back in. It needs one number per pod, and the simplest one is CPU.

k3s ships **metrics-server**, a small program that collects the CPU and memory use of every pod from the kubelet on each node every 15 seconds, and serves the latest numbers through the Kubernetes API. `kubectl top pods` reads them, and the HPA controller does too. The controller divides the CPU use of each pod by its CPU **request**, the share of a CPU that the pod asked for in <a href={weekHref(15)}>Week 15</a>, and averages the percentages. Every 15 seconds, it computes `desired replicas = ceil(current replicas × current average / target average)`. With two api pods at 140% of their request and a target of 70%, it asks for four. A pod without a CPU request has no percentage: the HPA shows `<unknown>` and does nothing.

Two defaults shape what you see. Scaling up happens at once, by up to four pods or double the count every 15 seconds. Scaling down waits for a **stabilization window** of 300 seconds and uses the highest count it computed in that window, which keeps the count from jumping with every spike.

The HPA writes its count into the scale of the Deployment, the same field that a `replicas` line in your manifest sets, and the ReplicaSet starts or stops pods to match. That shared field causes the classic mistake. When your manifest says `replicas: 2` and the HPA has scaled to four, the next `kubectl apply` sets two again, and the HPA scales back up 15 seconds later. Remove `replicas` from every Deployment that an HPA scales.

CPU is a good signal for the api: every request costs CPU. It is a weak signal for the worker. A worker spends most of a check waiting on the network, and a long queue of slow sites leaves its CPU low. <a href={weekHref(13)}>Week 13</a> gave you the honest number, `monitor_jobs_oldest_seconds`. Scaling on a Prometheus metric needs an adapter that serves it through the Kubernetes API, such as prometheus-adapter or KEDA. This week, the worker scales on CPU, and you watch the queue age to judge whether CPU is enough.

### Rolling Updates and Rollbacks

Every change to the pod template of a Deployment, such as a new image tag or a new environment variable, creates a new **ReplicaSet** and a new **revision**. A **rolling update** moves the pods from the old ReplicaSet to the new one in steps. Two settings bound each step: `maxSurge`, how many pods above the wanted count can exist during the rollout, and `maxUnavailable`, how many pods below the wanted count the rollout allows.

With `maxSurge: 1` and `maxUnavailable: 0`, the controller starts one new pod, waits until it is **available**, then stops one old pod, and repeats. Available means ready, and ready for `minReadySeconds` in a row: a pod that passes its first probe and crashes 5 seconds later never counts. When no step succeeds for `progressDeadlineSeconds`, Kubernetes marks the rollout as failed. The old pods keep serving, because none of them stops before a new one is available.

Two different programs pick the pod for a request. Traefik sends each request to a web pod, from the endpoints of the web Service it watches. nginx in that pod sends `/api/` on to the api Service, and **kube-proxy**, the part of k3s that implements Services on the node, picks an api pod. One race remains. When a pod is told to stop, the kubelet sends `SIGTERM` while the endpoint removal is still on its way to Traefik and to kube-proxy. For a moment, new requests still arrive at a pod that is shutting down, and they fail. A **preStop hook** runs before `SIGTERM`: a 5-second pause there keeps the pod serving while the rest of the cluster catches up. Both web and api need one. The `sleep` action of a hook, stable since Kubernetes 1.34, needs no `sleep` program in the image, which matters for images built `FROM scratch`, as yours are.

`kubectl rollout undo` switches the Deployment back to the pod template of the previous revision, as a new rolling update. It restores the pod template only: ConfigMaps, the HPA and the Services stay as they are. And it changes the cluster, not your repository. The next `deploy.yml` run from <a href={weekHref(14)}>Week 14</a> applies the manifests and the image tag it is given, and the bad version comes back. Use `undo` to stop the damage in seconds, then run `deploy.yml` with the commit SHA of the last good version to make the rollback stick.

### Rate Limits and Token Buckets

A **rate limit** caps how many requests of one client get answered in a span of time. The api needs one for three reasons: one visitor with a loop must not slow the status page for everyone, a scanner must not fill your logs, and each login guess costs a bcrypt check of about 0.3 seconds of CPU, which <a href={weekHref(11)}>Week 11</a> left uncapped across email addresses.

A **token bucket** holds up to `burst` tokens and refills at `rate` tokens per second. Each request takes one token. A request that finds the bucket empty gets `429 Too Many Requests` and a `Retry-After` header that says when a token is back. The burst absorbs a status page that loads twenty results at once; the rate caps a loop. The `golang.org/x/time/rate` package implements one bucket, and Traefik uses the same package inside its own rate limiter.

The hard part is the key. A per-client limit needs the client address, and behind proxies the api sees only the last proxy. Each proxy appends the address it received the request from to the `X-Forwarded-For` header, XFF for short. A client can send that header too, with any text in it. Only the entries that your own proxies appended are true, and they sit at the right end. The api trusts a list of networks, here the k3s pod network `10.42.0.0/16`, and walks the header from the right while each address belongs to one of them. The first address outside is the client.

Each api pod keeps its buckets in its own memory. With four replicas, a client whose requests kube-proxy spreads over all of them gets up to four times the limit. That is why the edge gets a limit too: Traefik sees every request before anything spreads it. k3s runs one Traefik pod, which makes the Traefik limit the one for the whole cluster.

### Backups You Have Restored

<a href={weekHref(8)}>Week 8</a> set two rules: keep a backup on another machine, and restore it on a schedule. A dump on the VPS disk breaks the first rule: the disk, the VPS or one `kubectl delete namespace` takes it with the data. This week, each dump leaves the box at once, to **object storage**, a service that stores files, called objects, in buckets over an S3-compatible API. It leaves encrypted with **age**, a small file encryption tool: the VPS holds only the public key, which can encrypt and never decrypt. The cluster gets only an upload key: an attacker on the VPS cannot read your backups, and the bucket rules of Step 11 keep what that key can hide or overwrite for 30 days.

Two numbers describe a backup plan. The **recovery point objective**, RPO, is how much data you accept to lose. It is the interval between two copies that reached another machine: with one upload a night, up to 24 hours of check results. The **recovery time objective**, RTO, is how long you accept the monitor to stay down while you restore. You do not know how long a restore takes until you time one. A **restore drill** does exactly that, into a new, empty server, and fails loudly when the newest backup is missing, too old, unreadable or not the database you meant to save. It runs on your laptop, the one place that holds the private key. The <a href={trackHref('backups')}>Backups track</a> covers physical backups with write-ahead log (WAL) archiving, which brings the RPO down to minutes.

<CodeFrom file="go/week17/your-monitor/internal/ratelimit/ratelimit.go" region="limiter" lang="go" title="internal/ratelimit/ratelimit.go" />

`rate.NewLimiter(limit, burst)` is one bucket. `ReserveN(now, 1)` takes a token and says how long the caller has to wait for it. The api never waits: when the delay is above zero, `CancelAt` puts the token back and `Allow` returns the delay, which becomes `Retry-After`. Every method takes `now` as a value, which gives the tests a clock they control.

A map that grows with every new address is a memory leak that an attacker controls. The sweep has an exact rule: a bucket that has gone `refill` without a request is full again, and a full bucket is the same as a new one. Deleting it changes nothing for the client. `MaxBuckets` caps the map at 100,000 buckets, which took 18 MB in a test on the machine that built this page. Past that, a new client gets 429 until some bucket has gone a full refill without a request. A flood from many addresses that keeps every bucket busy keeps new clients out for as long as it lasts, while clients that already have a bucket keep it.

Logins get two buckets of their own, and the second one closes the gap from Week 11:

- The per-email limit of Week 11 stops guesses at one account.
- The per-client login bucket stops one address from guessing at many accounts: five at once, then one every 12 seconds.

The shared cap has a price. ### Step 11: Send an Encrypted Backup Off the Box

Start with the key, on your laptop. `mkdir -p ~/.config/your-monitor && age-keygen -o ~/.config/your-monitor/backup.key` writes a private key to a file that only you can read, and prints its public key. Put the public key, the line that starts with `age1`, into `AGE_RECIPIENT` in the kustomization of Step 9. The private key never goes to the VPS or into Git. Keep a copy in your password manager and one offline, on a USB stick in a drawer: without the key, every backup is noise.

Next, a bucket, `your-monitor-backups`, at a provider with an S3-compatible API. Backblaze B2 is a cheap one, and AWS S3 itself works too. It needs two keys: an upload key for the cluster, and a read key for your laptop, which lists and reads. No provider offers an upload key that can only add, and the bucket rules cover what each key can do beyond that:

- **Backblaze B2.** The `writeFiles` capability also hides files, and a delete through the S3 API hides the newest version of a file. The lifecycle rule below hides each file 30 days after its upload and keeps hidden versions for 30 more days (`daysFromHidingToDeleting`): an attacker who hides your backups leaves you a month to unhide them.
- **AWS S3.** A policy that allows only `s3:PutObject` on the objects cannot delete, but it can upload over an existing name. Turn on versioning, which keeps the old version, and add a lifecycle rule that expires objects after 30 days, with a `NoncurrentVersionExpiration` of 30 days for the old versions that expiry and overwrites leave behind.
- **Both.** Any upload key can add a newer `.dump.age` and `.counts` pair of its own, encrypted to your public key, which is no secret. The drill takes the newest pair, and a planted one restores without error. Read the drill counts before a real restore, and restore an older backup by name when they do not look like your data.

Object Lock, which both providers offer, is the stronger option: no key can delete or overwrite a locked object until its retention period ends. With the `b2` command-line tool, the bucket and the two keys are:

```sh
b2 bucket create --lifecycle-rule '{"fileNamePrefix": "", "daysFromUploadingToHiding": 30, "daysFromHidingToDeleting": 30}' your-monitor-backups allPrivate
b2 key create --bucket your-monitor-backups backup-upload writeFiles
b2 key create --bucket your-monitor-backups backup-read listBuckets,listFiles,readFiles
```

On AWS, the IAM user of the upload key gets this policy, and the one of the read key gets `s3:ListBucket` on the bucket and `s3:GetObject` on `arn:aws:s3:::your-monitor-backups/*`:

```json
{"Version": "2012-10-17", "Statement": [{"Effect": "Allow", "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::your-monitor-backups/*"}]}
```

rclone, the tool that copies files to object storage, reads a remote named `offsite` from variables named `RCLONE_CONFIG_OFFSITE_*`. Put the upload key into a Secret:

```sh
cat > offsite.env <<'EOF'
RCLONE_CONFIG_OFFSITE_TYPE=s3
RCLONE_CONFIG_OFFSITE_PROVIDER=Other
RCLONE_CONFIG_OFFSITE_ENDPOINT=https://s3.us-west-004.backblazeb2.com
RCLONE_CONFIG_OFFSITE_ACCESS_KEY_ID=<upload key ID>
RCLONE_CONFIG_OFFSITE_SECRET_ACCESS_KEY=<upload key secret>
EOF
kubectl create secret generic offsite --from-env-file=offsite.env && rm offsite.env
```

The endpoint comes from your provider. For AWS S3, write `PROVIDER=AWS` and a line `RCLONE_CONFIG_OFFSITE_REGION=<region>` in place of the endpoint. The backup runs in an image of its own, the `backup` target of the Dockerfile:

### Step 12: Drill the Restore on Your Laptop

The drill needs the private key, which lives on your laptop, and runs there, in the same image. Write `~/.config/your-monitor/offsite-read.env` with the five lines of `offsite.env` and the read key in place of the upload key, add `BACKUP_REMOTE=offsite:your-monitor-backups` and `RCLONE_CONFIG=/dev/null`, and `chmod 600` it. Then build the image and run the drill:

```sh
docker build --target backup -t your-monitor-backup .
live=$(kubectl exec statefulset/postgres -- psql -U monitor -d monitor -Atc 'select count(*) from monitors')
docker run --rm -i --env-file ~/.config/your-monitor/offsite-read.env -e AGE_IDENTITY=- -e LIVE_MONITORS="$live" \
  your-monitor-backup restore-drill.sh < ~/.config/your-monitor/backup.key
```

`LIVE_MONITORS` passes the monitor count of the live database, and the drill requires it: unset, empty or not a number, it fails at once with `LIVE_MONITORS must be the monitor count of the live database`. An empty `$live` is what a failed `kubectl exec` leaves behind, and without the check a backup of an empty database passes. `AGE_IDENTITY=-` makes `age` read the key from standard input, which `-i` connects to the file: the key never lands on a disk inside the container.

<CodeFrom file="go/week17/your-monitor/deploy/backup/restore-drill.sh" region="drill-script" lang="sh" title="deploy/backup/restore-drill.sh" />

A new server, rather than a new database on the live one, proves more: the dump restores with no roles, no extensions and no settings from production. `MAX_AGE_HOURS` of 26 turns a backup CronJob that silently stopped into a failed drill. The counts of the `.counts` file catch a dump that restores only in part. They cannot catch a backup of the wrong database, whose dump and counts agree with each other; `LIVE_MONITORS` does: a restore with no monitors fails while the live database has some. A backup dated more than 5 minutes in the future fails too; the 5 minutes allow for skew between the clocks of the server and the laptop. ## Observe It

<ObserveIt>

**The autoscalers.** Watch them update every 15 seconds:

```txt
$ kubectl get hpa --watch
NAME     REFERENCE           TARGETS       MINPODS   MAXPODS   REPLICAS   AGE
api      Deployment/api      cpu: 4%/70%   2         4         2          3m
worker   Deployment/worker   cpu: 9%/70%   1         3         1          3m
```

`cpu: <unknown>/70%` means the HPA has no number: metrics-server is not running, which `kubectl top pods` confirms with an error, or the container has no CPU request. `kubectl describe hpa api` lists each scaling decision with its reason under **Events**.

**The worker queue.** CPU does not see the queue; the scheduler metrics from Week 13 do. Run `kubectl port-forward deploy/scheduler 2112:2112` and read `monitor_jobs_oldest_seconds` from `localhost:2112/metrics`. An age that climbs while the worker HPA sits at one replica means CPU is the wrong signal for your sites, and the queue age is the number to scale on.

**Rollouts.** `kubectl rollout status deployment/api` follows one rollout to its end, one line per step, and ends with `deployment "api" successfully rolled out`, or with an error after `progressDeadlineSeconds`.

**Limits.** Each refused request counts in `http_requests_limited_total`, under the limit it hit: `client` for a busy visitor, `login` for guesses from one address, `login_all` for guesses from many. A steady rise of `login_all` is an attack on your login, not a busy visitor. Traefik refusals never reach the api; they show as `429` in the Traefik access log once you add `logs.access.enabled: true` to the values in the same `HelmChartConfig`.

**Backups.** `kubectl get cronjob pg-backup` shows `LAST SCHEDULE`, and `kubectl get jobs` lists the recent runs with their completions. `kubectl logs job/<name>` prints the line of `backup.sh`, or a `FAILED` line that names the step that broke. The bucket gets a `.dump.age` and a `.counts` object each night. <a href={weekHref(18)}>Week 18</a> turns a missed backup into an alert.

</ObserveIt>

When `ab` ends, the count stays at four for the five-minute window, then drops. Delete the pod with `kubectl delete pod load`.

**Roll it back.** The drill change is revision 2 of the api:

```txt
$ kubectl rollout history deployment/api
deployment.apps/api
REVISION  CHANGE-CAUSE
1         <none>
2         load drill: RATE_LIMIT=0
```

`kubectl rollout undo deployment/api` starts a rolling update to the template of revision 1, and the history lists it again as revision 3. `kubectl set env deployment/api --list` shows `RATE_LIMIT=10` again.

**A bad image.** `deploy.yml` sets the image of all five Deployments and the CronJob, and a SHA that CI never built breaks all of them at once. The api, the worker and web roll: each new pod stays in `ImagePullBackOff`, and with `maxUnavailable: 0`, the old pods keep serving. The scheduler and the alerter use `Recreate`: their old pods stop first, the new ones never start, and from that moment no checks get queued and no alerts go out. Do not wait for `progressDeadlineSeconds`. Run `deploy.yml` again at once with the last good SHA, which the run summary of Week 14 lists. When the workflow itself is the problem, undo all five by hand with `for d in api worker scheduler alerter web; do kubectl rollout undo deployment/$d; done`, then fix the workflow: `undo` leaves the CronJob on the bad image.

**Everyone shares one bucket.** Visitors get 429 after a handful of requests, and `kubectl logs deploy/api | grep '"client"'` shows the same `10.42.x.x` address on every line. The client address dies at the node: `externalTrafficPolicy` is still `Cluster`, or the `HelmChartConfig` landed in the wrong folder. When `externalTrafficPolicy` reads `Local`, compare `TRUSTED_PROXIES` with the pod network of your node.

**Back up now, then drill.** Right after the first deploy, the bucket is empty, and the drill fails with `no dump`. Start a backup from the CronJob and follow its log:

```sh
kubectl create job --from=cronjob/pg-backup backup-now
kubectl logs -f job/backup-now --pod-running-timeout=2m
```

The log ends with the `backup:` line. Then run the drill of Step 12. Each failure names its cause; the table below lists them.

**Restore production.** When the live database is lost or holds bad data, restore the newest backup into the StatefulSet. Stop every writer first, and the backup, which keeps a half-restored database out of the bucket. Then fetch and decrypt the backup on your laptop, where the key is, stream it into the server, and start everything again. Take the name of the backup from the drill output. The HPA leaves a Deployment at zero replicas alone until you scale it back:

```sh
kubectl patch cronjob pg-backup -p '{"spec":{"suspend":true}}'
kubectl scale deployment/api deployment/worker deployment/scheduler deployment/alerter --replicas=0
docker run --rm -i --env-file ~/.config/your-monitor/offsite-read.env your-monitor-backup \
  sh -c 'rclone copyto "$BACKUP_REMOTE/$1" /tmp/b.age && age --decrypt --identity=- /tmp/b.age' sh monitor-20261011-031702.dump.age \
  < ~/.config/your-monitor/backup.key \
  | kubectl exec -i statefulset/postgres -- pg_restore -U monitor -d monitor --clean --if-exists --no-owner --single-transaction --exit-on-error
kubectl scale deployment/api --replicas=2
kubectl scale deployment/worker deployment/scheduler deployment/alerter --replicas=1
kubectl patch cronjob pg-backup -p '{"spec":{"suspend":false}}'
```

`--single-transaction` rolls the whole restore back when the stream breaks halfway, and `--clean --if-exists` drops each object of the dump before it creates it again. Your RTO is the restore time of the drill plus the minutes these steps take around it.

| What you see | What it points to |
| --- | --- |
| `cpu: <unknown>/70%` in `kubectl get hpa` | No metrics-server, or no CPU request on the container |
| New pods in `ImagePullBackOff`, rollout fails at 180 s | The image tag does not exist: rerun `deploy.yml` with the last good SHA |
| No new checks and no alerts after a failed deploy | The scheduler and the alerter use `Recreate`: their old pods are gone |
| `502` answers during every rollout | No preStop pause on web or api: requests reach pods after `SIGTERM` |
| Visitors get 429 together, one `client` address in the log | `externalTrafficPolicy` is `Cluster`: the node hides the client |
| The backup log ends with `rclone could not upload` | The `offsite` Secret: a wrong endpoint, or a key without the right to add objects |
| The drill fails with `no dump` or `hours old` | No backup reached the bucket lately: the log of the last backup job says why |
| The drill fails with `age could not decrypt` | The object is cut short, or `AGE_RECIPIENT` is not your public key |
| The drill fails with `no monitors` or `counts differ` | A backup of the wrong database, or a dump that restores only in part |
| The drill fails with `minutes in the future` | An upload that is not yours, or a wrong clock: restore an older backup by name |

## Side Lab

<SideLab title="Time a restore of one million rows and find where the time goes">

The drill restores a small database in a second. Build a bigger one on your laptop to see which part of a restore grows. Use the Postgres of Compose from <a href={weekHref(8)}>Week 8</a>, with `PGHOST`, `PGUSER` and `PGPASSWORD` set to reach it, and the Postgres 17 tools.

**1. Make a million results.** Create a database `sidelab` and restore one of your backups into it, decrypted with `age --decrypt --identity ~/.config/your-monitor/backup.key`. Then add rows in `psql`:

```sql
insert into check_results (monitor_id, checked_at, up, status_code, total_ms)
select 1 + (g % 3), now() - g * interval '10 seconds', g % 50 <> 0, 200, g % 300
from generate_series(1, 1000000) g;
```

On the machine that built this page, the insert took 14 seconds, the database grew to 132 MB, and `pg_dump --format=custom --file=side.dump` wrote 7.9 MB in 1.5 seconds. The dump holds rows, not indexes, and compresses well.

**2. Restore in three sections.** `pg_restore --section` runs one part of a dump at a time: `pre-data` creates the tables, `data` copies the rows, `post-data` builds the indexes and constraints. Time each one into an empty database `side_r` with `time pg_restore -d side_r --no-owner --exit-on-error --section=<section> side.dump`. One run on the same machine took 0.36 seconds for `pre-data`, 3.5 for `data` and 2.7 for `post-data`: Postgres rebuilds every index of `check_results` from scratch.

**3. Add jobs.** Recreate `side_r` and run the full restore with `--jobs=1`, then with `--jobs=4`. The same machine took about 4.3 and 3.7 seconds. `--jobs` runs whole tables and whole indexes in parallel, never parts of one: with one big table, only the index builds overlap.

**4. Predict.** Your live `check_results` grows by one row per monitor per interval. Compute its row count a year from now, scale the times from step 2, and decide whether a restore that long fits the RTO you accept for a status page.

</SideLab>
