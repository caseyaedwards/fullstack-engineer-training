At the end of <a href={weekHref(15)}>Week 15</a>, the whole monitor runs in a kind cluster on your laptop, and the `deploy.yml` workflow from <a href={weekHref(14)}>Week 14</a> waits for a cluster to deploy to. This week, you rent one small server, run Kubernetes on it, point a domain name at it, get a trusted certificate, and press **Run workflow**. At the end, anyone can open `https://status.example.com`, with your own domain in place of `example.com`. Everything on this box faces the internet. Most of the week goes into doors: which ones open, who holds the keys, and how you prove that the rest stay shut.

## Goals

- Choose a VPS by what the setup needs, and harden it: a user of your own, SSH keys only, a firewall.
- Install K3s and explain what its bundled Traefik and ServiceLB do with a request.
- Point a DNS A record at the box and get a Let's Encrypt certificate through cert-manager, staging first.
- Give CI a ServiceAccount that can deploy into one namespace and nothing more, reach the API server through an SSH tunnel, and read what each layer reports when it fails.

## Concepts

### One Box Running Kubernetes

A **VPS**, short for virtual private server, is a virtual machine that a hosting company runs for you in its data center. You get root access, a public IP address and a monthly bill. This course uses one VPS for Weeks 16 to 18, at about $10 to $25 a month. Any provider works when its plan meets three conditions. DigitalOcean, Hetzner Cloud and Linode are three that sell such a plan: compare their prices yourself, because they change.

- **A public IPv4 address**: the DNS A record for your status page points at it, and Let's Encrypt connects to it.
- **4 GB of RAM and 2 virtual CPUs**: the K3s documentation names 2 cores and 2 GB as the minimum for a server node, and your programs, Postgres and cert-manager run on top. The Week 15 limits alone add up to about 2 GB, and the autoscaling of <a href={weekHref(17)}>Week 17</a> needs room.
- **An Ubuntu LTS image**, 24.04 or newer: the commands on this page use Ubuntu tools, such as `ufw` and `adduser`.

**K3s** is a Kubernetes distribution packed into one binary. It runs the control plane, the node agent and a container runtime as one service, and keeps the cluster state in an SQLite file instead of etcd. It also installs components that a bare cluster lacks:

- **Traefik**, an **ingress controller**: a reverse proxy that reads Ingress objects and routes HTTP requests by host name and path to Services. An **Ingress** is the Kubernetes object that says which host and path go to which Service.
- **ServiceLB**, a load balancer for Services of type `LoadBalancer`. On a cloud, such a Service gets a load balancer from the provider. ServiceLB instead runs a small pod on each node that holds the Service ports, here `80` and `443`, on the node itself and forwards the traffic to the Service. The <a href={trackHref('load-balancing')}>Load Balancing track</a> compares it with the load balancers that cloud providers sell.
- CoreDNS, a storage provisioner that keeps volumes on the node disk, and metrics-server.

### A Certificate from Let's Encrypt

Week 4 showed that a browser trusts a certificate signed by a certificate authority it knows. **Let's Encrypt** is a free, automated certificate authority. Clients talk to it through **ACME**, the Automatic Certificate Management Environment protocol: they ask for a certificate, prove control of each name in it, and receive the signed certificate. **cert-manager** is the ACME client that runs inside your cluster. It watches Ingress objects, asks for the certificates they name, and renews them.

With the **HTTP-01 challenge**, you prove control of a name by serving a token over plain HTTP on port `80` of that name:

Two consequences follow from the diagram. Port `80` stays open for good, because every renewal repeats the challenge. And the DNS record has to point at the box before you ask for a certificate. Let's Encrypt certificates last 90 days, 64 days from February 10, 2027 (staging switches on October 14, 2026), and 45 days from 2028. cert-manager renews two thirds of the way through the life, which leaves a month to notice a failure today, and about 21 days with 64-day certificates. Let's Encrypt stopped sending expiry emails in 2025: the [Observe It](#observe-it) box shows how you notice instead.

**Rate limits** protect Let's Encrypt from broken clients. These three bite first when you experiment:

- 5 certificates for the exact same set of names every 7 days, with no override.
- 5 failed validations for one name per account every hour.
- 50 certificates per registered domain, such as `example.com`, every 7 days.

A typo in the Ingress, a closed port `80` or a missing DNS record each burn one failed validation per attempt, and cert-manager retries on its own. For that reason, Let's Encrypt runs a second, **staging** environment with much higher limits. Its certificates come from a test certificate authority that no browser trusts, and every name in that hierarchy starts with `(STAGING)`. You get everything working against staging, then switch one annotation to production and spend one real certificate. Every certificate Let's Encrypt issues lands in public **Certificate Transparency** logs, which anyone can search at `crt.sh`. Treat every name you put in a certificate as public. The <a href={trackHref('tls-pki')}>TLS and PKI track</a> covers the chain of trust in depth.

### Who Can Reach What

The box has three kinds of door. Ports `80` and `443` serve the status page to everyone. Port `22` serves SSH, and only a key opens it. Port `6443`, where the Kubernetes API server listens, stays closed to the internet: anyone who reaches it can try stolen tokens and exploits against the program that controls the whole cluster. `deploy.yml` still needs the API server. It reaches it through SSH: the job opens an **SSH tunnel**, a forwarded port that carries TCP traffic inside the encrypted SSH connection. Port `6443` on the runner then leads to `127.0.0.1:6443` on the VPS.

Behind the door, Kubernetes RBAC, role-based access control, decides what the caller can do. A **ServiceAccount** is an identity for a program, here CI. A **Role** lists allowed verbs, such as `get` and `patch`, on resources, such as `deployments`, in one namespace. A **RoleBinding** grants a Role to an identity. A ClusterRole and a ClusterRoleBinding do the same across every namespace. CI gets neither. The <a href={trackHref('iam')}>IAM track</a> compares this model with the roles of cloud providers.

## Build

Steps 1 to 5 build the box. Steps 6 to 9 make the name and the certificate. Steps 10 to 12 wire up `deploy.yml`. Each block that runs on the VPS starts with a comment such as `# ada@monitor:`. Use your own user name where the page says `ada`, your domain for `example.com`, and your VPS address for `203.0.113.10`. Every output from the VPS on this page is an example. The manifests come from the example code that this site tests, at `examples/go/week16/your-monitor/`, laid out as your repository. Three folders are new: `deploy/vps/` holds the configuration files for the VPS itself, `deploy/k8s/cluster/` the setup you apply once as administrator, and `deploy/k8s/overlays/prod/` what `deploy.yml` applies. `.github/workflows/deploy.yml` gains one step.

### Step 1: Rent the VPS

Create an SSH key on your laptop with `ssh-keygen -t ed25519` if you have none yet, and print its public half with `cat ~/.ssh/id_ed25519.pub`. In the provider console, create a server with the newest Ubuntu LTS image, a plan with 4 GB of RAM, and the region closest to you. Paste the public key into the SSH key field, and note the IPv4 address the server gets. Then create a cloud firewall in the console that allows inbound TCP `22`, `80` and `443`, and attach it. Take this step even though ufw follows in Step 3: it filters traffic before it reaches the VPS, including ports that Kubernetes opens past ufw, as Step 8 and the [Side Lab](#side-lab) show.

### Step 2: Make a User and Turn Off Passwords

Log in as `root` and make your own user with `sudo` rights. On images that log you in as `ubuntu` instead, run `sudo -i` first, and copy `/home/ubuntu/.ssh/authorized_keys` in the last `install` line. `adduser` asks for a password: `sudo` asks for it later, SSH never does. When the upgrade installs a new kernel, the last line reboots the box: log in as root again after a minute.

```sh
ssh root@203.0.113.10
# root@monitor:
adduser ada
usermod -aG sudo ada
install -d -m 700 -o ada -g ada /home/ada/.ssh
install -m 600 -o ada -g ada /root/.ssh/authorized_keys /home/ada/.ssh/authorized_keys
apt update && apt full-upgrade -y
[ -f /var/run/reboot-required ] && reboot
```

The SSH server, `sshd`, reads every file in `/etc/ssh/sshd_config.d/` in name order, and for each setting the first value it reads wins. Cloud images can ship a `50-cloud-init.conf` with `PasswordAuthentication yes`. A file whose name starts with `00` comes first and overrides it:

<CodeFrom file="go/week16/your-monitor/deploy/vps/sshd/00-hardening.conf" region="hardening" lang="txt" title="deploy/vps/sshd/00-hardening.conf" />

From a second terminal on your laptop, copy it over as `ada`, install it, check the syntax, restart the SSH service, and print the settings sshd now applies. Keep the root session open until this works: a mistake here locks you out, and the provider web console is the only way back in.

```sh
scp deploy/vps/sshd/00-hardening.conf ada@203.0.113.10:
ssh -t ada@203.0.113.10 'sudo install -m 644 00-hardening.conf /etc/ssh/sshd_config.d/ &&
  sudo sshd -t && sudo systemctl restart ssh && sudo sshd -T' | grep -E '^(passwordauthentication|kbdinteractiveauthentication|permitrootlogin) '
```

```txt
permitrootlogin no
passwordauthentication no
kbdinteractiveauthentication no
```

Your `ada` login works, and `ssh root@203.0.113.10` now answers `Permission denied (publickey)`. Work as `ada` from now on. Ubuntu installs security updates every day through the `unattended-upgrades` package, which the image enables.

### Step 3: Close Every Port but Three

`ufw`, the uncomplicated firewall, writes the packet filter rules of the Linux kernel for you. The script denies everything that comes in, then allows the three public ports. The K3s documentation lists three more rules for Ubuntu. Two stay: pods, in `10.42.0.0/16`, and Services, in `10.43.0.0/16`, reach programs on the node, such as the API server, and ufw sees that traffic as incoming. The third, `allow 6443/tcp`, serves agent nodes and remote `kubectl`: this box has no agents, and your `kubectl` comes through SSH.

<CodeFrom file="go/week16/your-monitor/deploy/vps/firewall.sh" region="firewall" lang="sh" title="deploy/vps/firewall.sh" />

`ufw enable` on its own asks whether to go ahead, because it can cut SSH connections. The rule for `22` comes first, and `--force` answers yes. Copy the script and run it: the status at the end lists the five rules, plus IPv6 copies of the first three. ServiceLB traffic to `80` and `443` reaches Traefik before ufw's rules run: those two rules are a backstop. For ports that Kubernetes opens, the provider firewall is the filter that counts.

```sh
scp deploy/vps/firewall.sh ada@203.0.113.10:
ssh -t ada@203.0.113.10 sudo sh firewall.sh
```

### Step 4: Install K3s

K3s reads `/etc/rancher/k3s/config.yaml` at start. Its one setting keeps your database password out of a plain-text copy of the SQLite file. It goes in before the install: no Secret is ever stored unencrypted, and no restart is needed.

<CodeFrom file="go/week16/your-monitor/deploy/vps/k3s/config.yaml" region="k3s-config" lang="yaml" title="deploy/vps/k3s/config.yaml" />

Copy it to your home folder on the VPS with `scp deploy/vps/k3s/config.yaml ada@203.0.113.10:`, then log in. Read the install script before you run it: it installs a system service as root, and calls `sudo` itself where it needs to. `INSTALL_K3S_CHANNEL=v1.36` picks the newest K3s release for Kubernetes 1.36, the minor version your kind cluster runs.

```sh
# ada@monitor:
sudo install -D -m 600 config.yaml /etc/rancher/k3s/config.yaml
curl -sfL https://get.k3s.io -o k3s-install.sh
less k3s-install.sh
INSTALL_K3S_CHANNEL=v1.36 sh k3s-install.sh
sudo k3s kubectl get nodes
sudo k3s secrets-encrypt status
sudo k3s kubectl -n kube-system get pods,svc
```

The node shows `Ready`, with a VERSION that starts with `v1.36`. `secrets-encrypt status` reports encryption as enabled. In `kube-system`, the `traefik` Service has type `LoadBalancer` with ports `80` and `443`, and a pod whose name starts with `svclb-traefik` is the ServiceLB pod that holds those ports.

### Step 5: Reach the Cluster from Your Laptop

K3s writes an administrator kubeconfig to `/etc/rancher/k3s/k3s.yaml`, readable by root only. Its server is `https://127.0.0.1:6443`, which works on the VPS itself. From your laptop, copy it out through your home folder on the VPS. `-t` gives `sudo` a terminal to ask for your password. The file holds a client certificate with full control of the cluster: keep it on your laptop only.

```sh
ssh -t ada@203.0.113.10 'sudo install -m 600 -o ada -g ada /etc/rancher/k3s/k3s.yaml ~/k3s.yaml'
scp ada@203.0.113.10:k3s.yaml ~/.kube/vps.yaml && ssh ada@203.0.113.10 rm k3s.yaml
chmod 600 ~/.kube/vps.yaml
```

Open the tunnel in its own terminal and leave it running. `-N` runs no remote command, and `-L` forwards local port `6443` to `127.0.0.1:6443` as the VPS sees it. The API server certificate names `127.0.0.1`, which keeps TLS verification working through the tunnel.

```sh
ssh -N -L 6443:127.0.0.1:6443 ada@203.0.113.10
```

In another terminal, point `kubectl` at the new file. A separate file keeps the VPS apart from your kind contexts in `~/.kube/config`:

```sh
export KUBECONFIG=~/.kube/vps.yaml
kubectl get nodes
curl -sS -k -m 5 https://203.0.113.10:6443/version
```

`kubectl` lists the node. `curl` straight at the public address waits the full five seconds and fails with error `(28)`, a timeout: ufw drops the packets without a reply. Every `kubectl` command from here on assumes the tunnel and this `KUBECONFIG`.

### Step 6: Point the Name at the Box

At your DNS provider, the company that serves the records for your domain, create an **A record**: name `status`, value `203.0.113.10`, TTL `300` seconds. With a short TTL, a move to a new box reaches every resolver within five minutes. Do not create an AAAA record: when a name has one, Let's Encrypt connects over IPv6 first, and this cluster serves IPv4 only. The <a href={trackHref('dns')}>DNS track</a> explains TTLs and record types. Check the answer from a public resolver, as in the Week 4 side lab: `dig +short status.example.com @1.1.1.1` prints `203.0.113.10` once the record is live.

### Step 7: Add Automatic Certificates

cert-manager installs from one manifest per release. Read the newest release name from GitHub, and check that the cert-manager [supported releases page](https://cert-manager.io/docs/releases/) lists Kubernetes 1.36 for it:

```sh
CM_VERSION=$(curl -fsSL https://api.github.com/repos/cert-manager/cert-manager/releases/latest | grep -m1 '"tag_name"' | cut -d '"' -f 4)
echo "$CM_VERSION"
kubectl apply -f "https://github.com/cert-manager/cert-manager/releases/download/$CM_VERSION/cert-manager.yaml"
kubectl -n cert-manager wait --for=condition=Available deployment --all --timeout=3m
```

The manifest creates the `cert-manager` namespace, the resource types `Certificate`, `ClusterIssuer` and four more, and three Deployments: `cert-manager`, `cert-manager-cainjector` and `cert-manager-webhook`.

### Step 9: Create the Two Secrets by Hand

Two Secrets stay out of Git, and CI cannot read them through the API. The first is the Secret `postgres` that your Week 15 base reads, with the key `POSTGRES_PASSWORD`; on kind, the overlay generated it from `postgres.env`. The user and database names come from the ConfigMap `monitor-config` in the base. Use letters and digits only, because the password goes into `DATABASE_URL`:

```sh
kubectl -n your-monitor create secret generic postgres \
  --from-literal=POSTGRES_PASSWORD="$(openssl rand -hex 24)"
```

The second gives the node access to your images. CI pushed them to GHCR in Week 14, and GHCR packages start out private. GHCR accepts only a classic personal access token: create one in your GitHub settings under **Developer settings**, **Personal access tokens**, **Tokens (classic)**, with the single scope `read:packages` and an expiry date. `read -rs` reads the token without showing it and without writing it to your shell history:

```sh
read -rs GHCR_TOKEN
kubectl -n your-monitor create secret docker-registry ghcr-pull \
  --docker-server=ghcr.io --docker-username=<your GitHub user name> --docker-password="$GHCR_TOKEN"
unset GHCR_TOKEN
```

First compare the fingerprint `ssh` showed on your first login with the one `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` prints on the VPS: a match proves that the line came from your box.

```sh
umask 077
ssh-keygen -t ed25519 -N '' -C deploy.yml -f deploy_key
scp deploy_key.pub ada@203.0.113.10:
```

## Operate It

<OperateIt>

**The certificate stays not ready.** cert-manager records each attempt as an Order and a Challenge. Start at the Challenge with `kubectl -n your-monitor describe challenge`: the `Reason` line names the failure. A self-check that times out means port `80` does not reach Traefik: the DNS record points elsewhere or does not exist yet, or a provider firewall blocks `80`. A response with the wrong body means another server answers for the name, at an old AAAA record for example. A message with `rateLimited` means the account hit a limit: wait out the time it names, and fix the cause on staging first.

**Pods stay in ImagePullBackOff.** `kubectl -n your-monitor describe pod -l app.kubernetes.io/name=api` shows the pull error. `401 Unauthorized` or `403 Forbidden` from `ghcr.io` means the `ghcr-pull` Secret is missing, or its token expired or lacks `read:packages`. `not found` means CI never pushed that SHA: deploy a commit whose CI run finished.

**The deploy fails at the tunnel step.** Each message points at one secret or one service:

| What the step prints | What it points to |
| --- | --- |
| `Host key verification failed.` | The VPS host key changed: you rebuilt the box, or someone sits in between. Check the fingerprint on the VPS before you update `DEPLOY_KNOWN_HOSTS` |
| `Permission denied (publickey)` | `DEPLOY_SSH_KEY` does not match `/home/tunnel/.ssh/authorized_keys`, or `10-tunnel.conf` names another user |
| A timeout on port `22` | `DEPLOY_HOST` holds an old address, or a firewall blocks `22` |
| `Unable to connect to the server` with `EOF` or `connection reset by peer` | The tunnel opened, but the forward fails on the VPS. Open the tunnel from your laptop without `-f`, as in Step 5, and read what `ssh` prints: `connect failed: Connection refused` means K3s is down (`sudo systemctl status k3s`), `administratively prohibited` means `PermitOpen` names another address |
| `You must be logged in to the server (Unauthorized)` | The token expired: run the token commands of Step 11 again and replace `KUBECONFIG` |
| `no` from `kubectl auth can-i` | The Role lost the `patch` verb on Deployments |

**The apply step says forbidden.** CI tried to write a kind its Role does not grant. `kubectl apply` first reads the object, and the message names that verb and the resource, as in this one for a Secret:

```txt
Error from server (Forbidden): error when retrieving current configuration of:
Resource: "/v1, Resource=secrets", GroupVersionKind: "/v1, Kind=Secret"
Name: "extra", Namespace: "your-monitor"
from server for: "secret.yaml": secrets "extra" is forbidden: User "system:serviceaccount:your-monitor:deployer" cannot get resource "secrets" in API group "" in the namespace "your-monitor"
```

Grant the new resource in `ci-deployer.yaml`, and apply the cluster setup yourself, from your laptop. CI cannot see pods or their logs either: debug a failed rollout with your administrator kubeconfig.

**Someone steals the CI credentials.** The thief can run any image in `your-monitor`, and through it read its Secrets, but cannot leave the namespace or reach the node. A Deployment `rootfs` that mounts the node disk is accepted, with a warning that names the same rule as below, and its pods never start. With your administrator kubeconfig, `kubectl -n your-monitor describe replicaset -l app=rootfs` shows the refusal in its events, for example:

```txt
  Warning  FailedCreate  2s    replicaset-controller  Error creating: pods "rootfs-5f4f7f46d9-blt7q" is forbidden: violates PodSecurity "restricted:v1.36": restricted volume types (volume "host" uses restricted volume type "hostPath")
```

Revoke the token by deleting the `deployer` ServiceAccount, which invalidates every token issued for it, then apply the cluster setup again and issue a new one. Replace the `tunnel` key in `authorized_keys`. The deployer cannot delete, and what the thief created keeps running: with your administrator kubeconfig, list `kubectl -n your-monitor get deploy,sts,svc,ingress,cm,middlewares`, compare it with `kubectl kustomize deploy/k8s/overlays/prod`, and delete everything else, except `kube-root-ca.crt` and older `monitor-config-` ConfigMaps. Then deploy a commit you trust. Treat both Secrets as read: set a new database password in Postgres and in the `postgres` Secret, and revoke the GHCR token on GitHub and create a new `ghcr-pull`.

**You locked yourself out of SSH.** Open the web console of your provider, log in there, fix the file in `/etc/ssh/sshd_config.d/`, and run `sudo sshd -t` before the restart.

</OperateIt>

## Side Lab

<SideLab title="Scan your own box from outside with nmap and explain every open port">

`nmap` is a port scanner: it sends packets to a range of ports and reports how each one answers. Install it with `brew install nmap` on macOS or `sudo apt install nmap` on Ubuntu. Scan only machines you own.

**1. Scan the doors you know.** From your laptop, not from the VPS:

```sh
nmap -Pn -p 22,80,443,6443,10250 203.0.113.10
```

`-Pn` skips the host discovery that `nmap` runs first and scans the ports straight away. Expect `open` for `22`, `80` and `443`, and `filtered` for `6443` and for `10250`, the API of the node agent. **Filtered** means no answer at all: ufw drops the packets. **Closed** means the machine answers with a reset because nothing listens, as in the Week 4 connection-refused example.

**2. Scan the NodePort range.** A Service of type `LoadBalancer` also gets a **NodePort**: a port between `30000` and `32767` on every node that leads to the Service. Print the ones Traefik got, then scan the range:

```sh
kubectl -n kube-system get svc traefik
nmap -Pn -p 30000-32767 203.0.113.10
```

The `PORT(S)` column reads `80:` and `443:`, each followed by a NodePort. Without a provider firewall, `nmap` lists those two NodePorts as open, although ufw has no rule for them.

**3. Explain the gap.** ufw filters packets addressed to programs on the host, such as `sshd` and the API server. For a NodePort, and for the ports ServiceLB holds, Kubernetes rewrites the destination of each packet to a pod address before that filter runs, and forwards it through rules of its own: ufw never sees it. Here the leak does no harm, because both ports lead to the same Traefik as `80` and `443`. The admission policy of Step 8 keeps `your-monitor` from adding more, by type or by `externalIPs`. Try it: `kubectl -n your-monitor create service nodeport leak --tcp=5432:5432` gets refused with the message of the policy, as does `kubectl -n your-monitor patch service api -p '{"spec":{"externalIPs":["203.0.113.10"]}}'`. Attach the provider firewall if you skipped it in Step 1, and scan again: the two NodePorts turn `filtered`.

</SideLab>
