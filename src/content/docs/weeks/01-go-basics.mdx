## Concepts

### How Go Runs Your Code

TypeScript needs two programs before your code runs: `tsc` turns TypeScript into JavaScript, and Node.js runs the JavaScript. Go needs one step. The Go **compiler** turns your source code into a **binary**: a file of machine code that your operating system runs directly. The computer that runs the binary needs no Go installation and no runtime such as Node.js.

Go code lives in packages. A **package** is a folder of `.go` files that all start with the same `package` line. A package named `main` is special: it builds into a program, and the program starts at its `func main()`. Every other package is a library that programs import. Your folder of packages is a **module**, named by the first line of `go.mod`, the way `package.json` names a Node.js project. Week 0 created yours as `github.com/<user>/your-monitor`.

Go ships with a large **standard library**: packages such as `fmt` for printing, `os` for talking to the operating system, `flag` for command-line flags, `net/http` for HTTP and `time` for clocks and durations. You import them by path, and nothing needs installing. Every line of code this week uses only the standard library.

When a program ends, it hands the operating system a small number, its **exit code**. `0` means success. Anything else means failure, and the program picks the number. Your shell stores the exit code of the last command in `$?`. Scripts, CI jobs and Kubernetes exec probes read the exit code, not the text a program prints, to decide whether it worked. The convention for command-line tools: `1` for a failure, `2` for a usage mistake such as a missing argument.

### Variables and Types

Every Go variable has a type, fixed when you compile. There are two ways to declare one:

```go
var timeout time.Duration = 5 * time.Second // type written out
url := "https://example.com"                // type worked out: string
var status int                              // no value given: status is 0
```

`:=` declares a variable and gives it a value in one statement, like `let` in TypeScript with an inferred type. It works only inside functions. `var` works everywhere, and you can leave off the value.

A variable you declare without a value holds the **zero value** of its type: `0` for numbers, `""` for strings, `false` for booleans, and `nil`, meaning no value, for pointers, slices, maps and errors. Go has no `undefined`: a variable always holds a value of its type.

The types you meet this week:

| Go | Holds | Closest TypeScript |
| --- | --- | --- |
| `int` | a whole number | `number` |
| `string` | text | `string` |
| `bool` | `true` or `false` | `boolean` |
| `time.Duration` | a length of time, counted in nanoseconds | a `number` of milliseconds, by convention |
| `error` | what went wrong, or `nil` | an `Error` that you throw |

Go converts nothing on its own. Adding an `int` variable to a `time.Duration`, or assigning `"three"` to an `int`, stops the build. A number written straight into the code, such as the `5` in `5 * time.Second`, is the exception: it takes on the type it needs. With `var count int = "three"` on line 6, the error points at column 18, where `"three"` starts:

```txt
./main.go:6:18: cannot use "three" (untyped string constant) as int value in variable declaration
```

Go is also strict about clutter. A variable you declare and never use, or a package you import and never use, is a compile error, not a lint warning. Each time you save, the VS Code Go extension removes unused imports and formats your file with `gofmt`, the standard Go formatter.

One more rule replaces the TypeScript `export` keyword. A name that starts with a capital letter, such as `http.Get` or `resp.StatusCode`, is **exported**: other packages can use it. A name that starts with a lowercase letter, such as `checkURL`, is visible only inside its own package.

### Errors Are Values

In TypeScript, a failure throws an exception. The exception skips every function between the `throw` and the nearest `catch`, and nothing in a function signature tells you which calls throw.

Go has no exceptions for expected failures such as an unreachable site. A function that can fail returns an `error` as its last result. `nil` means it worked. Anything else is a value that describes what went wrong, and its `Error()` method returns the message. The caller checks it straight away:

```go
resp, err := client.Get(url)
if err != nil {
	return 0, latency, err // hand the error to the caller; resp is nil
}
```

Compare the TypeScript version with `fetch`:

```ts
try {
  const res = await fetch(url);
  console.log(res.status);
} catch (err) {
  console.error("check failed:", err);
}
```

The two draw the same line. `fetch` rejects only when no response arrives at all: a `500` response resolves, with `res.status` set to `500`. In Go, `client.Get` returns an error only when no response arrives: a `500` comes back as a response with `StatusCode` set to `500`. A server error is an answer, and your monitor reads it as a status. One more case returns an error: `client.Get` follows redirects on its own, and after 10 of them in a row it gives up with `stopped after 10 redirects`.

To add context as an error moves up, wrap it: `fmt.Errorf("check of %s: %w", url, err)` builds a new error whose message starts with your text and ends with the original message. The `%w` keeps the original error inside, where code higher up can still inspect it: `errors.Is(err, target)` reports whether a given error sits anywhere in the chain, and `errors.As` pulls out an error of a given type, such as a timeout. The loop in [Slices, Maps and Loops](#slices-maps-and-loops) wraps an error this way.

Go does have a crash for bugs: a **panic**. Reading past the end of a list or following a `nil` pointer panics. The program prints the problem and a stack trace, then exits with code `2`. Treat a panic as a bug to fix, never as a way to report a site that is down.

### Structs and Pointers

A **struct** groups named fields into one type, much like a TypeScript object type:

<CodeFrom file="go/week01/basics.go" region="result" lang="go" title="basics.go" />

`r := Result{URL: "https://example.com", Status: 200}` creates a `Result`, and `r.Status` reads its field. A struct has exactly the fields its type lists: there are no optional fields and no extra ones. A field you leave out of the literal holds its zero value.

A **pointer** holds the memory address of a value instead of the value itself. `&` takes the address, and a `*` in front of a type means a pointer to that type. The difference matters because Go copies a struct each time you assign it or pass it to a function. A pointer shares one value instead. `client := &http.Client{Timeout: 5 * time.Second}` creates one client, and passing `client` around hands out its address, the way a TypeScript object reference works. That is why `checkURL` takes a `*http.Client`.

Go reads fields through a pointer for you: with `resp` of type `*http.Response`, write `resp.StatusCode`. To read the value behind a pointer to a plain type, put `*` in front: the `flag` package hands you a `*string`, and `*url` is the string.

### Slices, Maps and Loops

A **slice** is a list of values of one type, written `[]Result` or `[]string`. It is the Go version of a TypeScript array. `len(s)` gives its length, `s[0]` its first element, and `s = append(s, r)` adds one element. Reading past the end panics. The arguments of your program arrive as a slice: `os.Args`, of type `[]string`.

A **map** stores values by key, like a TypeScript `Map` or `Record`. `map[string]int` maps strings to integers. Reading a missing key gives the zero value, not an error. To tell a missing key from a stored zero, ask for a second value: `n, ok := counts["down"]` sets `ok` to `false` when the key is missing.

Go has one loop keyword, `for`, in three forms:

```go
for i := 0; i < 3; i++ { }      // counting, as in TypeScript
for status == 0 { }             // while the condition holds
for i, arg := range os.Args { } // each index and element of a slice
```

### Printing Text

The `fmt` package prints text. `fmt.Println` prints its arguments with spaces between them and a newline at the end. `fmt.Printf` takes a format string with **verbs**, placeholders that start with `%`:

| Verb | Prints | Example output |
| --- | --- | --- |
| `%s` | a string | `https://example.com` |
| `%d` | a whole number | `200` |
| `%q` | a string in double quotes, with the quotes inside escaped | `"Get \"http://...\": ..."` |

A program has two output streams. **Standard output**, or stdout, carries the results: `fmt.Println` and `fmt.Printf` write there. **Standard error**, or stderr, carries messages about the program itself, such as usage mistakes: write there with `fmt.Fprintln(os.Stderr, ...)`. Your terminal shows both, but a shell redirect such as `> results.txt` captures only stdout. <a href={weekHref(3)}>Week 3</a> builds on this split when your monitor logs to stdout.

### HTTP Requests and Time

An `http.Client` sends HTTP requests. Its `Timeout` field sets the longest a request can take, from the moment you send it until the response body is read. The zero value means no limit at all. `http.Get`, the shortcut you find in most tutorials, uses `http.DefaultClient`, which has no timeout. A server that accepts the connection and never answers holds the request forever. Your monitor always makes its own client with a timeout.

`client.Get(url)` returns once the status line and headers arrive. The **response body**, the page content itself, streams in after that, through `resp.Body`. You must close the body when you are done with it, even when you never read it, because an open body holds the network connection open. `defer resp.Body.Close()` schedules the close to run when the surrounding function returns, whichever `return` it leaves through.

To time something, read the clock before and after. `time.Now()` returns the current time, and `time.Since(start)` returns a `time.Duration`: the time that has passed since `start`. **Latency** is that delay between asking and getting an answer.

### Step 5: Read Command-Line Flags and Report the Result

Add `main` below `checkURL`:

A **command-line flag** is a named argument such as `-url https://example.com`. In TypeScript, you read `process.argv` and install a package such as `commander` to parse it. Go has the `flag` package in its standard library:

- `flag.String("url", "", "...")` defines a `-url` command-line flag with an empty default and a help text. It returns a `*string`, a pointer that `flag.Parse` fills in. Read the value with `*url`.
- `flag.Duration` defines `-timeout`. It accepts values such as `500ms`, `2s` or `1m`, and turns them into a `time.Duration`.
- `flag.Parse()` reads `os.Args`. On an unknown or malformed command-line flag, it prints the problem and the usage text, then exits with `2`. On `-h`, it prints the usage text and exits with `0`.
- A missing `-url` is not a parse error, which is why `main` checks for an empty value and exits with `2` itself.
- `&http.Client{Timeout: *timeout}` creates the one client the program uses.
- Each outcome prints one line to stdout in `key=value` form: easy to read, and easy to search with `grep` once Week 3 runs the monitor for hours. `latency.Milliseconds()` turns the duration into a whole number of milliseconds. `%q` wraps the error message in quotes, which keeps it one value.
- `os.Exit(1)` ends the program with exit code `1` when no response arrives, or when the status code is `400` or above: a `4xx` code means the server rejects the request, as `404 Not Found` does, and a `5xx` code means the server failed. When `main` reaches its end and returns, the exit code is `0`.

## Observe It

<ObserveIt>

Your CLI already prints the number this week is about: `latency_ms`. One number on its own tells you little. Run the binary nine times in a row:

```sh
for i in 1 2 3 4 5 6 7 8 9; do ./your-monitor -url https://example.com; done
```

The nine `latency_ms` values differ. Each run is a new process that finds the server and connects to it from scratch, and the network delay changes from one run to the next. Write down three numbers: the lowest, the highest and the middle one, the fifth in sorted order, called the **median**. Describe latency as a spread like this, never as a single run. <a href={weekHref(4)}>Week 4</a> splits each check into its parts, to show which part varies.

Then compare what your program measures with what the whole command costs. The shell `time` command reports how long a command takes from start to finish. In bash, read the `real` line. In zsh, the default shell on macOS, read the number just before the word `total`:

```sh
time ./your-monitor -url https://example.com
time go run . -url https://example.com
```

`latency_ms` stays about the same in both. The total time does not. In a test run for this page, against a server on the same machine, the binary took 5 ms from start to finish, and `go run` took 122 ms, because it builds the program before it runs it. Your latency number covers the request alone: process start-up never leaks into it.

Last, try a URL that redirects: `./your-monitor -url http://github.com`. GitHub answers `http://` with a `301` redirect to `https://`. `http.Client` follows up to ten redirects on its own and reports the final status, `200`. The latency is higher than for `https://github.com`, because it covers both requests.

```txt
down url=http://127.0.0.1:8080 latency_ms=2001 error="Get \"http://127.0.0.1:8080\": context deadline exceeded (Client.Timeout exceeded while awaiting headers)"
$ echo $?
1
```

The latency equals the timeout, and the error says why: the headers never arrive. Back in the first terminal, `nc` shows the request that Go sends, which is plain text:

```txt
GET / HTTP/1.1
Host: 127.0.0.1:8080
User-Agent: Go-http-client/1.1
Accept-Encoding: gzip
```

Now see why the timeout matters. Start `nc -l 8080` again and run `./your-monitor -url http://127.0.0.1:8080 -timeout 0`. A zero `time.Duration` means no limit, the same as `http.DefaultClient`, and the check waits with no end. Press **Ctrl+C** to stop it. A monitor without a timeout reports nothing at all about the one site that hangs.

**A server that answers with an error.** Hand `nc` a canned response to send. The `\r\n` pairs end each line, as HTTP requires:

```sh
printf 'HTTP/1.1 500 Internal Server Error\r\nContent-Length: 0\r\n\r\n' | nc -l 8080
```

```txt
$ ./your-monitor -url http://127.0.0.1:8080
down url=http://127.0.0.1:8080 status=500 latency_ms=0
```

No error this time: the request works, and the server says it is broken. The exit code is `1` because the status is `400` or above.

**Nothing listening.** On a default macOS or Ubuntu install, no program listens on port `1`:

```txt
$ ./your-monitor -url http://127.0.0.1:1/
down url=http://127.0.0.1:1/ latency_ms=0 error="Get \"http://127.0.0.1:1/\": dial tcp 127.0.0.1:1: connect: connection refused"
```

The machine answers at once that nothing listens there, which is why the latency is `0`. Compare it with the `nc` case: a fast failure points to a refused connection, and a failure at exactly the timeout points to a server that does not answer.

**A URL without a scheme.** Leave off the `https://`:

```txt
$ ./your-monitor -url example.com
down url=example.com latency_ms=0 error="Get \"example.com\": unsupported protocol scheme \"\""
```

Go needs the scheme to pick a protocol, and the empty string between the escaped quotes is the scheme it finds.

| What you see | What it means | Exit code |
| --- | --- | --- |
| `up` and a status below `400` | The site answers | `0` |
| `down` and a status of `400` or above | The site answers with an error | `1` |
| `down`, an error, and `latency_ms` equal to the timeout | No answer arrives in time | `1` |
| `down`, `connection refused` and a small latency | The host is up, but nothing listens on that port | `1` |
| `missing -url` and the usage text | The command is wrong, not the site | `2` |

Scripts act on the exit code. In the shell, `||` runs the second command only when the first one fails: `./your-monitor -url https://example.com || echo "example.com is down"` prints the warning only for a site that is down.

One failure does not show up in a single run: a missing `resp.Body.Close()`. Each unclosed body holds a network connection open. In Week 3, your monitor checks URLs in a loop for days, and the open connections pile up until the process runs out of the files it is allowed to open. Keep the `defer`.

## Side Lab

<SideLab title="Build your-monitor for another operating system and run it in a Linux container">

One Go installation builds binaries for many operating systems and processors. This is **cross-compiling**, and it is how your monitor reaches the Linux servers of the later weeks.

**1. See your own platform.** Go calls the operating system `GOOS` and the processor architecture `GOARCH`. Run `go env GOOS GOARCH`. On a Mac with Apple silicon, this prints `darwin` and `arm64`. On an Ubuntu laptop with an Intel or AMD processor, it prints `linux` and `amd64`. `go tool dist list` lists every pair Go supports: 48 in Go 1.24.

**2. Build for Linux.** Set the variables for one command. `$(go env GOARCH)` keeps your own processor type, which is the type Docker on your laptop runs:

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=$(go env GOARCH) go build -o your-monitor-linux .
file your-monitor-linux
```

`file` names the format of a file. Built on an Intel or AMD laptop, the output starts like this:

```txt
your-monitor-linux: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked
```

ELF is the Linux format for binaries. **cgo** is the part of Go that calls C code, and `CGO_ENABLED=0` turns it off. With cgo on, a binary built on Linux links to the C library of the build machine, and `file` reports `dynamically linked`. With cgo off, the binary is **statically linked**: it carries everything it needs and runs on any Linux machine with that processor type.

**3. Run it in Linux.** On macOS, `./your-monitor-linux` fails with `exec format error`: macOS does not run Linux binaries. This step needs Docker, which you installed in Week 0. Docker runs a small Linux system for you. With Docker running, mount the binary into an Alpine Linux container and run it there:

```sh
docker run --rm -v "$PWD/your-monitor-linux:/your-monitor" alpine /your-monitor -url https://example.com
```

The container has no Go installed, and the check works. Week 6 runs your monitor in containers with Docker Compose.

Delete the extra binaries when you are done, or add them to `.gitignore`.

</SideLab>
