## Concepts

### Frontend and Backend

The **frontend** is the code that runs in the browser of the person using the app: HTML for structure, CSS for looks and JavaScript for behavior. You write it in TypeScript and React, and a build tool turns it into plain files that a server hands to the browser. From then on, it runs on the computer of the user. Anyone can read it with the browser developer tools, which means it cannot keep a secret, such as a database password.

The **backend** is the code that runs on servers you control. It holds the secrets, talks to the database, and decides what each user can see and change. In your monitor, the backend also does work that no browser can: it checks sites around the clock, whether or not anyone has the status page open.

One rule follows: the frontend never talks to the database. It asks the backend, and the backend checks every request before it touches data. A check in the frontend, such as a form that refuses an empty URL, is a convenience for the user. The backend repeats it, because anyone can send a request with `curl` and skip your frontend.

### How the Browser Talks to the API

The frontend and the api talk over HTTP, the protocol from <a href={weekHref(4)}>Week 4</a>. The browser sends a request with a method, such as `GET` or `POST`, and a path. The api answers with a status code, headers and a body. The body is **JSON**, the text form of JavaScript objects and arrays, such as `{"status":"ok"}`. Go writes and reads it with the `encoding/json` package, and the browser reads it with `response.json()`. The `Content-Type: application/json` header tells the receiver what the body holds.

The browser adds one rule that `curl` does not have: the **same-origin policy**. An **origin** is the scheme, host and port of a URL. `http://localhost:5173` and `http://localhost:8080` are two origins, because the ports differ. JavaScript on a page from one origin can send a request to another origin, but the browser hides the response from it unless the server allows that origin. Without the policy, a page on any site can send a request to your webmail, which carries your login cookie, and read your mail from the answer.

A server allows other origins with response headers, such as `Access-Control-Allow-Origin: http://localhost:5173`. That protocol is **CORS**, Cross-Origin Resource Sharing. Two details help when you debug it:

- For a plain `GET`, the request reaches the server, and the server does the work and answers. The browser then withholds the answer from your code, which sees only `TypeError: Failed to fetch`. CORS protects the user in the browser. It does not protect your server.
- For a request outside the simple set, such as `PUT`, `DELETE` or a `POST` with `Content-Type: application/json`, the browser first sends a **preflight**: an `OPTIONS` request that asks whether the real request is allowed. The real request goes out only when the preflight answer allows it. A plain HTML form `POST` gets no preflight: it reaches the server like the `GET` above.

Your monitor keeps the page and the API on one origin, which means it needs no CORS at all. In development, the Vite dev server serves the page on port `5173` and passes `/healthz` and `/api/` requests on to the api. A server that passes requests on like that is a **proxy**. In production, nginx in the web image (<a href={weekHref(10)}>Week 10</a>) does the same job. <a href={weekHref(7)}>Week 7</a> puts the JSON routes under `/api/` to fit.

### One Repository for Every Program

A **monorepo** keeps every part of a project in one repository: the Go services, the web app and the deployment files. One pull request can change the api and the page that calls it, and one CI run tests both.

Two Go conventions shape the layout:

- `cmd/<name>/`: one folder per program, each with its own `package main`. `go build ./cmd/api` builds the program named `api`.
- `internal/`: the go command allows an import of a package under an `internal` folder only from code in the folder that holds `internal`, or below it. Your `internal/` sits at the root of the module, which means every program in `your-monitor` can import `internal/check`, and no other module can. You can change those packages without breaking anyone else.

### Images, Containers and Multi-Stage Builds

<a href={weekHref(0)}>Week 0</a> introduced images and containers. An **image** is a stack of read-only **layers**, one for each instruction that changes files, plus settings such as the user and the program to start. A **container** is a process started from an image, with its own view of the files, the network and the process list. The [side lab](#side-lab) looks at that process from the outside.

A **Dockerfile** lists the instructions that build an image. `FROM` picks the base image, `COPY` adds files, `RUN` runs a command at build time, `USER` sets the user, and `ENTRYPOINT` sets the program each container starts. Docker caches each layer, and on the next build it reuses every layer up to the first instruction whose input changed. Put the files that change least near the top.

A **multi-stage build** has more than one `FROM`. The first stage holds the full Go toolchain and compiles your code: `golang:1.27-alpine` alone is a 75 MB download on amd64. The final stage starts again from an empty image and copies only the binaries in. The toolchain and your source never reach the image you run.

That works because Go builds a **static binary**: one file that holds every library it uses. With `CGO_ENABLED=0`, Go leaves out C code, and the binary needs nothing from the operating system, not even the C library. The empty base image is called `scratch`. Your worker needs one file beyond itself: the CA certificates from Week 4, to trust the sites it checks over HTTPS.

A process in a container runs as `root` unless the image or Compose names another user. Week 3 gave the service its own user, and the image does the same with `USER 65532:65532`, a numeric user ID and group ID with no rights beyond its own files. `scratch` has no `/etc/passwd` to look names up in, and a number needs none.

### Docker Compose

**Docker Compose** starts several containers from one file, `compose.yaml`, and stops them together. Each entry under `services:` describes one container: the image or how to build it, its settings, and its links to the others. The <a href={trackHref('containers')}>Containers track</a> covers the rest of the format.

- **Network.** Compose creates one network for the project, `your-monitor_default`, and attaches every service to it. Docker runs a DNS server on that network that answers each service name with the address of its container: the api reaches Postgres at `postgres:5432`.
- **Ports.** Your laptop cannot reach a container port until you publish it. `"127.0.0.1:8080:8080"` maps port `8080` on the loopback address of your laptop to port `8080` in the container. Leave out `127.0.0.1:`, and Docker publishes the port on every network interface, where anyone on your Wi-Fi reaches it.
- **Volumes.** Every container starts from its image, and the files it writes go when you remove it. A **named volume**, such as `pgdata`, is storage that Docker keeps apart from any container: Postgres keeps its data there. A **bind mount** maps a file or folder of your laptop into a container, the way the worker gets `urls.txt`.
- **Healthchecks.** A healthcheck is a command that Docker runs inside the container at an interval. Exit code `0` means healthy and `1` unhealthy. After `retries` failures in a row, Docker marks the container `unhealthy`.
- **Start order.** `depends_on` with `condition: service_healthy` makes Compose wait until Postgres is healthy before it starts the api and the worker. A plain `depends_on` waits only until the Postgres container starts, and Postgres takes a few seconds more to accept connections.

### Make

`make` runs commands by name. A `Makefile` holds **rules**: a target, a colon, the prerequisites, and below them the **recipe**, the commands to run, each line indented with one tab character. `make build` runs the recipe of `build`. Make exists to rebuild files: when a target names a file, Make runs its recipe only when the file is missing or older than one of its prerequisites. Most of your targets name commands, not files, and the `.PHONY` line declares them. Everyone who clones your repository gets the same short commands, and CI in <a href={weekHref(14)}>Week 14</a> runs the same checks.

### Step 1: Move the Monitor Into the New Layout

Start a branch, then move the files with `git mv`. Git stores no record of a move: it detects a rename when the old and new files have nearly the same content. Only the import lines change here. That is why `git log --follow cmd/worker/main.go` still shows the history back to Week 1:

```sh
git switch main && git pull && git switch -c week-06
mkdir -p cmd/worker internal deploy
git mv main.go run_test.go signal_test.go cmd/worker/
git mv check pool probe internal/
git mv your-monitor.service deploy/
```

The import paths still name the old folders. `grep` lists every Go file that imports `check`, `pool` or `probe`, and `perl -pi -e` rewrites each one in place to add `internal/`, the same way on macOS and Linux:

```sh
grep -rlE --include='*.go' 'your-monitor/(check|pool|probe)"' . | xargs perl -pi -e 's#your-monitor/(check|pool|probe)"#your-monitor/internal/$1"#'
go vet ./... && go test ./...
```

Every test passes unchanged. `git status` lists the moved files as renamed, and `git diff` shows only import lines. A move changes where code lives, not what it does: the example tests check that each moved file matches its Week 5 version apart from the import paths. The unit file in `deploy/` still runs `/usr/local/bin/your-monitor`. To install the worker under that name, build it with `go build -o your-monitor ./cmd/worker`.

The go command now enforces the `internal/` rule. The example tests build a program outside `your-monitor` that imports `internal/check`, and the build fails:


## Observe It

<ObserveIt>

Three views show how the stack is doing. The outputs are examples.

**Health.** `docker compose ps` adds `(healthy)`, `(unhealthy)` or `(health: starting)` to the status of each service with a healthcheck. Docker keeps the last five check results, with exit code and output:

```txt
$ docker inspect --format '{{.State.Health.Status}} streak={{.State.Health.FailingStreak}}' your-monitor-api-1
healthy streak=0
$ docker inspect --format '{{json .State.Health.Log}}' your-monitor-api-1
```

**Logs.** `make logs` follows all three services, and Compose puts the service name in front of each line. The worker logs `started pid=1`: in its container, it is the first process. The round lines from Week 5 work as before: `docker compose logs --since 10m worker | grep ' round '` lists the last ten minutes of rounds, with their timeouts.

**Resources and size.** `docker stats --no-stream` prints the CPU and memory use of each container. With no limit set, its limit column shows all the memory of the Docker host: the [side lab](#side-lab) sets one. `docker image ls` lists `your-monitor-worker` at about 7 MB, the binary and a certificate file of about 200 KB. Compare it with the `golang` image that built it.

Read these signs:

- **`(health: starting)` never turns `healthy`.** The check command fails every time. The `Output` field of `.State.Health.Log` holds its error message.
- **`curl` works from your laptop, but the api is `unhealthy`.** The healthcheck runs inside the container. Its URL names a different port from the one the api listens on.
- **`docker compose ps` shows `Restarting`.** The program exits with an error, and `restart: on-failure` starts it again. `docker compose logs api` shows the last words of each run.
- **The worker memory climbs every round.** A leak. Check `goroutines=` in the round lines, as in Week 5.

</ObserveIt>

## Operate It

<OperateIt>

**Stop sends SIGTERM, then SIGKILL after 10 seconds.** `docker compose stop worker` sends SIGTERM and waits up to 10 seconds, the pattern from Week 3. Your worker cancels its checks and exits at once, and `docker compose ps -a` shows `Exited (0)`. A stop that takes the full 10 seconds and ends in `Exited (137)`, 128 plus 9 for SIGKILL, means SIGTERM never reached your code: the program ignores it, or it runs under a shell that does not pass it on. `stop_grace_period` in `compose.yaml` raises the 10 seconds for a service that needs longer.

**The volume outlives the containers.** `make down` keeps `your-monitor_pgdata`. `docker compose down --volumes` deletes it, with every row in it. Because Postgres reads `POSTGRES_PASSWORD` only on an empty volume, a password you change in `.env` later never reaches the database: in Week 8, the api then fails with `password authentication failed for user "monitor"`. While the database holds nothing you need, delete the volume and start again.

**A dynamic binary in an empty image.** On a Linux machine with a C compiler, such as the Debian-based `golang` images, `go build` turns cgo on by default and links the C library. In `scratch`, that binary fails at start with `exec /worker: no such file or directory`, although the file is there: the missing file is the loader that a dynamic binary names. `file` tells the two apart: `statically linked`, or `dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2` on amd64.

| What you see | What it points to |
| --- | --- |
| `port is already allocated` or `address already in use` | Another program or container holds that port on your laptop, such as a local Postgres on `5432`: set `POSTGRES_PORT=5433` in `.env` |
| `dependency failed to start: container your-monitor-postgres-1 is unhealthy` | Postgres fails its healthcheck ten times in a row: read `docker compose logs postgres` |
| `go: go.mod requires go >= 1.27.2 (running go 1.24.7; GOTOOLCHAIN=local)` during the build | `GO_VERSION` in the Dockerfile is older than the `go` line of `go.mod` |
| `x509: certificate signed by unknown authority` on every HTTPS check | The image has no CA certificates: the `COPY` of `ca-certificates.crt` is missing |
| `connection refused` for a URL with `127.0.0.1` or `localhost` in `urls.txt` | Inside a container, `127.0.0.1` is the container itself. Docker Desktop answers `host.docker.internal` with the address of your laptop. On Linux, add `extra_hosts: ["host.docker.internal:host-gateway"]` to the service, and listen on the Docker gateway address, not only on `127.0.0.1` |
| `missing separator` from `make` | A recipe line starts with spaces instead of a tab |

</OperateIt>

## Side Lab

<SideLab title="A container is a process: find its namespaces and its cgroup">

A container is an ordinary Linux process that the kernel gives a restricted view. **Namespaces** give it its own process list, host name, network and files. A **cgroup**, short for control group, limits the CPU and memory it uses. On macOS, these commands run in the Linux virtual machine of Docker Desktop. The outputs are examples.

**1. Start a container with a memory limit,** then look at it from inside and from outside:

```txt
$ docker run -d --name lab --memory 64m alpine:3.24 sleep 3600
$ docker exec lab ps
PID   USER     TIME  COMMAND
    1 root      0:00 sleep 3600
    7 root      0:00 ps
$ docker top lab
UID     PID     PPID    C    STIME   TTY   TIME       CMD
root    48213   48190   0    07:15   ?     00:00:00   sleep 3600
```

Inside, `sleep` is PID 1 in a process list of its own: that is the PID namespace. `docker top` shows the same process as the host sees it, with PID 48213. On Linux, `ps -o pid,user,cmd -p 48213` finds it in your own process list, next to your shell.

**2. Read the cgroup limit.** `docker exec lab cat /sys/fs/cgroup/memory.max` prints `67108864`: 64 MiB in bytes, 64 × 1024 × 1024.

**3. Hit the limit.** `tail /dev/zero` looks for the last line of a file with no line breaks and keeps everything it reads in memory:

```txt
$ docker run --name hog --memory 64m alpine:3.24 tail /dev/zero; echo "exit $?"
exit 137
$ docker inspect --format '{{.State.OOMKilled}}' hog
true
```

When the container reaches its limit, the out-of-memory killer of the kernel ends `tail` with SIGKILL: exit code 137, 128 plus 9, as in Week 3. Kubernetes sets the same cgroup limit for each container from its `resources.limits.memory`. Clean up with `docker rm -f lab hog`.

</SideLab>
