## Concepts

### Concurrency and Parallelism

**Concurrency** means several tasks are in progress at once: each one starts before the last one ends. **Parallelism** means several tasks execute at the same instant, on different CPU cores. A cook with four pots on the stove works concurrently. Four cooks work in parallel.

A check spends nearly all its time waiting: for DNS, for the handshakes, for the server. While one check waits, the CPU is free to start another. That is why concurrency speeds up your monitor even on a machine with one core: 100 checks that each wait 2 seconds take 2 seconds together, not 200, when they all wait at the same time.

### Goroutines

A **goroutine** is a function that runs concurrently with the rest of your program. The `go` keyword starts one:

```go
go check(url) // starts check in a new goroutine and moves on at once
```

The line returns before `check` does, and nothing waits for it. A goroutine starts with a stack of a few kilobytes that grows as needed, which makes it far cheaper than an operating system thread: a program can run tens of thousands of them. When `main` returns, the program exits and every goroutine stops with it, finished or not. A goroutine has no return value: to get a result back, or to know when it ends, you need a channel or a `sync.WaitGroup`, both below.

### The Scheduler

The Go **scheduler** is the part of the Go runtime that decides which goroutine runs where. It runs many goroutines on a few operating system threads. It keeps one **P**, short for processor, for each goroutine that can run in parallel. `GOMAXPROCS` sets how many Ps exist, and it defaults to the number of CPU cores. On Linux, Go 1.25 and newer default it to the CPU limit of the container instead, when that limit is lower: Week 6 runs the monitor in containers. Each P runs one goroutine at a time on one thread. The <a href={trackHref('operating-systems')}>Operating Systems track</a> covers threads and the kernel scheduler underneath.

### Channels

A **channel** is a typed pipe between goroutines. `make(chan string)` creates one that carries strings. `ch <- v` sends a value, and `v := <-ch` receives one.

An **unbuffered** channel, made with `make(chan string)`, has no room to hold a value. A send waits until another goroutine receives, and a receive waits until another goroutine sends. Every send is a handoff: when it returns, you know a receiver has the value.

A **buffered** channel, made with `make(chan string, 10)`, holds up to ten values. A send waits only when the buffer is full, and a receive waits only when it is empty. A buffer absorbs a burst. It does not fix a receiver that is slower than the sender for good: the buffer fills, and the sender waits again.

`close(ch)` tells the receivers that no more values come. A receive on a closed channel returns at once, with the zero value once the buffer is empty. `for v := range ch` receives until the channel is closed and empty, then ends the loop. Only the sender closes a channel. A send on a closed channel panics, and a second `close` panics too.

### Select

`select` waits on several channel operations and runs the first one that is ready. Week 3 used it to wait for either a tick or `ctx.Done()`. A case can send too: the pool pairs `case jobs <- target:` with `case <-ctx.Done():` to stop sending on cancellation. When several cases are ready at the same moment, `select` picks one at random. Code that depends on one case winning needs a second check, as the pool shows.

### WaitGroup

A `sync.WaitGroup` counts goroutines that have not finished yet. `wg.Add(1)` raises the count before you start a goroutine, `wg.Done()` lowers it when the goroutine ends, and `wg.Wait()` blocks until the count reaches zero. Call `Add` before the `go` statement, never inside the new goroutine: otherwise `Wait` can run first, see zero and return. Go 1.25 adds `wg.Go(f)`, which calls `Add`, runs `f` in a new goroutine and calls `Done` when `f` returns. This page uses `Add` and `Done`, which work in Go 1.24 or newer. The `errgroup` package in `golang.org/x/sync` adds error handling and a limit on top of the same idea. This course keeps to the standard library.

The two errors tell you what happened. `context.DeadlineExceeded` means the site ran out of time: a timeout to count. `context.Canceled` means your own program stopped the check, which is not the fault of the site. By convention, a Go function that takes a context takes it as its first parameter, named `ctx`.

### Data Races, Mutexes and Channels

A **data race** happens when two goroutines touch the same memory at the same time, at least one of them writes, and nothing synchronizes them. Go makes no promise about the result: a counter loses increments, a slice loses entries, a map crashes the program. The race detector from Week 2, `go test -race`, reports a race only when a test makes it happen, which is why the pool tests run many checks at once, 20 times over.

Goroutines that share memory need **synchronization**: a rule that makes their reads and writes take turns. Go gives you two tools. A channel hands a value from one goroutine to another, and from then on only the receiver touches it. A `sync.Mutex`, from Week 4, is a lock around memory that several goroutines touch in place. Pick the one that matches the job. The pool passes URLs and results along, which is a channel job: no two goroutines ever hold the same `Result`. `probe.Check` has hooks that write into one `Timings` value from another goroutine, which is a mutex job. For one counter, the `sync/atomic` package is simpler still: `atomic.Int64` has `Add` and `Load` methods that are safe from any goroutine. The tests below use it.

### Goroutine Leaks

A **goroutine leak** is a goroutine that waits forever: on a channel nobody sends to or receives from, or on a lock nobody releases. Go never collects it. It holds its stack, and every value it points to, until the process exits. A monitor that leaks a few goroutines every round runs out of memory after weeks, the same slow failure as the file descriptor leak in <a href={weekHref(3)}>Week 3</a>. Every goroutine you start needs a clear way to end. In the pool, each worker ends when `jobs` closes, the feeder ends after the last URL or on `ctx.Done()`, and the closer ends when the workers have.

### Why Bound the Pool

Starting one goroutine per URL with `go` looks simpler, and for five URLs it works. With 1,000 URLs, it opens 1,000 connections at the same instant, and two things break:

- **File descriptors.** Each connection holds one until it closes, as Week 3 showed. A process that reaches its `Max open files` limit gets `socket: too many open files` on the next connection, and the monitor reports sites as down that are fine.
- **The site on the other end.** When many URLs share one host, that host receives a burst of requests from one address. Many sites answer a burst with status `429 Too Many Requests`, or a firewall blocks the address. Your monitor then reports an outage that it caused itself.

A pool of N workers keeps both numbers at N, however long the list grows.

## Observe It

<ObserveIt>

**Count timeouts.** The round line is your first metric. Under systemd, add up the timeouts of the last hour:

```sh
journalctl -u your-monitor --since "1 hour ago" | awk -F'timeouts=' '/ round /{split($2, a, " "); n += a[1]} END {print n}'
```

`-F'timeouts='` splits each round line at `timeouts=`, `split` takes the number after it, and `END` prints the total. Then list the sites that time out, with the most timeouts first:

```sh
journalctl -u your-monitor --since "1 hour ago" | grep 'context deadline exceeded' | grep -o 'url=[^ ]*' | sort | uniq -c | sort -rn | head
```

Read the round lines for these patterns:

- **The same few URLs time out every round.** Those sites are down without refusing connections, or a firewall drops your packets: the black hole from Week 4.
- **Every URL times out in the same round.** The problem is on your side: your network, your DNS resolver, or a machine too busy to run the checks.
- **`duration_ms` is a multiple of `-timeout`.** Slow sites hold the workers. With S slow sites and W workers, a round takes at least S divided by W timeouts, rounded up, and the fast sites wait in the queue behind them.
- **`duration_ms` is larger than `-interval`.** The rounds overrun, and the ticker drops the missed ticks, as in Week 3. Raise `-workers` or `-interval`, or lower `-timeout`.
- **`goroutines` climbs every round.** A leak. In a healthy monitor, the number is the same at the end of every round. [Operate It](#operate-it) shows a leak.

</ObserveIt>

## Operate It

<OperateIt>

**A leak that grows every round.** Plant a deadline on the round in `Run`. Replace the `for r := range results` loop with this, and import `time`:

```go
deadline := time.After(time.Second)
for {
	select {
	case r, ok := <-results:
		if !ok {
			return out
		}
		out = append(out, r)
	case <-deadline:
		return out // give up on the stragglers
	}
}
```

Start the test site, then run the monitor with the debug server:

```sh
go run . -file urls100.txt -timeout 2s -interval 3s -debug-addr 127.0.0.1:6060
```

In a test run, every round line showed `skipped=17`: ten checks still in flight and seven URLs never sent. The goroutine count grew by 12 a round: `goroutines=36`, then `48`, `60` and `72`. In a second terminal, ask the debug server for the goroutine dump. `debug=1` groups identical stacks and counts them. This output is trimmed:

Read it from the top: 31 workers, `func1`, wait on line 44, the send to `results`. After one second, `Run` stops reading, and every worker still in a slow check blocks on its send for good. With no free worker, the feeder, `func2`, blocks on its send to `jobs`: one per round. The closer, `func3`, waits for all of them. `debug=2` prints every goroutine in full, with its state and, after the first minute, how long it has waited, such as `[chan send, 3 minutes]`. `go tool pprof -top http://127.0.0.1:6060/debug/pprof/goroutine` shows the counts per function as a table.

The tests pass with this bug, because no test check runs longer than one second. Write one that fails: one URL that answers after 1.5 seconds, a 2-second timeout, then `checkNoLeaks`. Then put the `range` loop back. A round that needs a time limit gets one through its context: the context cancels the checks, and `Run` still collects every result.

**One goroutine per URL.** Replace the body of `Run` after the `panic` check with the unbounded version, and delete the `sync` import:

```go
results := make(chan check.Result)
for _, target := range targets {
	go func() { results <- checkOne(ctx, target) }()
}
var out []check.Result
for range targets {
	out = append(out, <-results)
}
return out
```

Write 1,000 slow URLs with `for i in $(seq 1 1000); do echo "http://127.0.0.1:8000/slow/$i"; done > urls1000.txt`. A Go program raises its soft limit on open files to the hard limit when it starts, and `ulimit -SHn 256` lowers both for the shell and the programs it starts. In zsh, the default shell on macOS, a plain `ulimit -n` sets only the soft limit:

```txt
$ go build
$ ulimit -SHn 256
$ ./your-monitor -file urls1000.txt -timeout 5s -interval 1m
2026/10/11 05:49:34 round checks=1000 up=0 down=1000 timeouts=251 cancelled=0 skipped=0 duration_ms=5049 goroutines=3
```

251 checks get a socket and time out as expected. The other 749 fail at once with `dial tcp 127.0.0.1:8000: socket: too many open files`: sites your monitor reports as down because of its own limit. Close that shell, and run the binary from a new one. The limit no longer stops it, and the test site logs `peak_in_flight=1000`: one monitor sends 1,000 requests at the same site within a second. Undo the change and run the tests.

**A channel nobody closes.** Delete `defer close(jobs)` from the feeder and run `go test -timeout 10s ./pool`. No assertion fails: the test hangs for 10 seconds, then the test binary panics with `panic: test timed out after 10s` and dumps every goroutine. Search the dump for `pool.Run`: eight workers wait in `[chan receive]` on the `for target := range jobs` line, and `Run` waits on its own `range results`. A loop over a channel ends only when someone closes that channel. Put the line back.

## Side Lab

<SideLab title="Watch the scheduler run waiting and computing goroutines">

The pool speeds up checks because they wait. Work that computes needs a CPU core for each goroutine. This lab shows the difference and the run queue that fills. Put this program in a new folder, and run `go mod init spin` there:

<CodeFrom file="go/week05/spin/main.go" region="spin" lang="go" title="spin/main.go" />

`compute` keeps one core busy for a fixed number of steps. Run the program twice, the second time with one P. These numbers come from a test run on a 4-core machine that other programs shared:

```txt
$ go run .
GOMAXPROCS=4 CPUs=4
wait    goroutines=1 took 500ms
wait    goroutines=4 took 500ms
compute goroutines=1 took 420ms
compute goroutines=4 took 600ms
$ GOMAXPROCS=1 go run .
GOMAXPROCS=1 CPUs=4
wait    goroutines=1 took 500ms
wait    goroutines=4 took 500ms
compute goroutines=1 took 410ms
compute goroutines=4 took 1.65s
```

Waiting takes the same time on one P or four: a sleeping goroutine holds no P. Computing on four goroutines takes four times as long with one P, because they take turns on it. With four Ps and four idle cores, it takes as long as one goroutine. On a busy machine, as here, it takes a little longer.

Now watch the queues. `GODEBUG=schedtrace=200` makes the runtime print one line about the scheduler to stderr every 200 ms. Build the program first: `go run` is a Go program too, and prints its own lines. Two of the lines, from the waits and from the compute step:

```txt
$ go build
$ GOMAXPROCS=1 GODEBUG=schedtrace=200 ./spin
SCHED 411ms: gomaxprocs=1 idleprocs=1 threads=3 spinningthreads=0 needspinning=0 idlethreads=1 runqueue=0 [0]
SCHED 1639ms: gomaxprocs=1 idleprocs=0 threads=3 spinningthreads=0 needspinning=1 idlethreads=1 runqueue=2 [1]
```

During the waits, `idleprocs=1`: the one P has nothing to run. During the compute step, `runqueue` is the global queue and the number in brackets is the local queue of the P. Together they hold three: three goroutines wait their turn while the fourth runs. Run it without `GOMAXPROCS=1` on a 4-core machine: during the compute step, the brackets hold four local queues, one per P, and every queue reads `0`, because each goroutine has a P of its own.
