## Concepts

### Tables, Rows and Constraints

Postgres is a **relational database**: it keeps data in **tables**. A table has named **columns**, each with a type, and holds **rows**, one value per column. You ask for data in SQL, and Postgres works out how to find it.

Your schema uses a few types. `bigint` is a 64-bit integer, the size of a Go `int64`. `bigserial` is a `bigint` that Postgres fills from a counter: 1, 2, 3. `text` is a string of any length. `timestamptz` is a point in time, stored as UTC. `boolean` is true or false.

A column with no value holds **NULL**. NULL means unknown or absent, which differs from zero. Your monitor needs that difference: a TLS time of `0` ms says the handshake happened and took under a millisecond, and NULL says a plain `http://` check has no handshake at all. In Go, a nullable column becomes a pointer, such as `*int`, and `nil` stands for NULL.

**Constraints** are rules that Postgres enforces on every write, from every program, including a `psql` session where someone types an `insert` by hand:

- **Primary key**: names each row, unique and never NULL. Every table here has one.
- **Unique**: no two rows share the value. `monitors.url` is unique, and the api turns a violation into `409 Conflict`.
- **Check**: an expression every row must pass, such as `interval_seconds between 30 and 3600`. `monitor.Validate` checks the same rule first, to give a friendly error. The constraint catches any code that skips it.
- **Foreign key**: a value that must exist in another table. Each `check_results.monitor_id` names a row in `monitors`. `on delete cascade` deletes the results of a monitor when you delete the monitor.

### Connections and the Pool

Your programs talk to Postgres over a TCP connection, port `5432`, with a username and password. For each connection, Postgres starts a separate operating-system process, called a **backend**, that serves it until the connection closes. Opening a connection costs a process, memory and several round trips. A server accepts `max_connections` connections, `100` by default, and refuses the next one with `sorry, too many clients already`.

A **connection pool** opens a few connections and lends them out. Your code asks the pool for a connection, runs a query and gives it back, and the pool reuses it for the next query. You use `pgxpool` from `github.com/jackc/pgx/v5`, a widely used Postgres driver for Go. Its pool holds at most 4 connections or one per CPU, whichever is more. Add `pool_max_conns=10` to the connection string to change it.

Every query in your code sends its values separately from the SQL, as **parameters**: `where id = $1`, with the ID as an argument. Postgres never reads a parameter as SQL. Code that glues strings into SQL, such as `"where url = '" + url + "'"`, hands control to the data: a URL that contains a quote rewrites the query. That attack is called **SQL injection**, and parameters rule it out.

### Transactions and the Write-Ahead Log

A **transaction** groups statements: `BEGIN`, the statements, then `COMMIT`. Postgres applies all of them or none of them, and other connections never see half of it. `ROLLBACK`, or any error, throws the whole group away. A statement you send outside `BEGIN` runs as a transaction of its own.

`COMMIT` returns once the change is safe on disk. Postgres does not rewrite the table files at every commit, because those writes land all over the disk. It appends a record of each change to the **write-ahead log**, or WAL, in the `pg_wal` folder, and asks the disk to flush it with `fsync`. The changed table pages stay in memory, in **shared buffers**, and a **checkpoint** writes them to the table files later, by default at least every 5 minutes. After a crash, Postgres replays the WAL from the last checkpoint and ends up with every committed transaction and none of the others.

### Migrations

The schema changes over the life of the app: Week 9 adds a job queue, Week 11 adds users. Each change is a **migration**: a SQL file with a number, such as `001_init.sql` or `002_jobs_alerts.sql`. Your programs carry the files inside their binary and apply the new ones at start, in order of number. The `schema_migrations` table records each version that has run, which means each file runs once on each database: your laptop, CI and, in Week 16, the live server.

Two rules keep this safe:

- Each file runs in a transaction, together with its `schema_migrations` row. In Postgres, `create table` and the other schema statements are transactional too: a file that fails halfway leaves no trace, and the next start tries it again.
- A file that has run anywhere never changes. Postgres never sees the edit, because version 1 is already recorded. To change the schema, add the next file.

The api and the worker both migrate at start, and Compose starts them at the same moment. An **advisory lock** keeps them in line: a lock on a number of your choosing, which `pg_advisory_lock` takes, waiting while another connection holds it. The second program waits for the first to finish.

### Indexes

The api asks for the newest 50 results of one monitor. Without help, Postgres reads every row of `check_results`, keeps those of that monitor, sorts them by time and returns the first 50. That is a **sequential scan**, and its cost grows with the table: 100 monitors checked every 30 seconds add 288,000 rows a day.

An **index** is a second structure, sorted by the columns you name, that points at the rows. Postgres uses a **B-tree** by default, a balanced tree that finds one key in a few page reads and then walks forward in order. The index `(monitor_id, checked_at desc)` matches the query exactly: Postgres jumps to the entries of that monitor, which already sit newest first, reads 50 and stops. The order of the columns matters: an index on `(checked_at, monitor_id)` sorts by time first and spreads one monitor across the whole tree.

An index has a price. Every insert updates each index of the table, and indexes take disk space. Add the index that a real query needs, and check with `EXPLAIN` that Postgres uses it. `EXPLAIN` prints the **plan**, the steps Postgres chooses for a query, and `EXPLAIN ANALYZE` runs the query and adds the real times. These plans come from a table that holds a week of checks for 100 monitors, 2,016,000 rows. Both are trimmed, and the second has its cost estimates removed:

```txt
 Limit  (cost=0.43..141.60 rows=50 width=81) (actual time=0.042..0.205 rows=50 loops=1)
   ->  Index Scan using check_results_monitor_time on check_results  (cost=0.43..56544.54 rows=20026 width=81) (actual time=0.041..0.198 rows=50 loops=1)
         Index Cond: (monitor_id = 42)
 Execution Time: 0.244 ms
```

Read a plan from the innermost line out. The index scan finds the entries for monitor 42 and returns rows in order. `Limit` stops it after 50. The `cost` numbers are estimates in arbitrary units; `actual time` is in milliseconds. Without the index, the same query reads the whole table on three processes and sorts what it keeps:

```txt
 Limit  (actual time=69.670..74.069 rows=50 loops=1)
   ->  Gather Merge  (actual time=69.668..74.061 rows=50 loops=1)
         Workers Planned: 2
         ->  Sort  (actual time=66.216..66.220 rows=50 loops=3)
               Sort Key: checked_at DESC
               ->  Parallel Seq Scan on check_results  (actual time=0.032..65.187 rows=6720 loops=3)
                     Filter: (monitor_id = 42)
                     Rows Removed by Filter: 665280
 Execution Time: 74.127 ms
```

That is 300 times slower, and it grows with the table. On a table of a few rows, Postgres picks the sequential scan even when the index exists, because reading one page costs less than walking a tree. A plan on an empty development database tells you little: test with realistic data, as [Observe It](#observe-it) does.

### Backups

A **backup** is a copy of the data that you can restore after a mistake, a broken disk or a lost server. `pg_dump` writes a **logical backup**: the schema and the rows of one database, as of one consistent moment, while the programs keep writing. Its custom format, `--format=custom`, is compressed, and `pg_restore` reads it back into an empty database. It holds no index data, only the `create index` statements: the restore rebuilds each index.

Two rules decide whether a backup is worth anything. First, keep it on another disk and another machine, because the failure that destroys the database takes a backup on the same disk with it. Second, a backup you have never restored is a hope, not a backup. Restore it on a schedule, into a new database, and compare what comes back. The <a href={trackHref('backups')}>Backups track</a> covers the other kind, physical backups with WAL archiving, which restore to any moment.

## Observe It

<ObserveIt>

A database with a few hundred rows hides every performance problem. Load a lab database with a week of checks for 100 monitors, 2,016,000 rows, next to your real one. On a laptop, the inserts take about half a minute:

```sh
docker compose exec postgres createdb -U monitor monitor_lab
docker compose exec -T postgres psql -U monitor -d monitor_lab < migrations/001_init.sql
docker compose exec -T postgres psql -U monitor -d monitor_lab <<'SQL'
insert into monitors (url, interval_seconds)
  select 'https://site' || n || '.example', 30 from generate_series(1, 100) n;
insert into check_results (monitor_id, checked_at, up, status_code, dns_ms, connect_ms, tls_ms, first_byte_ms, total_ms)
  select m.id, now() - n * interval '30 seconds', true, 200, 12, 11, 14, 52, 53
    from monitors m, generate_series(1, 20160) n;
vacuum analyze check_results;
SQL
```

`generate_series(1, 20160)` returns the numbers 1 to 20,160, one row each: two checks a minute for seven days. `vacuum analyze` updates the statistics that the planner uses to pick a plan.

**The slow-query log.** `compose.yaml` starts Postgres with `log_min_duration_statement=200ms`: every statement that runs for 200 ms or longer goes to the Postgres log with its time. Run `make psql`, connect to the lab with `\c monitor_lab`, turn on `\timing on` to print the time of each query, and run an uptime report:

```sql
select monitor_id, round(100 * avg(up::int), 2) as uptime_pct
  from check_results where checked_at > now() - interval '7 days'
 group by monitor_id order by uptime_pct limit 3;
```

It reads every row of the week, and `docker compose logs postgres` shows it:

```txt
2026-10-11 06:58:46.524 UTC [10999] LOG:  duration: 234.842 ms  statement: select monitor_id, round(100 * avg(up::int), 2) as uptime_pct from check_results where checked_at > now() - interval '7 days' group by monitor_id order by uptime_pct limit 3
```

The number in brackets is the process ID of the backend. Run `explain analyze` on the results query for monitor 42 and compare with the plans in [Indexes](#indexes). In a real database, each line in this log is a question to answer: which program sends the query, how many times an hour, and whether an index or a smaller time window fixes it.

**Size and growth.** Measure the table and its indexes:

```txt
monitor_lab=# select pg_size_pretty(pg_relation_size('check_results')) as table,
monitor_lab-#        pg_size_pretty(pg_indexes_size('check_results')) as indexes,
monitor_lab-#        pg_total_relation_size('check_results') / count(*) as bytes_per_row
monitor_lab-#   from check_results;
 table  | indexes | bytes_per_row
--------+---------+---------------
 179 MB | 132 MB  |           161
```

At 161 bytes a row, 100 monitors every 30 seconds add 46 MB a day and 1.4 GB a month, and the two indexes are more than 40% of it. That number decides when the disk is full, which [Operate It](#operate-it) covers. Drop the lab with `docker compose exec postgres dropdb -U monitor monitor_lab` when you finish.

**Connections.** `select pid, state, left(query, 40) from pg_stat_activity where datname = 'monitor';` lists one row per connection: the pools of the api and the worker, `idle` between queries, and your own `psql`. A count that climbs toward `max_connections` points to a program that opens pools and never closes them.

## Operate It

<OperateIt>

**The disk fills up.** Postgres needs space for the WAL before it changes anything. For this page, a test server ran Postgres on a 96 MB disk and inserted rows until the disk ran out of space. Its log, trimmed:

```txt
PANIC:  could not write to file "pg_wal/xlogtemp.11898": No space left on device
LOG:  WAL writer process (PID 11898) was terminated by signal 6: Aborted
LOG:  all server processes terminated; reinitializing
LOG:  database system was not properly shut down; automatic recovery in progress
FATAL:  could not write to file "pg_wal/xlogtemp.12010": No space left on device
LOG:  startup process (PID 12010) exited with exit code 1
LOG:  shutting down due to startup process failure
```

A PANIC stops every backend. Postgres restarts, tries to recover, needs disk space for that too, and shuts down. From then on, every program gets `connection refused`, and the api answers 500 on every route. Postgres starts again once there is space. After the test gave the disk more room, recovery replayed the WAL, and all 100,000 rows of the last committed insert came back. The insert that hit the full disk never committed, and nothing of it remained. Do not delete files from `pg_wal` to make space: they hold committed data that is not in the table files yet. Free space elsewhere or grow the disk.

To see it coming, watch free space: `docker system df -v` shows the size of the `pgdata` volume, and `df -h` the free space on a server. Alert at 80% full. Week 13 adds the alert.

**Old rows never leave by themselves.** Keep 30 days with `delete from check_results where checked_at < now() - interval '30 days'`. A DELETE does not return space to the disk: Postgres marks the rows dead, and **VACUUM** later makes their space reusable for new rows. In the lab, deleting 1,152,200 of 2,016,000 rows left the table and its indexes at 311 MB. `vacuum check_results` brought them to 209 MB, because it gives back only empty pages at the end of the table file. `vacuum full check_results` rewrote everything at 121 MB, but it locks the table against every read and write while it runs, and it needs room for a full copy. Postgres runs VACUUM on its own, as **autovacuum**. Delete old rows every day, and the freed space gets reused before the file grows. Week 9 runs that job.

| What you see | What it points to |
| --- | --- |
| `failed SASL auth: FATAL: password authentication failed for user "monitor" (SQLSTATE 28P01)` | `POSTGRES_PASSWORD` in `.env` changed after Docker created the volume. Postgres reads it only on an empty volume, as Week 6 says |
| `dial tcp 127.0.0.1:5432: connect: connection refused` | Postgres is not running, or it listens on another port: check `docker compose ps` and `POSTGRES_PORT` in `.env` |
| `ERROR: relation "monitors" does not exist (SQLSTATE 42P01)` | The program queries before `Migrate` runs, or it connects to another database or schema than the one it migrated |
| `duplicate key value violates unique constraint "pg_type_typname_nsp_index"` at start | Two programs ran the same migration at once: the advisory lock is missing |
| `violates foreign key constraint "check_results_monitor_id_fkey"` in the worker log | Someone deleted a monitor during the round. The worker logs it and moves on, and the next round no longer lists that monitor |
| `FATAL: sorry, too many clients already (SQLSTATE 53300)` | The programs together hold more connections than `max_connections` |

</OperateIt>

## Side Lab

<SideLab title="Two sessions, one row: watch a lock wait and a deadlock">

Transactions that change the same row take turns. Open two terminals, and in each run `make psql`. Call them A and B. The outputs are examples.

**1. A lock wait.** In A, run `begin;` and `update monitors set interval_seconds = 60 where id = 1;`. In B, run `begin;` and `update monitors set interval_seconds = 90 where id = 1;`. B hangs: A holds a lock on that row until its transaction ends. Open a third terminal with `make psql` and look:

```txt
monitor=# select pid, state, wait_event_type, wait_event, pg_blocking_pids(pid) as blocked_by
monitor-#   from pg_stat_activity where datname = 'monitor' and query like 'update%';
  pid  |        state        | wait_event_type |  wait_event   | blocked_by
-------+---------------------+-----------------+---------------+------------
 13883 | idle in transaction | Client          | ClientRead    | {}
 13884 | active              | Lock            | transactionid | {13883}
```

A is `idle in transaction`: it holds the lock and waits for you. Run `commit;` in A, and B finishes at once. Run `commit;` in B. The row holds `90`, because B wrote last.

**2. A deadlock.** In A, run `begin;` and update monitor 1. In B, run `begin;` and update monitor 2. Now in A, update monitor 2: A waits for B. In B, update monitor 1: B waits for A, and neither can ever finish. After one second, the `deadlock_timeout`, Postgres looks for a cycle of waits and cancels one of the two transactions:

```txt
ERROR:  deadlock detected
DETAIL:  Process 14119 waits for ShareLock on transaction 1711; blocked by process 14118.
Process 14118 waits for ShareLock on transaction 1710; blocked by process 14119.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,2) in relation "monitors"
```

The cancelled transaction is over: its `commit;` prints `ROLLBACK`. The other one goes on and commits. Code that updates several rows in one transaction avoids deadlocks by touching them in the same order every time, such as by `id`.

Week 9 builds the job queue on exactly these row locks, with `FOR UPDATE SKIP LOCKED`: a worker skips a row that another worker has locked instead of waiting for it. The <a href={trackHref('databases')}>Databases track</a> covers isolation levels, which decide what one transaction sees of the others.

</SideLab>
