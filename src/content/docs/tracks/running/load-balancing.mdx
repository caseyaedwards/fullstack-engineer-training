A **load balancer** sits in front of several copies of a service and decides which copy answers each connection or request. It turns one address into many servers, which gives you more capacity, and one copy can fail or restart without users noticing. Every request to your status page passes through two or three of them, and each one has its own rules for picking a copy and noticing a broken one.

## What It Is

### Why Spread Traffic

Each copy of a service behind a load balancer is a **backend**, and the set of backends the balancer can choose from is the **pool**. A balancer gives you three things:

- **Capacity.** Four api pods answer about four times the requests of one, as long as the database keeps up.
- **Availability.** When one backend crashes, the balancer sends its traffic to the others.
- **Safe deploys.** A rolling update replaces backends one at a time while the rest keep serving.

The balancer itself becomes the one thing every request needs. Cloud providers run theirs as a cluster of machines behind one address. On your one virtual private server (VPS), the balancer and the backends share the same machine, and losing the machine loses everything.

### Layer 4 and Layer 7

Networking describes a connection in layers. **Layer 4**, the transport layer, is TCP, the Transmission Control Protocol, and UDP, the User Datagram Protocol: ports and connections. They travel between addresses of **layer 3**, the network layer, where the Internet Protocol (IP) moves each packet from one IP address to another. **Layer 7**, the application layer, is the protocol inside the connection, here HTTP. The <TrackLink slug="networking">Networking track</TrackLink> covers the layers in full.

A **layer 4 balancer** sees only the IP address and port of each packet. It picks a backend when a TCP connection opens and forwards every byte of that connection to the same backend, without reading it. It cannot route by path, and it does not end Transport Layer Security (TLS), the encryption under HTTPS: the encrypted bytes pass through to the backend. It is fast and protocol-agnostic. Three balancers on your path work at layer 4: kube-proxy, the part of Kubernetes that implements Services on each node; ServiceLB in k3s; and network load balancers in the cloud.

A **layer 7 balancer** is a **reverse proxy**: it accepts the connection itself, ends TLS, reads each HTTP request and opens its own connection to the backend it picks. It routes by host name, path or header, retries a failed request on another backend, adds headers such as `X-Forwarded-For`, and limits rates. It picks a backend per request, not per connection. Traefik, nginx, HAProxy and Envoy, and application load balancers in the cloud, work at layer 7.

The difference matters for long connections. A browser that holds one HTTP/2 connection open sends every request over it. A layer 4 balancer pins all of them to one backend; a layer 7 balancer spreads them.

### Picking a Backend

The rule that picks the next backend is the **algorithm**:

- **Round robin** hands out backends in turn: A, B, C, A, B, C. It needs no information about the backends and works well when every request costs about the same. **Weighted round robin** gives a bigger machine more turns. Traefik and nginx use weighted round robin by default, with every weight at one unless you set it.
- **Least connections** picks the backend with the fewest requests in progress. When some requests take 5 ms and others 5 seconds, a backend stuck on slow requests stops receiving new ones.
- **Random** picks any healthy backend. kube-proxy in its default iptables mode, which writes rules into the packet filter of the Linux kernel, picks a pod at random for each new connection. **Power of two choices** picks two backends at random and sends the request to the less busy one, which comes close to least connections without tracking every backend.
- **Hashing** maps a key, such as the client address or a cookie, to a backend, which keeps one client on one backend. This is a **sticky session**. It suits caches, and it hides a design problem when a backend keeps user state only in its own memory.

### Health Checks

A balancer must stop sending traffic to a backend that cannot answer. An **active health check** sends a request on a schedule, such as `GET /healthz` every 5 seconds, and counts the results. A backend leaves the pool after a number of failures in a row, the **unhealthy threshold**, and rejoins after a number of successes in a row, the **healthy threshold**. Two thresholds stop one slow answer from flapping a backend in and out. A **passive health check** watches real traffic instead: nginx marks a server unavailable for `fail_timeout`, 10 seconds by default, after `max_fails` failed attempts, one by default.

Kubernetes splits the job. The **kubelet**, the agent on each node that starts and watches its pods, runs the **readiness probe** of every pod, and a pod that fails it leaves the **endpoints** of its Service: the list of pod addresses behind the Service name. kube-proxy and Traefik watch that list and stop sending new connections and requests to the pod. The balancers in the cluster run no health checks of their own.

### Draining

A backend that leaves the pool on purpose, for a deploy or a scale-down, still has requests in flight. **Draining** stops new traffic to it and gives the open requests time to finish before the process exits. Without it, every deploy cuts off the requests that happen to be running and the clients see `502 Bad Gateway`.

### ServiceLB and Cloud Load Balancers

Kubernetes defines the Service type `LoadBalancer` but leaves the implementation to the platform. On a cloud, the cloud controller creates a load balancer with an address of its own, which survives the loss of any node. It health-checks the nodes, spreads connections over nodes in several availability zones, and costs a monthly fee plus traffic.

**ServiceLB**, the k3s implementation, creates no new machine and no new address. For each `LoadBalancer` Service, it starts a DaemonSet, one pod per node, whose pods hold the Service ports on the node itself through a `hostPort`. The Service gets the node addresses as its external addresses, and the pods forward incoming traffic to the Service. Your Domain Name System (DNS) record points at the VPS, and the balancing between pods happens behind it, in Traefik and kube-proxy.

| | ServiceLB on k3s | Cloud load balancer |
| --- | --- | --- |
| Address | The address of each node | Its own, stable address |
| A node fails | Its address stops answering | Traffic moves to the other nodes |
| Health checks | None: the node answers or not | Checks every node on a schedule |
| Cost | Nothing extra | A monthly fee plus traffic |
| Fits | One node, or a few with DNS in front | Clusters that must survive a node loss |

On your own hardware with several nodes, **MetalLB** fills the gap: it hands a Service a virtual address from a range you own and announces that address to your network from a healthy node.

## Common Mistakes

- **A health check that checks too much.** A `/healthz` that queries Postgres fails on every backend at once when the database is slow, and the balancer empties the whole pool. Users get `503` from the balancer instead of a slow answer from the api. Check what the backend itself needs to serve, and watch shared dependencies with alerts instead.
- **A health check that checks too little.** A `/healthz` that answers while the work loop hangs keeps a broken backend in the pool. Week 15 makes `/healthz` report whether the loop has made a pass recently.
- **No draining.** A pod that exits on `SIGTERM` while the endpoints still list it cuts off requests in flight and receives new ones for a moment. Users see `502`. Pause in a `preStop` hook, then finish open requests before exiting.
- **Trusting `X-Forwarded-For` from anyone.** A client can send the header with any address in it. Trust only the entries your own proxies append, from the right end of the list.
- **Idle timeouts in the wrong order.** When the backend closes idle keep-alive connections sooner than the balancer does, the balancer sends a request down a connection the backend just closed and returns `502`. Set the backend idle timeout longer than the balancer idle timeout.
- **State in one backend.** Sessions, caches or rate limit counters kept in the memory of one pod disappear when it restarts and differ between pods. Keep shared state in Postgres or another shared store, or accept the difference on purpose, as the per-pod rate limit of Week 17 does.

## Going Deeper

- **Consistent hashing.** It moves only a small share of keys when a backend joins or leaves, which matters for caches and for sharded data. Google Maglev is a well-known design.
- **Client-side load balancing.** gRPC clients and service meshes such as Linkerd pick a backend themselves from a list of endpoints, which removes the extra hop and balances long-lived HTTP/2 connections per request.
- **Gateway API.** The successor to the Kubernetes Ingress object, with separate objects for cluster operators and app teams, and routes for gRPC as well as HTTP. Traefik 3 in k3s supports it once you turn it on in a `HelmChartConfig`.
- **Global load balancing.** DNS answers that differ by region and anycast addresses, which many sites announce at once, spread users across data centers before any connection opens.
- **The PROXY protocol.** A layer 4 balancer can prepend the original client address to the connection, which keeps it intact without HTTP headers.
