You already design tests: equivalence classes, boundary values, regression suites. This page covers the decisions that change when you write the code as well as the tests: which level a test belongs at, which test double to reach for, how tests drive the design, and how to keep a suite fast and trustworthy as the backend grows.

## What It Is

### What a Test Proves

An automated test is an executable example: given this input, the code produces that output. Its value lies in its failure. A test that passes whatever the code does proves nothing, and a test that fails when nothing is broken trains everyone to ignore it.

Two questions check any test:

- **Does it fail when the behavior breaks?** Break the code on purpose, the way a bug breaks it, and watch the test fail. The examples in the Building tracks pass that check: each page names the change that makes its test fail. Tools that make such changes automatically and count the tests that catch them do **mutation testing**.
- **Does it pass whenever the behavior is right?** A test that depends on timing, test order, the network or the current date fails at random. Such a test is **flaky**, and one flaky test makes every red build suspect.

### The Test Pyramid

Tests come in levels, by how much of the system each one runs:

- A **unit test** calls one function or type with plain data. It runs in microseconds to milliseconds, and a failure points at a few lines.
- An **integration test** runs your code against a real dependency: Postgres, an HTTP server on `127.0.0.1`, the file system. It runs in milliseconds to seconds, and it catches what a unit test cannot, such as a typo in a SQL column name.
- An **end-to-end test** runs the whole app the way a user does, in a real browser. It runs in seconds, it breaks for many reasons, and it proves that the parts fit.

The **test pyramid** says to write many unit tests, fewer integration tests and a handful of end-to-end tests, because cost and flakiness grow toward the top. The [first diagram](#test-pyramid) shows the shape with the tests of the uptime monitor. Some teams draw a **testing trophy** instead, with the widest band at integration, because modern tools make integration tests nearly as fast as unit tests. Both shapes agree on the top: keep end-to-end tests for the flows a user cannot live without.

### Test Doubles: Fakes, Stubs, Spies and Mocks

A **test double** stands in for a real dependency during a test, as a stunt double stands in for an actor. The names come from Gerard Meszaros and his book xUnit Test Patterns, and each kind answers a different need:

| Double | What it does | Example |
| --- | --- | --- |
| Stub | Returns canned answers, and records nothing | A `fetch` that always answers `401` |
| Spy | Records how the code called it, for the test to check afterward | `spyBody` in Week 2, a response body that records whether the code closed it |
| Mock | Comes with expectations set up front, and fails the test when the calls differ | A generated mock of `Store` that expects one call to `Create` |
| Fake | A working, simpler implementation of the real thing | `MemStore` in Week 7, a map behind the `Store` interface |
| Dummy | Fills a parameter that the code under test never uses | A `nil` logger in a test that never logs |

A test with a stub or a fake checks the **state** after the call: what the function returned, what the store holds. A test with a mock checks the **interactions**: which methods the code called, in which order. Interaction checks couple a test to how the code works instead of what it does, and a harmless refactor that calls `Get` before `Create` breaks them. Prefer a fake or a stub, and use a real dependency where it is cheap, such as Postgres in a container. Go has no mocking library in its standard library, and a hand-written fake takes a struct and a few methods.

### Table-Driven Tests

A **table-driven test** lists cases as rows, and one loop runs the same checks on every row. Go writes it as a slice of structs with `t.Run` per row. Vitest and Jest write it as `it.each`. The table reads like the test design you already do: one row per equivalence class, plus a row at each boundary. A new case is one new line, and a failure names its row.

### Red, Green and Refactor

**Test-driven development**, or TDD, writes the test before the code, in a short loop:

1. **Red**: write one failing test for the next small behavior, and run it to see it fail for the reason you expect.
2. **Green**: write the least code that makes it pass.
3. **Refactor**: improve the code and the tests while every test stays green.

Seeing the test fail first proves that it can fail, which answers the first question about any test. The loop also keeps each step small enough that a red test points straight at the change you just made. The [second diagram](#red-green-refactor) walks the loop through two rows of the example.

### Tests Against Real Dependencies

A fake store tests the HTTP layer. Only a real Postgres tests the SQL. The database tests in the monitor create an empty **schema**, a namespace for tables, per test, and drop it at the end, which keeps parallel tests apart. They read the connection string from `DATABASE_URL`. Without it, they skip on a laptop, which keeps `go test ./...` usable without Docker, and they fail in continuous integration (CI), where `CI=true`: a database test that skips in CI tests nothing. The <TrackLink slug="databases" anchor="example">Databases track</TrackLink> shows one such test.

### Flaky Tests and Their Causes

Each flaky test has a cause you can name:

- **Wall-clock timing.** A `sleep` of 100 ms that waits for a goroutine passes on an idle laptop and fails on a CI runner busy enough to delay that goroutine past 100 ms. Wait on a channel or an event, or replace the clock: the <TrackLink slug="system-design" anchor="example">System and Software Design track</TrackLink> swaps its `sleep` function in tests.
- **Shared state.** Two tests that use the same table, file or global variable pass alone and fail together. Give each test its own schema, temporary directory or instance, and clean up with `t.Cleanup` or `afterEach`.
- **Order.** A test that only passes after another one has run hides a dependency. `go test -shuffle=on` runs the tests of a package in random order.
- **The outside world.** A test that calls a real website fails when the website or the network does. Start a local server with `httptest`, or intercept requests with `page.route` in Playwright.
- **Data races.** Two goroutines that touch the same memory produce a different result on some runs. `go test -race` finds them.

### Coverage

**Coverage** measures which lines a test run executes: `go test -cover` prints a percentage per package, and Vitest reports it with a coverage provider package. Coverage tells you what no test runs, which is useful. It does not tell you what any test checks: a test that calls a function and asserts nothing covers every line of it. Read the uncovered lines, and do not chase a number.

Three decisions in that code come from test rows:

- **Null is not zero.** A monitor with no checks has no uptime, and `0.00%` claims it is always down. `uptimePercent` returns `null` for an empty list, and `formatUptime` turns it into `no data`.
- **One rounding step.** `29 / 100 * 100` is `28.999999999999996` in JavaScript, because `0.29` has no exact binary form and the multiplication rounds a second time. `29 * 100 / 100` rounds once and gives `29`.
- **No false perfect record.** `toFixed(2)` rounds `99.999` to `100.00`. The guard shows `99.99%` for any value under 100.

The tests are one `it.each` table. Each row holds the input counts, the expected number and the expected text, and `$ok of $total checks up gives $text` names each row from its own fields:

<CodeFrom file="web/src/tracks/testing/uptime.test.ts" region="tests" lang="ts" title="uptime.test.ts" />

The rows cover the classes and the boundaries: no data, all up, all down, a fraction that repeats, a value that floating point gets wrong, and the edge just under 100. `toBe` compares with `Object.is`, which is exact: it passes for `29` and fails for `28.999999999999996`. For a result that floating point cannot hit exactly, such as `2 / 3`, the row holds the exact double that a single division produces, `66.66666666666667`. Swap the formula back to `up / results.length * 100`, and three rows fail: two of three, 29 of 100, and 99,999 of 100,000. Remove the guard in `formatUptime`, and the last row fails with `Received: "100.00%"`.

## Common Mistakes

- **A test that cannot fail.** No assertion, an assertion on the mock itself, or an `expect` inside a callback that the code never calls. `expect.assertions(1)` in Vitest fails a test whose assertion never runs. Break the code once, and watch the test go red.
- **Waiting with sleep.** A fixed sleep is too short on a busy runner and wastes time everywhere else. Wait for the event itself, or inject the clock or the sleep function.
- **Mocking every call.** A test that checks which methods the code calls breaks on every refactor and passes when the result is wrong. Check the result and the state, with a fake or a real dependency.
- **Tests that share state.** One test leaves a row, a file or a global behind, and another one fails only after it. Give each test its own data, and clean up in `t.Cleanup` or `afterEach`.
- **Exact comparison after float arithmetic.** `0.1 + 0.2` is `0.30000000000000004`, and `toBe(0.3)` fails. Restructure the arithmetic, or compare with `toBeCloseTo`.
- **A dependency test that skips in CI.** The suite stays green while it tests nothing. Fail when `CI=true` and the dependency is missing.
- **Everything end-to-end.** A suite of browser tests takes minutes, fails for reasons unrelated to the change, and points at nothing. Push each case down to the lowest level that can catch it.
- **Coverage as the goal.** A team told to reach 90% writes tests that run code without checking it. Use coverage to find untested code, not to grade tests.

## Going Deeper

- **Fuzzing**: `go test -fuzz` feeds generated inputs to a function and saves every input that makes it fail, which finds the boundaries you did not think of.
- **Property-based testing**: instead of rows, you state a rule that holds for every input, such as uptime staying between 0 and 100, and a library such as fast-check searches for a counterexample.
- **Mutation testing**: Stryker for TypeScript changes your code automatically and reports every change that no test notices.
- **Contract testing**: a consumer records the requests it makes and the answers it expects, and the provider runs that record in its own CI, which catches a breaking API change before deploy.
- **Testcontainers**: a library that starts a real Postgres or a real broker in a container for each test run, from inside the test code.
- **Load testing**: a tool such as k6 sends traffic at a set rate, which finds the slow query that no functional test shows.
