At the end of <a href={weekHref(2)}>Week 2</a>, `your-monitor` checks a list of URLs once and exits. A monitor has to keep watching. This week, you turn it into a **long-running process**: a program that starts once, checks every URL again at a fixed interval, writes one log line per check, and shuts down cleanly when asked.

To run a program like that, you need to know what Linux keeps for every running program and how to look at it. You learn processes, file descriptors, environment variables, users and signals, then hand your monitor to systemd, the program that starts and stops services on Ubuntu and most other Linux systems. The <a href={trackHref('operating-systems')}>Operating Systems track</a> goes deeper on each idea.

## Goals

## Concepts

### Where to Run the Commands

### Processes, PIDs and Parents

The **kernel** is the core of the operating system: it runs programs, hands out memory and talks to the hardware. A **process** is one running copy of a program, together with everything the kernel tracks for it. Every process has a number, its **process ID** or PID.

Every process also has a **parent**: the process that started it. A Linux process starts a program in two steps. It calls **fork**, which makes a copy of itself, the child. The child then calls **exec**, which replaces its own program with the new one. The child keeps what it copied from the parent: the environment variables, the current folder, the user and the open files. That is why your monitor prints to your terminal: it inherits the terminal from your shell. The first process, PID 1, starts everything else. On Ubuntu, PID 1 is systemd. When a parent exits before its child, the child becomes an **orphan**, and PID 1 adopts it.

`ps` lists processes. `pgrep -x your-monitor` prints the PID of every process named exactly `your-monitor`. Pass that PID to `ps` and pick the columns:

```txt
$ ps -o pid,ppid,user,stat,etime,rss,args -p 2107
    PID    PPID USER     STAT     ELAPSED   RSS COMMAND
   2107    2050 casey    Sl+        02:13  7952 ./your-monitor -file urls.txt -interval 10s
```

- `PPID`: the parent PID, here bash.
- `STAT`: the state. `S` means sleeping: the process waits for a timer or the network, which is where a monitor spends nearly all its time. `R` means running. `l` marks a process with several threads, which every Go program has. `+` marks the foreground program of a terminal.
- `ELAPSED`: the time since the process started.
- `RSS`: resident set size, the memory the process holds right now, in KiB.

`ps -ef` lists every process on the machine. `top` shows the busiest processes and refreshes every three seconds. `top -p 2107` watches one. Press `q` to quit. `htop` is a friendlier version with a tree view on the **F5** key: install it with `sudo apt install htop`.

### What the Kernel Keeps for Each Process

`/proc` is a folder that the kernel generates as you read it: nothing in it is on disk. Each running process has a folder named after its PID. `ps` and `top` read their numbers from here, and you can read them directly:

| Path | What it holds |
| --- | --- |
| `/proc/<pid>/cmdline` | the command line, with a zero byte between arguments |
| `/proc/<pid>/status` | the name, state, parent PID, user IDs, thread count and memory |
| `/proc/<pid>/environ` | the environment variables the process started with |
| `/proc/<pid>/cwd` and `/proc/<pid>/exe` | links to the current folder and to the binary |
| `/proc/<pid>/fd/` | one link per open file descriptor |
| `/proc/<pid>/limits` | the limits on the process, such as `Max open files` |

### Standard Streams and File Descriptors

A **file descriptor**, or fd, is a small number a process uses to refer to something it has open. The kernel keeps a table of them for each process. An fd points at a file, a terminal, a pipe between two programs, or a **socket**: one end of a network connection.

Every process starts with three: `0` is stdin, where it reads input, `1` is stdout, where it writes its results, and `2` is stderr, where it writes messages about itself, as Week 1 showed. Your shell sets these up before it execs a program. A redirect changes where one of them points:

| You type | What the shell does before it starts the command |
| --- | --- |
| `cmd > out.log` | points fd `1` at `out.log`, emptying the file first |
| `cmd >> out.log` | points fd `1` at `out.log`, and writes go to its end |
| `cmd 2> err.log` | points fd `2` at `err.log` |
| `cmd > all.log 2>&1` | points fd `1` at `all.log`, then fd `2` at wherever fd `1` points |
| `cmd < in.txt` | points fd `0` at `in.txt` |

The order matters: `cmd 2>&1 > all.log` points stderr at the terminal, because fd `1` still points there when the shell copies it. A pipe, `cmd1 | cmd2`, connects fd `1` of the first command to fd `0` of the second.

Every network connection your monitor opens takes one fd until it closes. A process can hold a limited number of fds, set on the `Max open files` line of `/proc/<pid>/limits`. Once a process reaches it, opening one more file or connection fails with `too many open files`.

That limit is why Week 1 and Week 2 insist on `defer resp.Body.Close()`. The Go HTTP client keeps the connection under a response open for as long as you can still read the body. Close the body, and Go gives the connection back for reuse or closes it. Forget, and each check holds one more socket. A one-shot CLI exits before that matters, because the kernel closes every fd of a process when it exits. A monitor that runs for weeks keeps them. [Operate It](#operate-it) shows the leak.

`lsof -p <pid>` lists the open files of a process, with the type of each one and, for a socket, both addresses and the TCP state.

### Environment Variables

An **environment variable** is a `NAME=value` pair that a process carries. A child gets a copy of the environment of its parent when it starts. Changes in the child never reach the parent.

`env` prints the environment of your shell. `export NAME=value` sets a variable for the shell and every program it starts afterward. `NAME=value ./your-monitor` sets it for that one command only. In Go, `os.Getenv("NAME")` reads one. The Go `time` package reads `TZ` to pick the time zone, and the `log` package prints local time: `TZ=UTC ./your-monitor -file urls.txt` logs in UTC, whatever zone your machine uses. A service under systemd does not inherit your shell environment. It starts with a small one of its own, and the unit file adds variables with `Environment=`.

### Users and Permissions

Every process runs as a user, identified by a number, the UID. `root` is UID `0` and passes every permission check. `id` prints your own user and groups.

Every file has an owner, a group and three sets of permissions. `ls -l` shows them:

```txt
-rw-r----- 1 root your-monitor 64 Oct 11 14:00 /etc/your-monitor/urls.txt
```

The first character is the type: `-` for a file, `d` for a folder. Then come three groups of three: `rw-` for the owner `root`, `r--` for the group `your-monitor`, and `---` for everyone else. `r` is read, `w` is write, and `x` is execute, or enter for a folder. `chmod 640 urls.txt` sets the three groups as digits, adding 4 for read, 2 for write and 1 for execute. `chown root:your-monitor urls.txt` sets the owner and the group. `sudo` runs one command as `root`.

A service runs as its own user with only the permissions it needs. When a bug or an attacker takes over your monitor, they get its user: it can read its URL file and nothing of yours, such as your SSH keys.

### Signals

A **signal** is a short notice that the kernel delivers to a process: a number with a name. A process can install a handler that catches most signals and decides what to do. A signal with no handler gets its default action, and for the four below, the default action ends the process.

| Signal | Number | Sent by | What it means for a service |
| --- | --- | --- | --- |
| SIGINT | `2` | Ctrl+C in a terminal | The person at the terminal wants it to stop. |
| SIGTERM | `15` | `kill <pid>`, `systemctl stop`, `docker stop`, Kubernetes | Shut down cleanly: finish or drop the current work, then exit. |
| SIGKILL | `9` | `kill -9 <pid>`, systemd after its stop timeout, the kernel when memory runs out | The process ends at once. Nothing can catch, block or ignore SIGKILL. |
| SIGHUP | `1` | the terminal closing | Hang up: the terminal is gone. Many servers, such as nginx, reload their configuration on SIGHUP instead. |

`kill` sends any signal, not only SIGKILL. `kill 2107` sends SIGTERM. `kill -INT 2107`, `kill -HUP 2107` and `kill -9 2107` send the others. `kill -l` lists every signal with its number. When a signal ends a process, the shell reports exit status 128 plus the signal number: `130` after Ctrl+C, `143` after SIGTERM, `137` after SIGKILL and `129` after SIGHUP. A process that catches the signal and exits on its own picks its exit code, as your monitor does with `0`. The pattern of SIGTERM first and SIGKILL later is the same everywhere. `docker stop` waits 10 seconds before SIGKILL. Kubernetes waits 30 seconds by default. systemd waits 90 seconds by default.

### Service Managers

A **service** is a long-running process that the machine runs with no person at a terminal. Something has to start it at boot, restart it when it fails, collect its output and stop it at shutdown. That program is a **service manager**. On Ubuntu, the service manager is systemd, PID 1. Kubernetes plays the same role for containers in <a href={weekHref(15)}>Week 15</a>.

You describe a service to systemd in a **unit file**: a short text file of `Key=value` lines in sections, kept in `/etc/systemd/system`. `systemctl` sends commands to systemd: `start`, `stop`, `restart`, `status`, and `enable` to start the service at every boot.

systemd connects stdout and stderr of a service to the **journal**, its log store, and `journalctl` reads it. That is why your monitor logs to stdout: it needs no log file, no file path and no code to rotate old logs. Docker and Kubernetes collect stdout the same way.

### The Files a Service Touches

A service on Linux reads and writes in a few standard places. The <a href={trackHref('storage')}>Storage track</a> covers disks and filesystems in depth.

| Path | What goes there |
| --- | --- |
| `/usr/local/bin` | programs you install by hand, such as your monitor |
| `/etc/your-monitor` | configuration for one program, such as `urls.txt` |
| `/etc/systemd/system` | unit files you write |
| `/var/log/journal` | the journal. On Ubuntu, it survives a reboot. |
| `/tmp` | scratch files. Ubuntu empties it at every boot. |

### Step 2: Check the List Again Every Interval

<CodeFrom file="go/week03/your-monitor/main.go" region="run" lang="go" title="main.go" />

`time.NewTicker(interval)` starts a **ticker**: it sends the current time on its channel, `ticker.C`, once per interval. A **channel** is a pipe between parts of a Go program, and `<-ticker.C` waits until a value arrives. <a href={weekHref(5)}>Week 5</a> covers channels in depth. `defer ticker.Stop()` releases the ticker when `run` returns.

`select` waits on several channels and runs the case of whichever is ready first. Here, it waits for either the next tick or `ctx.Done()`, the channel that closes when the context is cancelled. A signal that arrives between rounds ends the wait at once.

When a round takes longer than the interval, the ticker drops the ticks it missed, and the next round starts as soon as the last one ends. In a test run for this page, one URL that took 3 seconds to answer, checked with `-interval 2s`, gave a round every 3 seconds.

### Step 3: Shut Down on SIGTERM and SIGINT

Two lines in `main` do the signal handling: the call to `signal.NotifyContext` and `defer stop()`. `signal.NotifyContext` returns a context that it cancels when SIGINT or SIGTERM arrives. While it is registered, the Go runtime catches those two signals instead of applying the default action: the process keeps running, and your code decides when to exit. `stop` removes the handler, and `defer stop()` calls it when `main` returns.

A **context**, from the `context` package, carries a cancellation signal through a program. Week 4 adds deadlines to it. Code that holds a context checks it in two ways. `ctx.Err()` returns `nil` until the context is cancelled, which suits a check between steps. `ctx.Done()` returns a channel that closes on cancellation, which suits a `select`.

`run` checks `ctx.Err()` before each check, not during one. `check.URL` takes no context, which leaves a check in flight to run to its end: at most the `-timeout` of 5 seconds. The rest of that round is skipped and logged. `run` returns, `main` logs `stopped` and returns, and the exit code is `0`. Never call `os.Exit` on this path: it ends the process at once and skips every deferred call. <a href={weekHref(4)}>Week 4</a> passes the context into each check, which cancels the check in flight too.

- `[Unit]`: `Description` names the service in `systemctl status` and the journal. `After` and `Wants` start it once the network is up.
- `ExecStart`: the command, with an absolute path to the binary. `User` and `Group`: the user the process runs as, which you create in Step 8.
- `Restart=on-failure` and `RestartSec=5s`: start the process again 5 seconds after it fails, which means a non-zero exit code, a signal such as SIGKILL, or a timeout. `systemctl stop` does not count as a failure.
- `[Install]`: `WantedBy=multi-user.target` makes `systemctl enable` start the service at every boot.

The unit sets no stop options, which leaves the defaults: SIGTERM, then SIGKILL after 90 seconds.

### Step 8: Run It as a Service

On an Ubuntu machine with systemd, or in the Multipass VM after `cd ~/your-monitor`, install the files. On a Mac, use `your-monitor-linux` in place of `your-monitor` in the second command.

```sh
sudo useradd --system --no-create-home --shell /usr/sbin/nologin your-monitor
sudo install -m 755 your-monitor /usr/local/bin/your-monitor
sudo install -d -m 755 /etc/your-monitor
sudo install -m 640 -o root -g your-monitor urls.txt /etc/your-monitor/urls.txt
sudo cp your-monitor.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now your-monitor
```

`useradd --system` creates a user for a service, with no home folder and no login shell, and a group of the same name. `install` copies a file and sets its mode, owner and group in one command, and `-d` creates a folder instead. The URL file gets mode `640`: `root` can write it, and the `your-monitor` group can only read it. `daemon-reload` makes systemd read the unit files again: run it after every change to a unit file. `enable --now` starts the service at every boot, and starts it now.

Check it. This is an example of the output, trimmed:

```txt
$ systemctl status your-monitor
● your-monitor.service - your-monitor uptime checks
     Loaded: loaded (/etc/systemd/system/your-monitor.service; enabled; preset: enabled)
     Active: active (running) since Sun 2026-10-11 14:30:02 UTC; 41s ago
   Main PID: 812 (your-monitor)
     CGroup: /system.slice/your-monitor.service
             └─812 /usr/local/bin/your-monitor -file /etc/your-monitor/urls.txt -interval 30s
```

Read the log with `journalctl -u your-monitor`. Add `-f` to follow new lines, `-n 20` for the last 20, or `--since "1 hour ago"`. The journal puts its own time, the host name and the PID before each line:

```txt
Oct 11 14:30:02 lab your-monitor[812]: 2026/10/11 14:30:02 started pid=812 urls=2 interval=30s
Oct 11 14:30:02 lab your-monitor[812]: 2026/10/11 14:30:02 up url=https://example.com status=200 latency_ms=121
```

Run `ps -o user,args -p 812` to see the process run as `your-monitor`, not as you. Then stop it with `sudo systemctl stop your-monitor`, and read the last lines of the journal:

```txt
Oct 11 14:35:10 lab systemd[1]: Stopping your-monitor.service - your-monitor uptime checks...
Oct 11 14:35:10 lab your-monitor[812]: 2026/10/11 14:35:10 stopped
Oct 11 14:35:10 lab systemd[1]: your-monitor.service: Deactivated successfully.
Oct 11 14:35:10 lab systemd[1]: Stopped your-monitor.service - your-monitor uptime checks.
```

The `stopped` line is the proof that your handler ran. systemd counts an exit caused by SIGTERM as a clean stop too: a program without a handler also shows `Deactivated successfully`. Start the service again with `sudo systemctl start your-monitor`.

## Observe It

<ObserveIt>

A service that runs for weeks fails slowly: a few more open files each hour, a few more megabytes. Measure the process itself, not only the sites it checks. **Count its file descriptors and memory.** With the service running, record both numbers every 10 minutes for an hour:

```sh
pid=$(systemctl show -p MainPID --value your-monitor)
ls /proc/$pid/fd | wc -l
ps -o rss= -p $pid
```

`systemctl show -p MainPID --value` prints the PID alone. In a healthy monitor, both numbers rise during the first rounds and then stay flat. A count that climbs by one per check is a leak, as in Operate It.

**Read the rounds from the log.** Each round starts one interval after the one before. A gap between rounds longer than the interval means a round took longer than the interval: as in Week 2, one slow site holds up every URL after it. Count the failures in the last hour:

```sh
journalctl -u your-monitor --since "1 hour ago" | grep -c ' down '
```

</ObserveIt>

## Operate It

<OperateIt>

**SIGKILL.** Run the monitor in a terminal, and send SIGKILL from another one with `kill -9 <pid>`:

```txt
2026/10/11 14:40:12 up url=http://127.0.0.1:8000/ status=200 latency_ms=1
Killed
$ echo $?
137
```

`Killed` comes from bash. The exit status is `137`: 128 plus 9. The log stops after the last check, with no `shutting down` line and no `stopped` line. The kernel ends the process without running any of its code: no handler, no deferred calls, no rest of the check in flight. The kernel still closes every fd and frees all memory of the process, which means a leak never outlives it. For your monitor, SIGKILL loses one check and nothing else, because it keeps no state. From <a href={weekHref(8)}>Week 8</a>, the monitor writes to Postgres, and a process that ends mid-write leaves work half done. That is why databases use transactions, and why a service gets SIGTERM and time to finish before SIGKILL.

Under systemd, send it with `sudo systemctl kill --signal=SIGKILL your-monitor`. The journal records the failure, and `Restart=on-failure` brings the process back after 5 seconds with a new PID:

```txt
your-monitor.service: Main process exited, code=killed, status=9/KILL
your-monitor.service: Failed with result 'signal'.
your-monitor.service: Scheduled restart job, restart counter is at 1.
```

**A shutdown slower than the stop timeout.** `systemctl stop` waits 90 seconds before SIGKILL, and your shutdown waits for at most one check, the 5-second `-timeout`. Keep `-timeout` well under the stop timeout. To see what happens when it is not, run `nc -l 8080` in the VM as a site that never answers, and put `http://127.0.0.1:8080/` on the first line of `/etc/your-monitor/urls.txt`. In `/etc/systemd/system/your-monitor.service`, add `-timeout 60s` to `ExecStart` and `TimeoutStopSec=3s` to the `[Service]` section. Run `sudo systemctl daemon-reload`, restart the service, and stop it during the check. The journal shows `State 'stop-sigterm' timed out. Killing.`, the SIGKILL, and `Failed with result 'timeout'`. Undo all three changes.

**A file descriptor leak.** Comment out `defer resp.Body.Close()` in `check/check.go` and build. In one terminal, start a site that keeps connections open: `python3 -m http.server 8002 -p HTTP/1.1`. In another, check it every second with no timeout:

```sh
echo http://127.0.0.1:8002/ > leak.txt
./your-monitor -file leak.txt -interval 1s -timeout 0
```

In a third terminal, run `ls /proc/$(pgrep -x your-monitor)/fd | wc -l` every few seconds. In a test run for this page, the count went 7, 8, 9, 10, 11 and on, one more per check, and `lsof -p` listed a TCP connection in state `ESTABLISHED` for every check so far. Stop the monitor, lower the limit for this shell with `ulimit -n 16`, and start it again. After 11 checks, a site that is up shows as down:

```txt
2026/10/11 14:52:53 down url=http://127.0.0.1:8002/ latency_ms=0 error="Get \"http://127.0.0.1:8002/\": dial tcp 127.0.0.1:8002: socket: too many open files"
```

Close that shell, open a new one, and run the leaky build with the default `-timeout 5s`. The count stops near 10: an `http.Client` with a `Timeout` cancels the request when the timeout runs out, and that closes the connection under an unread body. The timeout hides the leak at one check per second, and a monitor with many URLs still holds one socket per check for 5 seconds. Put the `defer` back. Without it, `go test ./check` fails, through the spy body from Week 2.

**A permission mistake.** Run `sudo chmod 600 /etc/your-monitor/urls.txt`, then `sudo systemctl restart your-monitor`. The monitor runs as `your-monitor`, which can no longer read the file. The journal shows `open /etc/your-monitor/urls.txt: permission denied`, then `Main process exited, code=exited, status=2/INVALIDARGUMENT`. systemd restarts it every 5 seconds, and it fails every time, with `activating (auto-restart)` in `systemctl status`. Run `sudo chmod 640 /etc/your-monitor/urls.txt` to fix it.

</OperateIt>

## Side Lab

<SideLab title="Make an orphan and a zombie, and watch who cleans up">

When a process exits, the kernel keeps its exit code until the parent reads it with a system call named **wait**. Until then, the dead process is a **zombie**: it holds no memory and no files, only its PID and its exit code. Run this lab on Ubuntu or in the Multipass VM, where systemd is PID 1.

**1. Make an orphan.** Start a `sleep` in the background from a shell that exits at once:

```txt
$ bash -c 'sleep 300 > /dev/null & echo $!'
23293
$ ps -o pid,ppid,stat,args -p 23293
    PID    PPID STAT COMMAND
  23293       1 S    sleep 300
```

The parent bash is gone, and PID 1 adopts the child. On an Ubuntu desktop, a `systemd --user` process adopts it instead.

**2. Make a zombie.** In the next command, a subshell starts `sleep 1` in the background, then replaces itself with `sleep 60` through `exec`. The new program never calls wait, and the `sleep 1` child stays a zombie after it exits:

```txt
$ (sleep 1 & exec sleep 60) &
[1] 23114
$ sleep 2; ps -o pid,ppid,stat,args --ppid $!
    PID    PPID STAT COMMAND
  23116   23114 Z    [sleep] <defunct>
```

`Z` and `<defunct>` mark the zombie. `kill -9 23116` changes nothing: the process has already exited.

**3. Clean up.** Send SIGTERM to the parent with `kill $!`, then run `ps -p 23116`. The zombie is gone: PID 1 adopts it and calls wait at once.

A service that starts child processes must wait for each one, or zombies pile up and hold PIDs. In a container that starts your program as its first process, your program is PID 1 and inherits that job. `docker run --init` starts a small init program as PID 1 to do it instead.

</SideLab>
