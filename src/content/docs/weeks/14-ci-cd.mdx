## Concepts

### CI and CD

**Continuous integration** (CI) means two habits: everyone merges small changes into `main` at least once a day, and a machine runs the checks on every change before it merges. The machine is the point. It runs every check, every time, on a clean computer, and it shows the result on the pull request for every reviewer to see.

**Continuous delivery** (CD) adds one step: every commit that passes the checks produces something you can deploy, here a container image for each program. **Continuous deployment** goes one step further and deploys each such commit automatically. This course does the first two automatically and keeps deployment a button you press, because a deploy to your one small server is an event you want to watch.

### The Parts of GitHub Actions

GitHub Actions is the CI service built into GitHub. Its vocabulary:

- A **workflow** is a YAML file in `.github/workflows/`. GitHub reads every file there.
- An **event** starts a workflow: `pull_request` when a pull request opens or gets a new commit, `push` when commits reach a branch, `workflow_dispatch` when you press **Run workflow**.
- A **job** is a list of steps that runs on one runner. Jobs of one workflow run side by side, unless `needs:` makes one wait for others.
- A **runner** is the machine that runs a job. A GitHub-hosted runner is a fresh virtual machine, created for the job and deleted after it. Nothing on its disk survives into the next job.
- A **step** either runs a shell script, with `run:`, or calls an **action** with `uses:`: a packaged step that someone publishes in a Git repository, such as `actions/checkout`, which clones your repository onto the runner.
- An **expression** such as `${{ github.sha }}` reads a value from a **context**: `github` describes the event and the commit, `secrets` holds secrets, `matrix` holds the current matrix values. GitHub replaces each expression with its value before the step starts.

### Tokens, Permissions and Secrets

Every job gets a **`GITHUB_TOKEN`**: a password for the GitHub API that GitHub creates when the job starts and revokes when it ends. The `permissions:` key sets what the token can do. As soon as a workflow names one permission, every permission it does not name is `none`. Your CI grants `contents: read` to every job, and adds `packages: write` to the images job alone. A test dependency that turns hostile finds a token that cannot push a commit, a tag or an image.

**Secrets** are values you store in the repository settings, such as the kubeconfig for your cluster. A workflow reads them as `${{ secrets.NAME }}`, and GitHub masks their values in the logs. Two rules protect them from strangers. A pull request from a **fork**, a copy of your repository in another account, runs with a read-only token and without your secrets. A secret stored in an **environment**, a named target such as `production`, reaches only the jobs that declare that environment.

### Pin Actions to a Commit

`uses: actions/checkout@v7` looks fixed, but `v7` is a Git **tag**, and the owner of a repository can move a tag to any commit. Whoever controls the action repository, or has stolen the credentials of someone who does, can point `v7` at new code, and your next run executes that code with your token and your secrets. In March 2025, an attacker did exactly that to the `tj-actions/changed-files` action: every tag pointed at a commit that printed the secrets of each run into its log. Workflows pinned to a commit SHA kept running the old code.

A **commit SHA** is the 40-character hexadecimal hash that Git computes from the content of a commit. Change one byte, and the SHA changes. `uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1` therefore names one exact version of the action, forever. GitHub documents a full-length SHA as the only way to use an action as an immutable release. Two costs come with it:

- You no longer receive fixes on your own. Dependabot, the GitHub bot that proposes dependency updates, opens a pull request for each new release and updates the SHA and the comment together.
- A SHA tells a human nothing. The comment after it, `# v7.0.1`, names the release, and Dependabot reads it too.

Read each SHA from the action repository yourself, and never copy one from a blog post or an AI answer. A SHA from a fork of the action also works in `uses:`, because GitHub serves the commits of a fork through the original repository. Only `git ls-remote` against the original repository proves that the commit is the release you mean.

### Images Tagged with the Commit

The images job tags each image with `${{ github.sha }}`, the full SHA of the commit that the workflow runs on. A tag such as `latest` moves with every build and says nothing about the code inside. A SHA tag answers three questions at once: which code an image holds, which image to deploy for a commit, and which image to roll back to. The **GitHub Container Registry**, GHCR at `ghcr.io`, stores the images next to your repository. The job logs in with its `GITHUB_TOKEN`, and GitHub links each package it pushes to the repository.

A **concurrency group** holds at most one running and one pending run. A new run cancels the pending one, and with `cancel-in-progress: true` it cancels the running one too. Each push to `main` therefore gets its run ID, a group no other run shares.

### Step 7: Read Every SHA Yourself

Each `uses:` line in the examples names a commit SHA and a release. Before you copy a line, check its SHA against the action repository. `git ls-remote --tags` lists tags and the commits they point at, straight from GitHub:


The input is the dangerous part. GitHub pastes every `${{ }}` expression into the script text before bash reads it. ```

`gh pr checks --watch` refreshes the list of checks until all of them finish. The pull request page shows the same list under **Checks**. The first run fills the caches and takes the longest.

Make the checks required. On GitHub, open **Settings**, then **Rules** and **Rulesets** in the sidebar, and click **New ruleset**, **New branch ruleset**. Name it `main`, set the enforcement status to **Active**, add the default branch as the target, select **Require status checks to pass before merging**, and add `lint`, `test`, `web` and `e2e`. Click **Create**. The check names exist once they have run, which is why the pull request comes first. On GitHub Free, rulesets work only in a public repository. In a private one, merge only on green by habit, or move to GitHub Pro.

Merge the pull request. The push to `main` starts `ci.yml` again, and this time the five `images` jobs run. Find the packages under **Packages** on your profile page, or on the right side of your repository page. Each one shows the SHA tag and links to your repository.

### Step 12: Break It on Purpose

On a new branch, change an expected value in one Go test, push, and open a pull request. The `test` job turns red. Read the failure from your terminal:

```sh
gh run list --workflow ci.yml --limit 3
gh run view <run-id> --log-failed
```

`--log-failed` prints only the steps that failed, with the `FAIL` line and the file and line number of the failing check. Fix the test, push again, and watch the run turn green. Close the pull request without merging.

## Observe It

<ObserveIt>

Your pipeline is a system of its own, and it deserves the same habits as the monitor.

**Measure how long a run takes.** A slow pipeline costs focus: when CI takes 20 minutes, you switch to other work and meet the red result an hour later. List the last runs on `main` with their start and end times:

```sh
gh run list --workflow ci.yml --branch main --limit 10 --json databaseId,conclusion,startedAt,updatedAt
```

`gh run view <run-id>` lists each job with its duration. Keep a pull request run under 10 minutes. When it grows past that, the slowest job tells you where to cut. In the examples, the `internal/auth` tests take the longest of the Go packages, because bcrypt is slow on purpose.

**Watch the caches.** In the log of the `setup-go` and `setup-node` steps, a cache hit prints a line that names the restored cache key. A run without a hit downloads every module again. The Docker cache shows up in the build log as `CACHED` next to each layer it reuses.

**Count flaky tests.** A **flaky** test passes and fails on the same code. When a job fails, rerun only the failed jobs with `gh run rerun <run-id> --failed`. If it passes, you found a flaky test: write down its name and fix it this week. A rerun that hides flakes trains everyone to ignore red.

**Read the summary.** The run summary page of every push to `main` lists the five images with their digests. That list answers which image runs which code, which Week 17 needs for its rollbacks.

</ObserveIt>

## Operate It

<OperateIt>

Here is how the common failures look, and what each one points to.

**The lint job fails, and `make lint` passes on your laptop.** CI and your laptop run different golangci-lint releases: each release adds checks. Compare `golangci-lint version` with `version:` in `ci.yml`, and make them match. When the binary is older than your Go, the job fails before it lints anything:

```txt
Error: can't load config: the Go language version (go1.25) used to build golangci-lint is lower than the targeted Go version (1.27.0)
```

Install a golangci-lint release built with your Go version or newer, and raise `version:` to match.

**The Go tests fail with `DATABASE_URL is not set; CI must provide a Postgres database`.** The `env:` block of the `test` job is missing or misspelled. The Week 8 helper fails on purpose when `CI=true`, rather than skipping every Postgres test and reporting green.

**The Go tests fail with `connection refused` on port `5432`.** The service container is not ready, or not published. Check `ports:` and the health options: without `--health-cmd`, GitHub starts the steps as soon as the container starts, before Postgres accepts connections.

**Playwright fails with `Executable doesn't exist at`.** The `npx playwright install` step is missing or runs in the wrong folder: the browsers must match the `@playwright/test` version in `web/package-lock.json`.

**The images job fails at the push with a `denied` error from `ghcr.io`.** The job token lacks `packages: write`, or a package with the same name already exists in your account and is linked to another repository. Check the `permissions:` of the job first, then the package settings on GitHub.

**The build fails with `repository name must be lowercase`.** An image name holds a capital letter: the name step is missing, or a tag uses `github.repository` directly.

**The deploy fails with `sha must be a full 40-character commit SHA`.** The input holds a short SHA or a branch name. `git rev-parse <short-sha>` prints the full one.

| What you see | What it points to |
| --- | --- |
| Lint fails in CI, passes locally | Different golangci-lint releases, or one built with an older Go |
| `DATABASE_URL is not set` | The `env:` of the test job is missing |
| `connection refused` on `5432` | The service has no published port or no health check |
| `Executable doesn't exist at` | Playwright browsers not installed in the job |
| `denied` from `ghcr.io` | No `packages: write`, or the package belongs to another repository |
| `repository name must be lowercase` | The image name skips the lowercase step |

</OperateIt>

## Side Lab

<SideLab title="Stop a broken push before CI sees it, with a Git pre-push hook">

A **Git hook** is a script that Git runs at a fixed point, such as before a commit or before a push. Hooks live in `.git/hooks/`, outside version control: each clone sets up its own. A hook that exits with a non-zero status cancels the operation.

**1. Write the hook.** In your repository, create `.git/hooks/pre-push`:

```sh
#!/bin/sh
# Runs before every git push. A non-zero exit cancels the push.
exec make lint
```

Make it executable:

```sh
chmod +x .git/hooks/pre-push
```

**2. Watch it stop a push.** On a new branch, such as `hook-test`, add a line that drops an error, such as `f.Write(b)` without checking what it returns, commit it and push. This run comes from a small test repository with your `.golangci.yml` and one such line:

```txt
$ git push -u origin hook-test
golangci-lint run
main.go:11:9: Error return value of `f.Write` is not checked (errcheck)
	f.Write([]byte("hello\n"))
	       ^
1 issues:
* errcheck: 1
make: *** [Makefile:2: lint] Error 1
error: failed to push some refs to '../remote.git'
```

Nothing reached the remote. Fix the line, and the push goes through.

**3. Compare the two gates.** `git push --no-verify` skips the hook. That is the difference between the two: a hook is a convenience on your laptop that anyone can skip or never install, while the required checks on GitHub apply to every merge. Use the hook to save yourself a red pull request, and the ruleset to protect `main`.

Write down how long `make lint` takes. A hook that holds every push for 30 seconds trains you to type `--no-verify`. When yours takes that long, keep the fast checks in the hook and leave the slow ones to CI.

</SideLab>
