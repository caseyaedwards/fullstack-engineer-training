At the end of <a href={weekHref(9)}>Week 9</a>, the monitor runs on its own: the scheduler queues checks, workers run them and store each result in Postgres, and the alerter opens an incident after three failures in a row. One request per monitor is the **N+1 pattern**: one request for the list, then one for each of its N items. It is simple, and each row loads and fails on its own. It also grows with every monitor you add. The fix is a route that returns the status of every monitor in one answer, shaped for this page. That trade-off, a general api against one shaped for each screen, comes up again in the <a href={trackHref('system-design')}>System and Software Design track</a>. For a status page with tens of monitors, the simple design is enough, and [Observe It](#observe-it) shows how to count the requests.

### State, Effects and Cancellation

A React component is a function from props and state to markup. React calls it to **render**, and calls it again each time its state changes. `useState` holds a value across renders. `useEffect` runs code after a render, for work that is not markup, such as a request. Its second argument, the **dependency array**, lists the values the effect reads: React runs the effect again when one of them changes. The function the effect returns is its **cleanup**: React runs it before the next run of the effect, and when the component leaves the page, which React calls **unmounting**.

A request outlives the component that sent it. When the answer arrives after the component unmounted, nothing needs it. Worse, an old answer can overwrite a newer one. `AbortController` cancels a `fetch`: you pass its `signal` to `fetch`, and `controller.abort()` makes that `fetch` reject with an `AbortError`. The cleanup calls it.

In development, `main.tsx` wraps the app in `<StrictMode>`. StrictMode mounts every component, unmounts it, and mounts it again, which runs each effect, then its cleanup, then the effect again. A missing cleanup shows up at once as two timers and two loops of requests. In a production build, StrictMode does nothing.

### Types at the Boundary

TypeScript checks your code, not the data that arrives. `res.json()` returns whatever the api sends, and the type `Monitor[]` is a promise you make about it. When a Go field is renamed, the compiler stays quiet and the page shows `undefined`. Two habits keep the two sides in step: write each type to match the Go struct and its JSON tags field for field, and check both against the OpenAPI file from <a href={weekHref(7)}>Week 7</a> when either side changes. A Go pointer such as `*int` arrives as a number or `null`, and the type states it: `total_ms: number | null`. Go writes a `time.Time` as RFC 3339 text, such as `"2026-10-11T14:02:07Z"`, and `Date.parse` reads it.

### Drawing with SVG

SVG, Scalable Vector Graphics, describes a picture as elements in the page: `<line>`, `<circle>`, `<path>`. React renders them like any other element, which means a chart is a component and your tests can query it. The `viewBox` attribute sets the coordinate system, and the browser scales it to the size CSS gives the element. Your chart uses a box 300 wide and 60 high. The y axis points down: `y = 0` is the top edge.

Drawing a chart comes down to two **scale** functions, which turn data into coordinates. x maps a check time, from the oldest to the newest check, onto 0 to 300. y maps a duration, from 0 to the slowest check, onto 60 to 0, upside down, which puts the slowest check at the top. A `<path>` draws a line from a string of commands: `M0,30` moves the pen to x 0 and y 30, and `L100,0` draws a line to x 100 and y 0. A new `M` lifts the pen, which is how the chart leaves a gap at each failed check. A charting library does the same work with more options, and adds its code to every page load. Yours is 30 lines that you can test.

### Three Levels of Tests

The page has logic, components and a browser to test, and each level fakes a different part. **jsdom** is a browser document written in JavaScript: it runs in Node, holds a DOM that React renders into, and draws nothing. **Testing Library** queries that DOM the way a person, or a screen reader, finds things on the page: by role, by accessible name and by text, never by CSS class. **Playwright** drives a real browser, Chromium here, and `page.route` answers the requests of the page from your test instead of the network.

### Serving the Page in Production

`vite build` turns `web/` into static files in `web/dist`: an `index.html` and, under `assets/`, one JavaScript and one CSS file whose names hold a hash of their content, such as `index-CHghxbEO.js`. Any web server can hand them out. Your `web` image runs **nginx**, a web server that also works as a proxy, which does two jobs on one origin: it serves `dist/`, and it passes every `/api/` request on to the api container, as the Vite dev server does in development. The browser sees one origin, and the page needs no CORS, as <a href={weekHref(6)}>Week 6</a> explains.

## Operate It

<OperateIt>

**The api stops.** Stop it with `docker compose stop api`. In development, the Vite proxy answers `502`, and the dev server logs `http proxy error: /api/monitors` with `connect ECONNREFUSED 127.0.0.1:8080`. Through nginx, the answer is `502` with an HTML page, and `docker compose logs web` shows `connect() failed (111: Connection refused) while connecting to upstream`. Either way, the page keeps its last data, and the alert reads `The last refresh failed: GET /api/monitors: status 502`. Start the api again: the next refresh clears the alert.

**nginx keeps an old address.** nginx looks up `api` once, when it starts. When Compose recreates the api container, for example after `make up` with a changed api image, and the new container gets a different address, every `/api/` request through nginx fails with `502`, while `curl 127.0.0.1:8080/healthz` answers `{"status":"ok"}`. `docker compose restart web` makes nginx look the name up again. In Kubernetes, from <a href={weekHref(15)}>Week 15</a>, the api sits behind a Service, whose address stays the same.

**A new build and an old page.** Without `no-cache` on `index.html`, a browser keeps the old `index.html` after you deploy, and it keeps loading the old JavaScript file that it names. The page looks the same as before your fix. With the headers from Step 10, the browser asks nginx about `index.html` every time, and a hashed asset never needs that question: a changed file has a new name.

| What you see | What it points to |
| --- | --- |
| `TypeError: Failed to fetch` in the console, and a CORS error | The page calls `http://localhost:8080` directly instead of a path such as `/api/monitors` |
| Every row reads **No checks yet** for minutes | The scheduler or the worker is not running: check `docker compose ps`, then the worker log |
| A row reads `Cannot load results: ... status 404` | The api is older than Week 8, or someone deleted the monitor between two refreshes |
| The Checked line reads `undefined ms` | A field name differs between the Go struct and `api.ts` |
| The Playwright test passes, and the real page breaks | The mocked JSON differs from what the api sends: compare it with `curl` output and `api/openapi.yaml` |
| `Playwright Test did not expect test() to be called here` from Vitest | The `include` line in `vite.config.ts` is missing, and Vitest runs `e2e/` |

</OperateIt>

## Side Lab

<SideLab title="Watch HTTP caching with curl: ETag, 304 Not Modified and Cache-Control">

Browsers avoid downloading a file twice with two mechanisms. With a **validator**, the browser asks whether its copy is still current. With a **lifetime**, it skips the question. `curl` shows both against the `web` container from Step 10. The outputs are examples from nginx, trimmed.

**1. Get a validator.** nginx sends an `ETag`, a short tag for one version of a file. For a static file, nginx builds it from the modification time and the size, both in hexadecimal: `1d3` is 467 bytes.

```txt
$ curl -sI http://127.0.0.1:3000/
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 467
Last-Modified: Sun, 11 Oct 2026 07:03:16 GMT
ETag: "6acb34b4-1d3"
Cache-Control: no-cache
```

**2. Ask with it.** Send the tag back in `If-None-Match`, as a browser does for a `no-cache` file. When the file has not changed, nginx answers `304 Not Modified` with no body: one round trip, no download.

```txt
$ curl -sI -H 'If-None-Match: "6acb34b4-1d3"' http://127.0.0.1:3000/
HTTP/1.1 304 Not Modified
ETag: "6acb34b4-1d3"
Cache-Control: no-cache
```

Change any text on the page, run `make up`, and ask again with the old tag: the answer is `200`, with the new file and a new tag.

**3. Skip the question.** The assets carry `max-age=31536000`, one year in seconds, and `immutable`. A browser that holds one never asks again. In the developer tools, reload the page with **Network** open: `index.html` shows `304`, and the JavaScript file shows `(memory cache)` or `(disk cache)` in the **Size** column. Tick **Disable cache** and reload: every file comes back with `200`.

**4. Compare the compressed size.** `curl` sends no `Accept-Encoding` header unless you ask, and nginx then sends the file as it is:

```txt
$ curl -s -o /dev/null -w '%{size_download}\n' http://127.0.0.1:3000/assets/index-CHghxbEO.js
223823
$ curl -s -o /dev/null -H 'Accept-Encoding: gzip' -w '%{size_download}\n' http://127.0.0.1:3000/assets/index-CHghxbEO.js
81921
```

nginx compresses at level 1 unless `gzip_comp_level` says otherwise: fast, and 82 KB here. `gzip -6 -c` on the same file gives 70 KB, close to what Vite reports. Set `gzip_comp_level 6;` in `nginx.conf`, rebuild, and measure again: each answer gets smaller and costs nginx more CPU.

</SideLab>
