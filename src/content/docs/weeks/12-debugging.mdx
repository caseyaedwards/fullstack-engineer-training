## Concepts

### When Green Tests Hide Bugs

A test checks what its author thought to check. The branch from Sam passes every test because each bug sits where no test looks: in a header on the wire, in the browser cache, in a default value, and in a code path that only HTTPS reaches. Your testing background is the asset here. Debugging is testing with the order turned around: the failure comes first, and you work back to the cause.

The method has six steps, and it works the same with every tool:

1. **Reproduce.** Find the shortest way to see the symptom on demand. A bug you cannot trigger is a bug you cannot confirm fixed.
2. **Observe.** Look at what the system does, not at what the code says. Pick the tool that sees the layer where the symptom shows.
3. **Hypothesize.** Name one cause that explains everything you see.
4. **Test the hypothesis.** Look at one value, or change one thing, that proves the cause or rules it out. A ruled-out cause is progress: it removes a place to look.
5. **Fix.** Write the test that fails first, then change the code until it passes.
6. **Keep the test.** It stops the same bug from coming back.

When the compiler optimizes, it moves code around and keeps variables in registers. `dlv debug` and `dlv test` build your code with optimizations turned off, through the Go build option `-gcflags='all=-N -l'`, which keeps every variable where the debug information says it is. A breakpoint stops every goroutine, not only the one that hits it. While you read variables, nothing in the program moves, and every clock keeps running.

### How a CPU Profile Works

A **profiler** measures where a program spends its resources. Go has one built in, and `net/http/pprof`, which your worker serves on `-debug-addr` since <a href={weekHref(5)}>Week 5</a>, hands its results out over HTTP. Week 5 reads the goroutine dump. This week, you read the CPU profile.

For a CPU profile, the Go runtime asks the operating system for a signal, `SIGPROF`, after every 10 ms of CPU time the program uses. At each signal, the runtime records the call stack of the goroutine that is running. After 10 seconds, the profile holds one stack per tick, and `go tool pprof` adds them up. Two columns matter:

- **flat**: the time in which the function itself runs, at the top of the stack.
- **cum**, short for cumulative: the time in which the function appears anywhere in the stack, itself or anything it calls.

A function with a small flat and a large cum calls the work. A function with a large flat does the work. To find the cause of a busy program, sort by cum and read down from `main` until the path splits.

### The HTTP Cache in the Browser

A browser keeps answers it can reuse. The `Cache-Control` response header sets the rules:

| Value | What the browser does |
| --- | --- |
| `max-age=300` | Keeps the answer and reuses it for 300 seconds without asking the server |
| `no-cache` | Keeps the answer, but asks the server before each reuse |
| `no-store` | Keeps nothing: every request goes to the server |
| `public` | Allows shared caches, such as a company proxy or a CDN (content delivery network), to keep it too |

## Observe It

<ObserveIt>

Two of the four bugs leave clues in output you already have. Make these habits:

- **Log the settings a program runs with, at start.** The worker prints `poll=1µs` on its first line. A busy loop, a wrong timeout or the wrong database shows up there before anywhere else. The api prints only its address: add every value it reads from a command-line flag or the environment to its `listening` line, except secrets such as `DATABASE_URL`, which holds the database password.
- **Measure the same thing with two tools.** `curl -w` against `tls_ms` catches the TLS row. When a number from your code matters, find a second tool that measures it on its own, and compare them once.
- **Keep a baseline profile.** Take a 10-second CPU profile of the healthy worker, idle and with 100 monitors, and save both files. A later profile that disagrees with the baseline points at what changed. Note the `Total samples` line of each: the fixed idle worker stays under 1%.
- **Count the requests the api serves.** The api logs one line per request since <a href={weekHref(7)}>Week 7</a>. With the status page open, `docker compose logs api | grep -c 'path=/api/monitors '` counts its polls. Under the caching bug, the count stays flat while the page polls.

<a href={weekHref(13)}>Week 13</a> turns these into metrics and dashboards. The <a href={trackHref('observability')}>Observability track</a> covers profiles as one of the signals a service gives off.

</ObserveIt>

## Operate It

<OperateIt>

Debugging tools change the program they look at. Know the cost before you point one at a running service:

- **A breakpoint stops every goroutine.** Health checks time out while you read variables, and from <a href={weekHref(15)}>Week 15</a>, Kubernetes restarts a container whose liveness probe fails. Debug a copy, or a test, not the live service.
- **The production image cannot be debugged.** The Dockerfile from <a href={weekHref(6)}>Week 6</a> builds with `-ldflags="-s -w"`, which strips the symbol table and the debug information that Delve reads. Reproduce the bug on your machine, as Steps 5 and 6 do.
- **The debug server is a door.** `/debug/pprof/` shows the inside of the program and starts profiles on request. Keep `-debug-addr` on `127.0.0.1` and never publish its port in `compose.yaml`.
- **A cache header outlives its fix.** Every browser that received `max-age=300` keeps that answer for up to 300 seconds after you deploy the fix, and a CDN keeps it until you purge it. Before you ship a `max-age`, decide how stale an answer can be.

| What you see | Tool to start with |
| --- | --- |
| A header, status code or cookie looks wrong | `curl -v` against the api, with no browser in between |
| The page shows old data, or behaves differently with DevTools open | DevTools **Network** panel: the **Size** column and the response headers |
| A process uses CPU or memory it has no reason to use | `go tool pprof` on its debug server: profile for CPU, heap for memory, goroutine for leaks |
| A value is wrong, and the code that computes it looks right | A failing test, then `dlv test` with a breakpoint where the value is set |

</OperateIt>

## Side Lab

<SideLab title="Find the commit that broke a test with git bisect">

With four commits, reading each diff works. With 400, it does not. `git bisect` runs a binary search over the history: you name a commit where a test fails and one where it passes, and Git checks out the commit halfway between, again and again, until it finds the first bad one. 400 commits take nine steps.

The TLS test lives in your fix commit, which bisect removes from the tree when it checks out an older commit. Copy the test aside first, then let `git bisect run` drive the search. On `review/sam`, after you commit the fixes and before you merge:

```sh
git show HEAD:internal/probe/tls_test.go > /tmp/tls_test.go
git bisect start $(git log --format=%h -1 --author=sam@example.com) main
git bisect run sh -c 'cp /tmp/tls_test.go internal/probe/ && go test ./internal/probe -run TestTLSRowIsTheHandshakeOnly; status=$?; rm internal/probe/tls_test.go; exit $status'
git bisect reset
```

`git bisect start` takes the bad commit first, the last one from Sam, then the good one. `git bisect run` runs the command at each step: exit code `0` marks the commit good, and any code from `1` to `127` except `125` marks it bad. The command copies the test in, runs it, removes it again, and passes on the result of `go test`. Git ends with this output, trimmed:

```txt
c70596d375a19779b03acdf869c39d02b40162e3 is the first bad commit
commit c70596d375a19779b03acdf869c39d02b40162e3
Author: Sam Rivera <sam@example.com>

    probe: say what each trace hook measures
```

Your hash differs. `git bisect reset` returns you to the branch you started from. The same trick fails for the worker. `poll_test.go` uses `defaultPoll`, which exists only from the worker commit on. Before it, the test does not compile, and `go test` exits with `1`. Every commit then counts as bad, and bisect blames the first commit from Sam. A check must work at every commit, or exit with `125`, which tells bisect to skip a commit it cannot test. The help text from `-h` works at every commit:

```sh
git bisect start $(git log --format=%h -1 --author=sam@example.com) main
git bisect run sh -c 'go run ./cmd/worker -h 2>&1 | grep -q "(default 1s)"'
git bisect reset
```

`grep -q` exits with `0` when the help shows the one-second default, and with `1` when it does not. Bisect ends with `a9273ea6dc4172da955c5632afc103193269d284 is the first bad commit` and `worker: name the flag defaults`.

</SideLab>
