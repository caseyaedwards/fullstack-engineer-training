## Goals

- Design REST routes for monitors, and pick the status code for each success and each mistake.
- Serve them with `http.ServeMux` method patterns, and read the `{id}` path segment with `r.PathValue`.
- Decode JSON safely: a size cap, no unknown fields, one object per body, and errors written for the client.
- Put storage behind a `Store` interface, with an in-memory version that is safe for concurrent requests.
- Describe the API in OpenAPI 3.1, lint the file, and test that it lists exactly the routes the code serves.
- Test the handlers with `httptest`: a table of bad requests, one full flow over a real port, and a fake store that fails.

## Concepts

### Resources, Methods and Status Codes

**REST**, short for Representational State Transfer, is a style for HTTP APIs: every thing the API manages is a **resource** with its own URL, and the HTTP method says what to do with it. Your api manages one type of resource. `/api/monitors` is the **collection**, the list of every monitor, and `/api/monitors/7` is one **item** in it:

| Method and path | Does | Success |
| --- | --- | --- |
| `GET /api/monitors` | lists every monitor | `200` and a JSON array |
| `POST /api/monitors` | creates a monitor from the JSON body | `201` and the new monitor |
| `GET /api/monitors/{id}` | returns one monitor | `200` and the monitor |
| `DELETE /api/monitors/{id}` | deletes one monitor | `204` and no body |

The URL names a noun and the method carries the verb: `POST /api/monitors`, not `POST /api/createMonitor`. Two method properties matter when a client retries after a timeout:

- **Safe**: the request changes nothing on the server. `GET` is safe, and a client or a proxy can repeat it any number of times.
- **Idempotent**: sending the request twice leaves the server in the same state as sending it once. `DELETE` is idempotent: the second `DELETE` of monitor 7 answers `404`, but monitor 7 is gone either way. `POST` is neither safe nor idempotent. A client that retries a `POST` after a lost answer creates the monitor twice, unless the server refuses the second one. Your api refuses it with `409`, because two monitors never share a URL.

The **status code** in the first line of every response tells the client the outcome before it reads the body. The first digit gives the class: `2xx` means success, `4xx` means the client sent something wrong and must change the request before it tries again, and `5xx` means the server failed and the same request can work later. Your api uses these codes:

| Code | Name | Your api answers it when |
| --- | --- | --- |
| `200` | OK | a read succeeds |
| `201` | Created | a `POST` creates a monitor; the `Location` header holds its path |
| `204` | No Content | a `DELETE` succeeds; the response has no body |
| `400` | Bad Request | the body is not valid JSON, has an unknown field, or breaks a rule; the id is not a number |
| `404` | Not Found | no monitor has that id, or no route has that path |
| `405` | Method Not Allowed | the path exists, but not for that method; the `Allow` header lists the methods that work |
| `409` | Conflict | a monitor for that URL exists |
| `413` | Request Entity Too Large | the body is over 1 MiB |
| `415` | Unsupported Media Type | the `Content-Type` header is not `application/json` |
| `500` | Internal Server Error | the store fails |

Every error body has one shape, `{"error": "<message>"}`, with `Content-Type: application/json`. The status code tells a program what happened, and the message tells a person. Any client, such as the status page in <a href={weekHref(10)}>Week 10</a>, reads the message the same way on every route.

### How Go Serves a Request

The `net/http` package does the network work for you. `http.Server` accepts connections, reads each request, and passes it to a **handler**: any value with the method `ServeHTTP(w http.ResponseWriter, r *http.Request)`. `r` holds the method, the URL, the headers and the body. `w` is where the handler writes the status code, the headers and the body of the answer.

The server runs each connection in its own goroutine, the concurrency tool from <a href={weekHref(5)}>Week 5</a>. Two clients therefore run your handlers at the same time, and any data the handlers share needs a lock.

`http.ServeMux` is a handler that picks another handler. It is a **router**, also called a mux, short for multiplexer. Since Go 1.22, a pattern can hold a method before the path, and **wildcards** in the path: `"GET /api/monitors/{id}"` matches `GET /api/monitors/7`, and `r.PathValue("id")` returns `"7"`. A wildcard matches one whole path segment. When two patterns match a request, the more specific one wins: `/api/monitors/new` beats `/api/monitors/{id}`. When the path matches no pattern, the mux answers `404`. When the path matches but the method does not, it answers `405` with an `Allow` header.

A handler that wraps another handler is called **middleware**: it runs code before and after the inner handler, for every route at once. Your api gets two pieces of middleware this week: one turns the plain-text `404` and `405` answers of the mux into JSON, and one logs every request.

### Reading and Writing JSON

The `encoding/json` package turns Go values into JSON and back. A **struct tag**, from Week 6, names the JSON field of each struct field: `IntervalSeconds int` with the tag `json:"interval_seconds"` reads and writes `"interval_seconds"`. Five behaviors of the package shape your handlers:

- **A missing field gets its zero value.** A body without `interval_seconds` decodes with `IntervalSeconds` set to `0`. Validation then refuses `0`, which turns a missing field into a clear error.
- **Unknown fields are ignored** by default. Without a check, a client that sends `"interval": 60` gets `interval_seconds must be between 30 and 3600, got 0` for a value it believes it sent. `Decoder.DisallowUnknownFields` makes the typo itself the error.
- **A nil slice encodes as `null`, not `[]`.** A list handler that returns a nil slice for an empty store sends `null`, and a frontend that calls `.map` on it crashes.
- **`time.Time` encodes as RFC 3339 text**, such as `"2026-10-11T06:52:07.622539Z"`: the date, a `T`, the time, and the time zone, where `Z` means UTC.
- **Field names match without regard to case** when decoding. `{"URL": "https://example.com", "Interval_Seconds": 60}` creates a monitor, and Go has no setting to stop it. The contract names the lowercase fields, and clients send those.

A body is untrusted input of any size. `http.MaxBytesReader` wraps the body and fails the read after a limit, here 1 MiB, which stops a client from filling the memory of your api with one request.

### Validate at the Boundary

Your api is a **trust boundary**: data from outside crosses into code that relies on it. Week 6 explained why the backend checks every request even when the frontend checks the form: anyone can send a request with `curl`. `400`, `409`, `413` and `415` are all mistakes by the client, but each one asks for a different fix: correct the body, pick another URL, send less, or set the header. A `500` is never the fault of the client. Its message stays fixed, `internal error`, and the real cause goes to your log: a database error can hold table names, SQL text or a host name, and none of that belongs in a response.

### Layers and the Store Interface

The code splits into layers, each with one job:

- `internal/api` knows HTTP: routes, JSON, headers and status codes.
- `internal/monitor` knows monitors: the type, the rules in `Validate`, and the `Store` interface.
- A store keeps monitors. The handlers call it only through the four methods of `Store`, and never learn whether a map or Postgres sits behind it.

An **interface** in Go lists methods, and any type with those methods satisfies it, with no `implements` keyword. <a href={weekHref(2)}>Week 2</a> used the `Getter` interface to swap the HTTP client for a fake in tests. Here the same idea swaps the storage.

### OpenAPI: The Contract

An **API contract** is the written promise of what the API accepts and returns. **OpenAPI** is the standard format for it: a YAML or JSON file that lists every path, method, parameter, request body, response and status code. Version 3.1 describes data with **JSON Schema**, the standard vocabulary for the shape of JSON: types, required fields, and limits such as `minimum: 30`.

The file serves three readers. People read it as documentation. Tools lint it, render it as a browsable page, and generate clients and types from it. Tests compare it with the code. Some teams write the contract first and the code after it, others generate the contract from the code. Here you write the code first, then the contract by hand, and a test fails when the two list different routes. The <a href={trackHref('system-design')}>System and Software Design track</a> compares the approaches.

### Testing HTTP Handlers

A handler is a function of a request, which makes it easy to test without a network. The `net/http/httptest` package gives you two tools:

- `httptest.NewRecorder()`: a `ResponseWriter` that keeps the status, the headers and the body in memory. Call `h.ServeHTTP(rec, req)` directly, with no port and no goroutines. Use it for many small cases.
- `httptest.NewServer(h)`: starts `h` on a free port of `127.0.0.1`, and a real `http.Client` talks to it. Use it to test a whole flow the way a client sees it, including what the server itself adds, such as `Content-Length`.

A **fake** is a small type that satisfies an interface with canned behavior. A store that always fails is hard to get from a real database and takes a few lines as a fake. The <a href={trackHref('testing')}>Testing track</a> compares fakes, stubs and mocks.

## Operate It

<OperateIt>

**A restart empties the store.** Create a monitor, stop the api with **Ctrl+C**, start it again, and list: the answer is `[]`. Under Compose, `docker compose restart api` does the same, as does every `make up` that rebuilds the image. Until Week 8, every monitor is gone on the next start.

**A panic in a handler drops the connection.** When a handler panics, for example on a write to a nil map, `net/http` recovers the panic for that one request, logs it, and closes the connection without an answer. The rest of the server keeps running:

```txt
$ curl -sS http://127.0.0.1:8080/api/monitors
curl: (52) Empty reply from server
```

The api log holds `http: panic serving 127.0.0.1:36424: assignment to entry in nil map` and a stack trace that names the line. No `request` line follows, because the panic unwinds through `LogRequests` before it logs. An empty reply with a stack trace in the log means a bug in your handler.

| What you see | What it points to |
| --- | --- |
| `415` and `Content-Type must be application/json` from `curl -d` | `curl -d` sends `Content-Type: application/x-www-form-urlencoded` unless you pass `-H 'Content-Type: application/json'` |
| `404` and `not found` for `/api/monitors/` | The trailing slash makes a different path, and no pattern matches it |
| `405` and `Allow: DELETE, GET, HEAD` | The path exists, and the method you sent is not in `Allow` |
| `400` and `unknown field` | A typo in a field name, or a client written against another version of the contract |
| `413` and `body is larger than 1048576 bytes` | The client sends over 1 MiB: a bug in the client, or a file sent to the wrong route |
| `TypeError: Cannot read properties of null (reading 'map')` in the browser | The list route answers `null`: the nil-slice guard is missing |
| `500` and `internal error` | The store fails: the `error method=` line in the api log holds the cause |
| `curl: (7) Failed to connect to 127.0.0.1 port 8080` | The api is not running, or listens on another address: read its `listening addr=` line |

</OperateIt>

## Side Lab

<SideLab title="Speak HTTP/1.1 by hand with netcat">

HTTP/1.1 is text: a request line, header lines, an empty line, then the body. Every line ends in a carriage return and a line feed, written `\r\n`. `nc`, short for netcat, opens a TCP connection and passes its input through it. macOS ships it, and Ubuntu installs it by default. Start your api with `make run-api` and send a request through `printf`, which turns each `\r\n` into those two bytes:

```txt
$ printf 'GET /api/monitors HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' | nc 127.0.0.1 8080
HTTP/1.1 200 OK
Content-Type: application/json
Date: Sun, 11 Oct 2026 06:52:35 GMT
Content-Length: 3
Connection: close

[]
```

`Connection: close` asks the server to close the connection after its answer, which ends `nc`. Without it, HTTP/1.1 keeps the connection open for the next request, and `nc` waits.

**1. Leave out Host.** Send the same request without the `Host` line. Go answers `400 Bad Request: missing required Host header` as plain text, before your handlers run: HTTP/1.1 requires the header, because one address can serve many sites.

**2. Send a body.** The server knows where the body ends from `Content-Length`, the size in bytes. The body below is 54 bytes, which `printf '%s' '<body>' | wc -c` confirms:

```sh
printf 'POST /api/monitors HTTP/1.1\r\nHost: localhost\r\nContent-Type: application/json\r\nContent-Length: 54\r\nConnection: close\r\n\r\n{"url": "https://example.com", "interval_seconds": 60}' | nc 127.0.0.1 8080
```

The answer is `201 Created` with a `Location` header.

**3. Lie about the length.** Set `Content-Length: 20` and send the same body. The server reads 20 bytes, `{"url": "https://exa`, and answers `400` with `body is not valid JSON`. Then set `Content-Length: 100`. The server waits for the 46 bytes that never arrive, and `nc` waits for an answer that never comes. Press **Ctrl+C**. The api logs the request with a `duration_ms` as long as you waited: the Week 6 `ReadHeaderTimeout` covers the headers, not the body. `http.Server` has a second setting, `ReadTimeout`, which bounds the whole request, body included, and stops a slow client from holding a connection.

</SideLab>
