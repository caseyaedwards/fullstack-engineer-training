## Concepts

### Who Are You, and What Can You Do

Two questions guard every request. **Authentication** asks who you are: the api checks an email and a password, then remembers the answer. **Authorization** asks what you can do: the api looks up the rules for that person and that request. The monitor has one rule: anyone can read, and any logged-in user can write. Bigger systems give each person roles, such as viewer and editor. The <a href={trackHref('iam')}>IAM track</a>, short for identity and access management, covers them.

### Storing Passwords

The api never stores a password. It stores a **hash**: the output of a one-way function. At login, it hashes what you type and compares the two hashes. Nobody can turn a hash back into the password, but anyone with the hash can guess: hash `password1`, compare, try the next word. A fast hash such as SHA-256 runs billions of times a second on one graphics card, which tries every common password in seconds.

Two fixes stop that:

- A **salt**: random bytes mixed into each hash. Two users with the same password get different hashes, and an attacker who steals the table has to guess each user separately.
- A **slow hash**, built to cost time on purpose. bcrypt takes a **cost**: it runs 2 to the power of the cost rounds, and each step up doubles the time. On the machine that built this page, one hash takes 68 ms at cost 10, 269 ms at cost 12 and 1.13 s at cost 14. A login pays that once. An attacker who steals the hashes pays it for every guess. An attacker who guesses through the login form makes your server pay it instead, which is why Step 5 limits guesses.

A bcrypt hash carries everything needed to check it, in 60 characters, such as `$2a$12$cPYsvj8HiV7yznYS7TVYSeVzUEXRo51fqRpOjVL7/5Kf5tHiRseE2`:

| Part | Example | Meaning |
| --- | --- | --- |
| Version | `$2a$` | The bcrypt version |
| Cost | `12$` | 2 to the power of 12 rounds |
| Salt | `cPYsvj8HiV7yznYS7TVYSe` | 22 characters, new for every hash |
| Hash | `VzUEXRo51fqRpOjVL7/5Kf5tHiRseE2` | The last 31 characters |

Because the cost sits in the hash, you can raise it later: new hashes use the new cost, and old ones still check.

bcrypt has one sharp edge: it reads only the first 72 **bytes** of a password. Bytes, not characters: in UTF-8, `é` takes two bytes and `🔒` four. The Go package `golang.org/x/crypto/bcrypt` refuses to hash a longer password and returns `ErrPasswordTooLong`. When it checks a password, it compares the first 72 bytes and ignores the rest. The api refuses any password over 72 bytes itself, at both ends.

The OWASP Password Storage Cheat Sheet ranks Argon2id first, then scrypt, and lists bcrypt "for legacy systems", with a cost of 10 or more and a 72-byte limit. This course uses bcrypt at cost 12, because its Go package has a two-function API and keeps the cost and the salt inside the hash. Argon2id, in `golang.org/x/crypto/argon2`, leaves you to store its settings and salt yourself.

### Sessions: A Random Name for a Login

HTTP forgets you between requests. To remember a login, the api creates a **session**: a row in Postgres that says which user logged in and when the login ends. The browser holds the name of that row in a **cookie**: a value the server sets with a `Set-Cookie` header, and the browser sends back in a `Cookie` header on every later request to the same site.

The name is a **token**: 26 random characters from `crypto/rand.Text`, with at least 128 bits of randomness. At a billion billion guesses a second, trying half of all 128-bit tokens takes about five trillion years. The sessions table stores the SHA-256 hash of the token, not the token: a copy of the table, in a backup for example, logs nobody in. A fast hash is enough here, unlike for passwords, because nobody can guess the input.

### What Each Cookie Attribute Blocks

The api sets the cookie with this header. Each attribute after the value closes one door:

```txt
Set-Cookie: session=4JSM4QUGWTA4AWIZ2BSX5JLPON; Path=/; Max-Age=86400; HttpOnly; Secure; SameSite=Lax
```

| Attribute | What the browser does | What it blocks |
| --- | --- | --- |
| `Path=/` | Sends the cookie with every path on the site | Nothing: it makes `/api/me` and `/api/monitors` both receive it |
| `Max-Age=86400` | Deletes the cookie after 86,400 seconds, 24 hours | A login that lasts forever on a shared computer |
| `HttpOnly` | Leaves the cookie out of `document.cookie` | Script injected into the page reading the token and sending it away |
| `Secure` | Sends the cookie only over HTTPS. Chrome and Firefox exempt `http://localhost`, and Chromium also `http://127.0.0.1` | Anyone on the network path reading the token from plain HTTP |
| `SameSite=Lax` | Leaves the cookie off requests that another site starts, except a top-level `GET` navigation | Cross-site request forgery |

**Cross-site scripting** (XSS) is an attack where a page runs script that someone else wrote, through text that the page shows without escaping. React escapes text by default, which is why the status page from <a href={weekHref(10)}>Week 10</a> is safe from it. `HttpOnly` limits the damage of one: the script can still send requests from your page, but it cannot copy the token and use it from elsewhere.

**Cross-site request forgery** (CSRF) is an attack where another site makes your browser send a request to your api. Without `SameSite`, the browser adds your cookie to it, and the api sees a logged-in request. `SameSite` decides when the browser adds the cookie. It compares **sites**, not origins. An origin is the scheme, host and port. A site is the scheme plus the registrable domain: `https://app.example.com` and `https://api.example.com` are two origins on one site, and `http://localhost:5173` and `http://localhost:8080` are one site too. With `Lax`, a request from another site carries the cookie only when it is a top-level navigation, such as a link click, with a safe method: `GET` or `HEAD`. A form `POST`, a `fetch`, an image or an iframe from another site gets no cookie.

A request from another origin also meets CORS, short for cross-origin resource sharing: the headers a server sends to tell the browser which other origins can read its answers. A **simple request**, such as a form `POST` or a `fetch` with a `text/plain` body, still reaches the api and runs the handler: CORS only decides whether the other origin reads the answer. A request with a JSON body or the `DELETE` method is not simple. The browser asks first with an `OPTIONS` request, the **preflight**, and sends the real request only when the answer carries the right CORS headers. Two rules of the api turn this into a defense, and every later week keeps them: **writes take JSON only, and the api sends no CORS headers.** The browser hides each answer from other origins, and blocks each JSON or `DELETE` request at the preflight.

Rules that hold by habit break by accident, and `SameSite` admits a sibling subdomain. A third check reads what the browser says about the request itself. Every current browser sends `Sec-Fetch-Site` with each request to an HTTPS address, to `localhost` or to another loopback address: `same-origin`, `same-site`, `cross-site`, or `none` for an address the user typed. A request to plain HTTP on any other host carries no `Sec-Fetch-Site`, and `sameOrigin` then compares the `Origin` header with the host of the request. Step 7 adds `sameOrigin`, which refuses every write that does not come from the api's own origin.

### Sessions or Tokens

The other common answer is a **JSON Web Token** (JWT): the server writes the user and an expiry into a JSON payload, signs it with a secret key, and hands out `header.payload.signature`, each part written in base64url: a way to write bytes as text that is safe in a URL. Any server that holds the key checks the signature and the expiry, with no database lookup. The side lab builds one by hand.

| | Session in a table | Signed token (JWT) |
| --- | --- | --- |
| Check a request | One indexed query in Postgres | Check the signature: CPU only |
| Log out, or lock someone out | Delete the row: the next request fails | The token stays valid until it expires, unless every server checks a deny list in a database |
| Secret to manage | None: the token is random | The signing key. Whoever holds it logs in as anyone |
| What the client holds | A random name that says nothing | The payload, readable by anyone: base64url is encoding, not encryption |

The monitor uses sessions. It has one api and one Postgres already, which makes the lookup cheap. Logout and lockout work at once. No signing key exists to leak. A JWT fits a different shape: many services, run by different teams or companies, that each check who sent a request without calling one shared database. OpenID Connect, the protocol behind Sign in with Google, hands your identity to another company as a JWT.

### The OWASP Top 10

The Open Worldwide Application Security Project (OWASP) publishes the **OWASP Top 10**: a ranked list of the most common kinds of weakness in web applications. The current list is the 2025 edition. Eight of its ten categories touch the monitor:

| Category | In the monitor |
| --- | --- |
| A01:2025 Broken Access Control | Before this week, anyone wrote. `requireUser` now guards every write, and `sameOrigin` refuses writes from other sites |
| A02:2025 Security Misconfiguration | Compose publishes Postgres on `127.0.0.1` only, and the api sends no CORS headers |
| A03:2025 Software Supply Chain Failures | `go.sum` pins the checksum of every module, including the new `golang.org/x/crypto` |
| A04:2025 Cryptographic Failures | bcrypt for passwords, SHA-256 for tokens, a `Secure` cookie |
| A05:2025 Injection | Every SQL statement passes values as `$1` parameters, since <a href={weekHref(8)}>Week 8</a>. React escapes text, which blocks XSS |
| A07:2025 Authentication Failures | A login limit per email, one answer for a wrong email or password, a new random token at each login |
| A09:2025 Security Logging and Alerting Failures | One log line per failed login, with the reason and without the password |
| A10:2025 Mishandling of Exceptional Conditions | Errors answer `internal error` and keep the details in the log, since <a href={weekHref(7)}>Week 7</a>. When the session lookup fails, `requireUser` answers `500` and refuses the request |

### Step 1: Add the Crypto Module

bcrypt lives in `golang.org/x/crypto`, a module that the Go team maintains outside the standard library. From the folder that holds `go.mod`, run:


### Step 5: Limit Password Guessing

A slow hash makes each guess cost time. A limit caps the number of guesses. This one allows five login attempts per email address every 15 minutes:

<CodeFrom file="go/week11/your-monitor/internal/auth/limit.go" region="limiter" lang="go" title="internal/auth/limit.go" />

The key is the email address, not the client address, because every request behind nginx or the Vite dev server arrives from the address of the proxy. The trade-off: anyone who knows your email can lock you out for 15 minutes. `TestLimiterUnderParallelGuesses` fires 100 attempts at once and counts exactly five that pass.

The cap of 10,000 keys protects the memory of the api from guesses at made-up emails. A full map makes room by deleting the expired keys, then the oldest one, which means a flood never locks out a real user: `TestLimiterCapsItsMemory` fills the map and logs in with a fresh email. `Login` refuses an email over 254 bytes, the longest that SMTP allows, before it reaches the map or the log. Each guess at a new email still costs the server one bcrypt check, about 0.27 s of CPU, and nothing caps those until <a href={weekHref(17)}>Week 17</a> adds a limit per client address for the whole api.

`-b cookies.txt` sends the saved cookie back. `curl`, like Chromium, treats `127.0.0.1` as secure and sends the `Secure` cookie to it over plain HTTP:

```txt
$ curl -sS -b cookies.txt -H 'Content-Type: application/json' -d '{"url":"https://example.org","interval_seconds":60}' http://127.0.0.1:8080/api/monitors
{"id":2,"url":"https://example.org","interval_seconds":60,"created_at":"2026-10-11T07:36:52.476284Z"}
$ curl -sS -b cookies.txt -c cookies.txt -X POST -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/logout
204
$ curl -sS -b cookies.txt -X DELETE -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/monitors/2
401
```

The `curl` loop from Week 10 that adds monitors needs `-b cookies.txt` from now on. Run `rm cookies.txt` and `unset PASSWORD` when you finish: until you log out, the file holds a live token.

### Step 11: Keep Secrets Out of Git

The monitor has two secrets: `POSTGRES_PASSWORD` and `ALERT_WEBHOOK_URL`. Sessions add none, because their tokens are random and live only in Postgres and the browser. Both secrets come from `.env`, which Compose reads, and the Week 0 `.gitignore` keeps `.env` out of Git. Check both claims. `git check-ignore -v` prints the rule that ignores a file:


## Observe It

<ObserveIt>

The api writes one line per login attempt, next to the request log line. These four lines come from the fifth wrong password in a row and the attempt after it:

```txt
2026/10/11 07:28:06 login failed email="you@example.com" reason="wrong password"
2026/10/11 07:28:06 request method=POST path=/api/login status=401 bytes=36 duration_ms=300.3
2026/10/11 07:28:07 login refused email="you@example.com" reason="too many attempts"
2026/10/11 07:28:07 request method=POST path=/api/login status=429 bytes=62 duration_ms=0.1
```

The answer to the client says only `wrong email or password`. The log names the reason, because you need it and an attacker does not. `%q` quotes the email: an email with a line break in it shows as `\n`, and cannot forge a second log line.

Read the lines with `docker compose logs api | grep 'login '` and look for these patterns:

- **Many `wrong password` lines for one email.** Someone guesses that password. The `429` lines show the limit at work.
- **`no such user` lines for many different emails.** Someone tries a list of email and password pairs leaked from another site, an attack called credential stuffing.
- **A `401` on `/api/login` that takes 300 ms, and a `429` that takes 0.1 ms.** bcrypt costs the time, and the limiter answers before bcrypt runs.

Never log a password, a token or a `Cookie` header. The request log writes the path, not the headers. pgx replaces the password in its error messages with `xxxxxx`, as in ``cannot parse `postgres://monitor:xxxxxx@127.0.0.1:5432/monitor` ``.

</ObserveIt>

## Operate It

<OperateIt>

**Login works, then every request answers 401.** You started the dev server with `npm --prefix web run dev -- --host` and opened the page from your phone at `http://192.168.1.20:5173`. The login answers `200` with the cookie, and the browser drops it: `Secure` allows plain HTTP only for `localhost`, and in Chromium for `127.0.0.1`. In Chromium, `window.isSecureContext` is `false` on that address, and **Application** shows no cookie. Use HTTPS, which <a href={weekHref(16)}>Week 16</a> sets up, or test on the machine that runs the stack.

**You locked yourself out.** Five wrong passwords give `429` with `Retry-After: 900` or less. Wait that many seconds, or restart the api with `docker compose restart api`: the limiter lives in memory. Two api replicas, from <a href={weekHref(15)}>Week 15</a>, keep two separate counts.

**A user forgot the password, or leaves.** Delete the user. `ON DELETE CASCADE` deletes their sessions with them, which logs them out at once:

```sh
docker compose exec postgres psql -U monitor -d monitor -c "DELETE FROM users WHERE email = 'you@example.com'"
```

Then create the user again with Step 9. To log everyone out, after a laptop with a live cookie goes missing for example, run `DELETE FROM sessions`. With JWTs, the only equivalent is rotating the signing key.

**A secret reached a commit.** Rotate it first: after you rewrite your history, the old copy stays readable in forks and caches. The `postgres` image reads `POSTGRES_PASSWORD` only when it creates an empty data directory, which means a new value in `.env` changes nothing in the `pgdata` volume. Change the password inside Postgres, where `\password` asks for it twice without showing it:

```sh
docker compose exec postgres psql -U monitor -d monitor -c '\password monitor'
```

Put the same value in `.env`, then run `make up`, which recreates the containers whose settings changed.

| What you see | What it points to |
| --- | --- |
| `401` `login required` with a cookie that worked before | The session passed its 24 hours, someone deleted it, or the cookie never reached the api |
| `401` `wrong email or password` | A wrong password, an email with no account, or a password over 72 bytes |
| `429` with `Retry-After` | Five attempts for that email in 15 minutes |
| `415` from `/api/login` | The body is a form, or the request has no `Content-Type: application/json` |
| `403` `cross-origin request refused` | A page on another origin sent the write, or a proxy in front of the api serves the page from a different origin |
| `password must have at least 15 characters` from `-create-user` | The password on stdin is shorter than 15 characters, or stdin is empty |

</OperateIt>

## Side Lab

<SideLab title="Make a JWT by hand and see what logout cannot do">

The site examples hold a small JWT signer in `examples/go/week11/jwt.go`, written with the standard library. It signs with HMAC, short for hash-based message authentication code, over SHA-256: the scheme JWT calls HS256.

<CodeFrom file="go/week11/jwt.go" region="sign" lang="go" title="jwt.go" />

**1. Make a token.** From `examples/go`, create a random 32-byte key and sign a token that lasts an hour:

```sh
export JWT_KEY=$(openssl rand -base64 32)
TOKEN=$(go run ./week11/cmd/jwt -sub you@example.com)
echo "$TOKEN"
```

**2. Read it without the key.** The middle part is base64url JSON, and `atob` in Node decodes it:

```sh
node -e "console.log(atob(process.argv[1].split('.')[1].replace(/-/g,'+').replace(/_/g,'/')))" "$TOKEN"
```

The output is the payload, such as `{"sub":"you@example.com","exp":1791707423}`. Anyone who holds the token reads it. Never put a secret in a JWT payload.

**3. Forge it.** Swap in a payload for another user and keep the old signature:

```sh
FORGED=$(node -e "const [h, , s] = process.argv[1].split('.'); const p = btoa(JSON.stringify({ sub: 'root@example.com', exp: 4102444800 })); console.log([h, p.replace(/=+\$/, '').replace(/\+/g, '-').replace(/\//g, '_'), s].join('.'))" "$TOKEN")
go run ./week11/cmd/jwt -verify "$FORGED"
```

The answer is `signature does not match`. The signature covers the header and the payload, and only the key makes a new one. `go run ./week11/cmd/jwt -verify "$TOKEN"` still answers `valid`.

**4. Try to log out.** Nothing you run ends `$TOKEN` before its `exp`: `Verify` reads only the key and the clock. You have two ways out: change `JWT_KEY`, which logs out everyone, or keep a list of revoked tokens in a database and check it on every request, which is a session table again. Read `TestJWT` in `jwt_test.go` for each case, including a token with `"alg":"none"`, which `Verify` refuses.
