## Concepts

### Background Jobs and Queues

A **background job** is work that runs outside any request: no user waits for it. Checking a site every 60 seconds is one. A **job queue** holds those jobs between two kinds of programs. A **producer** adds jobs, and a **consumer** takes them out and does them. Your scheduler is the producer and your workers are the consumers.

The queue decouples the two sides:

- **Scale.** Ten workers drain the queue faster than one, and the scheduler does not change.
- **Restarts.** The jobs live in the database, not in the memory of a process. Restart a worker, and its jobs wait for it.
- **Backlog.** When the workers fall behind, the queue grows. Its length tells you how far behind they are, which you log in [Observe It](#observe-it).

### Postgres as the Queue

A dedicated message broker, such as NATS, RabbitMQ or Redis Streams, is a server built to move messages. This course uses a table in the Postgres you already run, for three reasons:

- One database to run, back up and restore. The `pg_dump` from Week 8 covers the queue too.
- One transaction covers the job and its result: the worker cannot store a result and lose track of the job, or the other way round.
- The pattern is common in production: River for Go and Solid Queue for Ruby on Rails keep their jobs in a database table and claim them the same way.

The cost: workers ask the table for work over and over, which is called **polling**, and each check in flight holds a database connection. A monitor for 300 sites with 60-second intervals makes five jobs a second, far below what one Postgres server handles. When you need many thousands of messages a second, or many different consumers of the same message, a broker fits better. The <a href={trackHref('messaging')}>Messaging and Streaming track</a> compares the three brokers with this table.

### Row Locks and SKIP LOCKED

A **transaction** groups SQL statements into one unit. It starts with `BEGIN` and ends with `COMMIT`, which makes every change visible to everyone at once, or `ROLLBACK`, which throws every change away. Postgres rolls back on its own when the connection drops before the commit.

`SELECT ... FOR UPDATE` reads rows and **locks** them until the transaction ends. Any other transaction that tries to lock, change or delete those rows waits. That is half of what a queue needs: two workers never hold the same job. The other half is speed. With plain `FOR UPDATE`, every worker asks for the oldest job, and every worker after the first waits for that one row, which makes your workers take turns.

`SKIP LOCKED` changes the wait into a skip: Postgres passes over the rows another transaction has locked and returns the next row that is free. Each worker gets a different job, at once.

### At-Least-Once Delivery

The diagram shows the delivery guarantee of this queue. A job runs **at least once**: a crash before the commit hands it to the next worker, and the site gets one more `GET`. Its result lands **exactly once**, because the insert of the result and the delete of the job commit together. No queue can promise that the work itself runs exactly once: a worker that dies a moment before its commit has already done the work. Design every job such that a second run does no harm. Such a job is **idempotent**. A `GET` against a site is.

The guarantee has a price. A worker holds its transaction open for the whole check, up to the 5-second timeout. While it does, Postgres shows that connection as `idle in transaction`, and the worker needs one connection per goroutine. Queues that run longer jobs use a **lease** instead: the claim sets a time until which the job belongs to the worker and commits at once, and the job comes back when the lease runs out. Amazon SQS calls this the visibility timeout.

### From Results to Incidents

One failed check is not worth waking anyone for: a single request times out, or a deploy restarts the server for two seconds. An **incident** is a period during which a monitor is down. Your rule: three failed checks in a row open an incident, and the next successful check resolves it. People get a notification when an incident opens and when it resolves, never for each failure. A monitor that flips between up and down on every check is **flapping**, and a rule that alerts on every flip trains people to ignore alerts.

The alerter keeps no state in memory. Each round, it reads the newest three results and the open incident of each monitor from Postgres and decides again. Restart it at any moment, and the next round picks up where the last one stopped.

A **webhook** is a URL that accepts an HTTP `POST` and does something with it, such as posting a message to a chat channel. The alerter inserts the incident and sends the webhook inside one transaction, and commits only after the webhook answers with a `2xx` status. A webhook that fails rolls the insert back, and the next round tries both again. Notifications, too, arrive at least once: a crash between the webhook and the commit sends the same incident twice. The receiver spots a repeat by the `incident_id` and the `kind` of each event.

### Step 2: Enqueue the Due Monitors

Create `internal/queue/queue.go`. The scheduler needs one function:

<CodeFrom file="go/week09/your-monitor/internal/queue/queue.go" region="enqueue" lang="go" title="internal/queue/queue.go" />

`WITH due AS (UPDATE ... RETURNING m.id)` is a **data-modifying CTE**, short for common table expression: the `UPDATE` marks the due monitors and returns their IDs, and the `INSERT` turns each ID into a job. One statement does both, inside one transaction. `make_interval(secs => m.interval_seconds)` turns the interval column into a Postgres interval.

Three choices keep the queue correct:

- **One clock.** Every time comes from `now()` in Postgres, never from the clock of the machine that runs the scheduler. Two schedulers on two machines with clocks that disagree still agree on what is due.
- **No pile-up.** `NOT EXISTS` skips a monitor that still has a job waiting. When every worker is down, the queue holds one job per monitor, not one per round. `TestEnqueueAddsOneJobPerDueMonitor` fails without that line.
- **Two schedulers, one job.** When two schedulers run the `UPDATE` at the same moment, the second waits for the row locks of the first. After the first commits, Postgres checks the `WHERE` again against the new row, sees a fresh `last_enqueued_at`, and skips it. `TestTwoSchedulersDoNotQueueAMonitorTwice` runs four schedulers on 50 monitors and counts 50 jobs. A test transaction locks every monitor first, and the test waits until all four schedulers wait for it: the four `UPDATE`s overlap on every run, not only on a lucky one.

### Step 4: Retry a Failing Job

A job that fails, for example because of a panic or a failed insert, gets two more tries, further apart each time. That growing gap is called **backoff**. A job that fails on every try is a **poison job**, and after `MaxAttempts` the worker drops it:

<CodeFrom file="go/week09/your-monitor/internal/queue/queue.go" region="retry" lang="go" title="internal/queue/queue.go" />

`retry` runs in the same transaction, which still holds the job: no other worker takes it before the new `run_at` commits. A worker that dies on SIGKILL never reaches `retry`: its job comes back with the same `attempts`, and the next worker tries at once.

## Observe It

<ObserveIt>

The scheduler round line is the pulse of the queue. `queued` counts the jobs waiting, and `oldest_ms` is how long the oldest of them has waited past its `run_at`:

```txt
2026/10/11 07:02:53 round enqueued=1 queued=1 oldest_ms=2
```

Follow it with `docker compose logs --follow scheduler`, and read these signs:

- **`queued` equals `enqueued`, and `oldest_ms` stays under 1000.** The workers keep up: the jobs of the last round are done.
- **`queued` stays near the number of monitors, and `oldest_ms` grows every round.** No worker takes jobs: the workers are down, or each one waits for a database connection. `NOT EXISTS` keeps the queue from growing past one job per monitor.
- **`oldest_ms` climbs during busy minutes and falls after them.** The workers keep up on average but not at the peak. Raise `WORKERS`, or start a second worker container with `docker compose up --detach --scale worker=2`.

Postgres shows each worker in flight. `docker compose exec postgres psql -U monitor -d monitor` opens `psql`, the Postgres client:

```sql
SELECT state, count(*) FROM pg_stat_activity WHERE datname = 'monitor' GROUP BY state;
SELECT id, monitor_id, run_at, attempts FROM check_jobs WHERE attempts > 0;
```

During a round of checks, the `idle in transaction` row counts the checks in flight: each one holds a claimed job. The second query lists jobs that failed at least once and wait for a retry. A row there points to a bug in the worker or a database problem, not to a site that is down, because a failed check counts as a result. Week 13 turns `queued` into the `monitor_jobs_queued` gauge.

</ObserveIt>

## Operate It

<OperateIt>

**A worker gets SIGKILL in the middle of a check.** Try it: `docker compose kill --signal SIGKILL worker` while checks run. Postgres rolls back the open transactions, and the jobs wait in `check_jobs` with `attempts` unchanged. The container stays down, because Docker never restarts a container that a person stopped by hand, and `docker compose kill` counts as one. Run `docker compose start worker`, and it claims the jobs. No result is lost, and none is stored twice.

**A job crashes the worker process itself,** for example by running out of memory. The process dies before `retry`, the job never gains an attempt, and every worker that claims it dies too: a crash loop. A lease, from the At-Least-Once section, solves this case: the claim counts the attempt and commits before the check starts.

**The scheduler is down.** The queue empties, no new results arrive, and the alerter stays quiet: no results means no failures. A monitor that stops monitoring looks exactly like a site that is up. `SELECT max(checked_at) FROM check_results` shows the time of the newest check: when it is older than the shortest interval plus a minute, the checks have stopped. Week 18 turns that into a check freshness SLO.

**The webhook fails.** The alerter logs `round failed: monitor 1: webhook to hooks.example.com: status 500`, and no incident row exists yet. Each round tries again, every 10 seconds, until the webhook answers `2xx`. The status page shows the incident only once someone has been told.

**Too many connections.** Postgres accepts 100 connections by default. Each worker container opens up to `WORKERS` plus one, and the api, the scheduler and the alerter open their own pools. Past the limit, a new connection fails with `FATAL: sorry, too many clients already`. Count before you scale: three worker containers with `WORKERS=30` take 93 connections on their own.

| What you see | What it points to |
| --- | --- |
| `queued` near the number of monitors and `oldest_ms` growing | No worker claims jobs: the workers are down, stuck or out of connections |
| No new rows in `check_results`, and `queued=0` | The scheduler is down, or no monitors exist |
| A `DELETE /api/monitors/{id}` takes up to 5 seconds | A worker checks that monitor: the `DELETE` waits for the check, up to `-timeout` |
| `job 12: dropped after 3 attempts` in the worker log | A poison job: the same job fails on every try. The error on the line before names the cause |
| The alerter logs `round failed` every 10 seconds | The webhook or the database is down. The incident opens once both answer |
| Two notifications for one `incident_id` | The alerter died between the webhook and its commit, and sent the event again: at-least-once delivery |
| `FATAL: sorry, too many clients already` | Every connection slot of Postgres is taken: lower `WORKERS` or the number of containers |

</OperateIt>

## Side Lab

<SideLab title="Watch row locks from two psql sessions: FOR UPDATE, NOWAIT and SKIP LOCKED">

Postgres row locks drive the whole queue. Watch them from two terminals, without any Go code. Open `psql` in each terminal with `docker compose exec postgres psql -U monitor -d monitor`. These outputs come from Postgres 16, and Postgres 17 prints the same columns.

**1. Create a toy queue,** in terminal A:

```sql
CREATE TABLE lab_jobs (id int PRIMARY KEY, payload text);
INSERT INTO lab_jobs VALUES (1, 'first'), (2, 'second'), (3, 'third');
```

**2. Lock the first job in terminal A,** and leave the transaction open:

```sql
BEGIN;
SELECT id, payload FROM lab_jobs ORDER BY id LIMIT 1 FOR UPDATE;
```

**3. Try three claims in terminal B:**

```txt
monitor=# SELECT id, payload FROM lab_jobs ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;
 id | payload
----+---------
  2 | second
(1 row)

monitor=# SELECT id, payload FROM lab_jobs ORDER BY id LIMIT 1 FOR UPDATE NOWAIT;
ERROR:  could not obtain lock on row in relation "lab_jobs"
monitor=# SELECT id, payload FROM lab_jobs ORDER BY id LIMIT 1 FOR UPDATE;
```

`SKIP LOCKED` returns job 2 at once. `NOWAIT` fails at once instead of waiting. Plain `FOR UPDATE` hangs.

**4. Find the wait.** Open a third terminal with `psql` and ask what each session does:

```txt
monitor=# SELECT pid, state, wait_event_type, wait_event, left(query, 40) AS query FROM pg_stat_activity WHERE datname = 'monitor' AND pid <> pg_backend_pid();
 pid  |        state        | wait_event_type |  wait_event   |                  query
------+---------------------+-----------------+---------------+------------------------------------------
 5393 | idle in transaction | Client          | ClientRead    | SELECT id, payload FROM lab_jobs ORDER B
 5398 | active              | Lock            | transactionid | SELECT id, payload FROM lab_jobs ORDER B
(2 rows)
```

Terminal A is `idle in transaction`: it holds the lock and waits for you. Terminal B waits on `transactionid`, the transaction of A. `SELECT locktype, mode, granted FROM pg_locks WHERE NOT granted;` shows that request: a `ShareLock` with `granted` set to `f`, for false. When your monitor runs, its own sessions show up in the list too.

**5. Release it.** Type `COMMIT;` in terminal A, and terminal B returns job 1 at once. Run `DROP TABLE lab_jobs;` in A to clean up. A worker that hangs with an open transaction blocks others the same way. The Postgres setting `idle_in_transaction_session_timeout` ends such sessions after a time you choose.

</SideLab>
