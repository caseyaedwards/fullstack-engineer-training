## Concepts

### Scaling Out with the HorizontalPodAutoscaler

**Scaling out** adds copies of a program; **scaling up** gives one copy a bigger machine. A **HorizontalPodAutoscaler**, HPA for short, scales a Deployment out and back in. It needs one number per pod, and the simplest one is CPU.

k3s ships **metrics-server**, a small program that collects the CPU and memory use of every pod from the kubelet on each node every 15 seconds, and serves the latest numbers through the Kubernetes API. `kubectl top pods` reads them, and the HPA controller does too. The controller divides the CPU use of each pod by its CPU **request**, the share of a CPU that the pod asked for in <a href={weekHref(15)}>Week 15</a>, and averages the percentages. Every 15 seconds, it computes:

```txt
desired replicas = ceil(current replicas × current average / target average)
```

With two api pods at 140% of their request and a target of 70%, it asks for four. A pod without a CPU request has no percentage: the HPA shows `<unknown>` and does nothing.

Two defaults shape what you see. Scaling up happens at once, by up to four pods or double the count every 15 seconds. Scaling down waits for a **stabilization window** of 300 seconds and uses the highest count it computed in that window, which keeps the count from jumping with every spike.

That shared field causes the classic mistake. When your manifest says `replicas: 2` and the HPA has scaled to four, the next `kubectl apply` sets two again, and the HPA scales back up 15 seconds later. Remove `replicas` from every Deployment that an HPA scales.

CPU is a good signal for the api: every request costs CPU. It is a weak signal for the worker. A worker spends most of a check waiting on the network, and a long queue of slow sites leaves its CPU low. <a href={weekHref(13)}>Week 13</a> gave you the honest number, `monitor_jobs_oldest_seconds`. Scaling on a Prometheus metric needs an adapter that serves it through the Kubernetes API, such as prometheus-adapter or KEDA. This week, the worker scales on CPU, and you watch the queue age to judge whether CPU is enough.

### Rolling Updates and Rollbacks

Every change to the pod template of a Deployment, such as a new image tag or a new environment variable, creates a new **ReplicaSet** and a new **revision**. A **rolling update** moves the pods from the old ReplicaSet to the new one in steps. Two settings bound each step:

- `maxSurge`: how many pods above the wanted count can exist during the rollout.
- `maxUnavailable`: how many pods below the wanted count the rollout allows.

With `maxSurge: 1` and `maxUnavailable: 0`, the controller starts one new pod, waits until it is **available**, then stops one old pod, and repeats. Available means ready, and ready for `minReadySeconds` in a row: a pod that passes its first probe and crashes 5 seconds later never counts. When no step succeeds for `progressDeadlineSeconds`, Kubernetes marks the rollout as failed. The old pods keep serving, because none of them stops before a new one is available.

One race remains. When a pod is told to stop, the kubelet sends `SIGTERM` while the news of the endpoint removal is still on its way to Traefik and to nginx. For a moment, new requests still arrive at a pod that is shutting down, and they fail. A **preStop hook** runs before `SIGTERM`: a 5-second pause there keeps the pod serving while the rest of the cluster catches up. The `sleep` action of a hook, stable since Kubernetes 1.34, needs no `sleep` program in the image, which matters for images built `FROM scratch`, as yours are.

`kubectl rollout undo` switches the Deployment back to the pod template of the previous revision, as a new rolling update. It restores the pod template only: ConfigMaps, the HPA and the Services stay as they are. And it changes the cluster, not your repository. The next `deploy.yml` run from <a href={weekHref(14)}>Week 14</a> applies the manifests and the image tag it is given, and the bad version comes back. Use `undo` to stop the damage in seconds, then run `deploy.yml` with the commit SHA of the last good version to make the rollback stick.

### Rate Limits and Token Buckets

A **rate limit** caps how many requests of one client get answered in a span of time. The api needs one for three reasons: one visitor with a loop must not slow the status page for everyone, a scanner must not fill your logs, and each login guess costs a bcrypt check of about 0.3 seconds of CPU, which <a href={weekHref(11)}>Week 11</a> left uncapped across email addresses.

A **token bucket** holds up to `burst` tokens and refills at `rate` tokens per second. Each request takes one token. A request that finds the bucket empty gets `429 Too Many Requests` and a `Retry-After` header that says when a token is back. The burst absorbs a status page that loads twenty results at once; the rate caps a loop. The `golang.org/x/time/rate` package implements one bucket, and Traefik uses the same package inside its own rate limiter.

The hard part is the key. A per-client limit needs the client address, and behind proxies the api sees only the last proxy. Each proxy appends the address it received the request from to the `X-Forwarded-For` header, XFF for short. A client can send that header too, with any text in it. Only the entries that your own proxies appended are true, and they sit at the right end. The api trusts a list of networks, here the k3s pod network `10.42.0.0/16`, and walks the header from the right while each address belongs to one of them. The first address outside is the client.

Each api pod keeps its buckets in its own memory. With four replicas, a client whose requests Traefik spreads over all of them gets up to four times the limit. That is why the edge gets a limit too: Traefik sees every request before it spreads them. k3s runs one Traefik pod, which makes the Traefik limit the one for the whole cluster.

### Backups You Have Restored

<a href={weekHref(8)}>Week 8</a> set two rules: keep a backup on another machine, and restore it on a schedule. Two numbers describe a backup plan. The **recovery point objective**, RPO, is how much data you accept to lose: with a nightly dump, up to 24 hours of check results. The **recovery time objective**, RTO, is how long you accept the monitor to stay down while you restore. You do not know how long a restore takes until you time one. A **restore drill** does exactly that, on a schedule, into a new, empty server, and fails loudly when the newest dump is missing, too old or broken. The <a href={trackHref('backups')}>Backups track</a> covers physical backups with write-ahead log (WAL) archiving, which brings the RPO down to minutes.

`netip.Addr` is the Go value type for an IP address: it compares with `==` and works as a map key. `Unmap` turns `::ffff:203.0.113.7`, the IPv6 form of an IPv4 address, back into `203.0.113.7`, which keeps one client in one bucket. <CodeFrom file="go/week17/your-monitor/internal/ratelimit/ratelimit.go" region="limiter" lang="go" title="internal/ratelimit/ratelimit.go" />

`rate.NewLimiter(limit, burst)` is one bucket. `ReserveN(now, 1)` takes a token and says how long the caller has to wait for it. The api never waits: when the delay is above zero, `CancelAt` puts the token back and `Allow` returns the delay, which becomes `Retry-After`. Every method takes `now` as a value, which gives the tests a clock they control.

A map that grows with every new address is a memory leak that an attacker controls. The sweep has an exact rule: a bucket that has gone `refill` without a request is full again, and a full bucket is the same as a new one. Deleting it changes nothing for the client. `MaxBuckets` caps the map at 100,000 buckets, which took 18 MB in a test on the machine that built this page. Past that, new clients wait one refill time, until the sweep frees room.

### Step 12: Validate and Ship

Build the overlay and check every object against the schemas of Kubernetes 1.36 before the cluster sees it. `kubeconform` knows the built-in kinds. ## Observe It

<ObserveIt>

**The autoscalers.** Watch them update every 15 seconds:

```txt
$ kubectl get hpa --watch
NAME     REFERENCE           TARGETS       MINPODS   MAXPODS   REPLICAS   AGE
api      Deployment/api      cpu: 4%/70%   2         4         2          3m
worker   Deployment/worker   cpu: 9%/70%   1         3         1          3m
```

`cpu: <unknown>/70%` means the HPA has no number: metrics-server is not running, which `kubectl top pods` confirms with an error, or the container has no CPU request. `kubectl describe hpa api` lists each scaling decision with its reason under **Events**.

**The worker queue.** CPU does not see the queue; the scheduler metrics from Week 13 do. Forward its port and read the age:

```sh
kubectl port-forward deploy/scheduler 2112:2112 &
curl -s localhost:2112/metrics | grep '^monitor_jobs_oldest_seconds'
```

An age that climbs while the worker HPA sits at one replica means CPU is the wrong signal for your sites, and the queue age is the number to scale on.

**Rollouts.** `kubectl rollout status deployment/api` follows one rollout to its end:

```txt
Waiting for deployment "api" rollout to finish: 1 out of 2 new replicas have been updated...
Waiting for deployment "api" rollout to finish: 1 old replicas are pending termination...
deployment "api" successfully rolled out
```

**Limits.** Each refused request counts in `http_requests_limited_total`, under the limit it hit: `client` for a busy visitor, `login` for guesses from one address, `login_all` for guesses from many. A steady rise of `login_all` is an attack on your login, not a busy visitor. Traefik refusals never reach the api; they show as `429` in the Traefik access log once you add `logs.access.enabled: true` to the values in the same `HelmChartConfig`.

**Backups.** `kubectl get cronjob` shows `LAST SCHEDULE` for each CronJob, and `kubectl get jobs` lists the recent runs with their completions. `kubectl logs job/<name>` prints the line of `backup.sh` or the report of the drill. <a href={weekHref(18)}>Week 18</a> turns a missed backup into an alert.

</ObserveIt>

## Operate It

<OperateIt>

**Load drill: watch the api scale.** The api limit stops a load test from one address, which is the point of it. Turn it off for the drill with a change that rolls out like any other:

```sh
kubectl annotate deployment/api kubernetes.io/change-cause="load drill: RATE_LIMIT=0" --overwrite
kubectl set env deployment/api RATE_LIMIT=0
kubectl rollout status deployment/api
```

The load comes from a pod inside the cluster, which talks to the api Service directly, past Traefik. The `httpd` image carries `ab`, the Apache HTTP server benchmarking tool. A plain `kubectl run` fails here: the namespace enforces the restricted Pod Security Standard of Week 16, and the image starts as root. The pod file sets what restricted asks for:

<CodeFrom file="go/week17/your-monitor/deploy/k8s/load/load.yaml" region="load-pod" lang="yaml" title="deploy/k8s/load/load.yaml" />

```sh
kubectl apply -f deploy/k8s/load/load.yaml
kubectl wait --for=condition=Ready pod/load --timeout=2m
kubectl logs -f pod/load
```

In a second terminal, `kubectl get hpa api --watch` shows the CPU climb past 70% and the replicas go to three, then four. When `ab` ends, the count stays at four for the five-minute window, then drops. Delete the pod with `kubectl delete pod load`.

**Roll it back.** The drill change is revision 2 of the api:

```txt
$ kubectl rollout history deployment/api
deployment.apps/api
REVISION  CHANGE-CAUSE
1         <none>
2         load drill: RATE_LIMIT=0

$ kubectl rollout undo deployment/api
deployment.apps/api rolled back
```

The undo starts a rolling update to the template of revision 1, and the history lists it again as revision 3. `kubectl set env deployment/api --list` shows `RATE_LIMIT=10` again.

**A bad image.** `deploy.yml` with a SHA that CI never built leaves the new pod in `ImagePullBackOff`. With `maxUnavailable: 0`, the two old pods keep serving. After `progressDeadlineSeconds`, 180, `kubectl rollout status` ends with `error: deployment "api" exceeded its progress deadline`, and the workflow fails. Run `kubectl rollout undo deployment/api`, then run `deploy.yml` again with the last good SHA, which the run summary of Week 14 lists.

**Everyone shares one bucket.** Visitors get 429 after a handful of requests, and `kubectl logs deploy/api | grep '"client"'` shows the same `10.42.x.x` address on every line. The client address dies at the node: `externalTrafficPolicy` is still `Cluster`, or the `HelmChartConfig` landed in the wrong folder. When `externalTrafficPolicy` reads `Local`, compare `TRUSTED_PROXIES` with the pod network of your node.

**The restore drill.** Run it now, without waiting for Sunday:

```sh
kubectl create job --from=cronjob/restore-drill drill-now
kubectl wait --for=condition=complete job/drill-now --timeout=15m
kubectl logs job/drill-now
```

Write the restore time down next to the size of the dump: that is how long a restore of your data takes, today. The drill fails in three named ways. `FAILED: no dump` means the backup CronJob never wrote one: `kubectl logs` of its last job says why, such as a wrong password in the Secret. `FAILED: ... hours old` means the backups stopped. `FAILED: pg_restore` means the dump is broken: keep the older dumps, which `KEEP_DAYS` holds for 14 days, and find out what cut it short.

| What you see | What it points to |
| --- | --- |
| `cpu: <unknown>/70%` in `kubectl get hpa` | No metrics-server, or no CPU request on the container |
| HPA replicas drop and climb back after each deploy | A `replicas` field in the manifest still fights the HPA |
| New pod in `ImagePullBackOff`, rollout fails at 180 s | The image tag does not exist: undo, then redeploy the last good SHA |
| `502` answers during every rollout | No preStop pause: requests reach pods after `SIGTERM` |
| Visitors get 429 together, one `client` address in the log | `externalTrafficPolicy` is `Cluster`: the node hides the client |
| The site answers 404 after the Middleware change | The annotation names a Middleware that does not exist |
| The drill fails with `hours old` | The backup CronJob stopped writing dumps |

## Side Lab

<SideLab title="Time a restore of one million rows and find where the time goes">

The drill on your server restores a small database in a second. Build a bigger one on your laptop to see how restore time grows, and which part grows. Use the Postgres of Compose from <a href={weekHref(8)}>Week 8</a>, with `PGHOST`, `PGUSER` and `PGPASSWORD` set to reach it, and the Postgres 17 tools.

**1. Make a million results.** Create a database `sidelab`, restore one of your dumps into it, then add rows in `psql`:

```sql
insert into check_results (monitor_id, checked_at, up, status_code, total_ms)
select 1 + (g % 3), now() - g * interval '10 seconds', g % 50 <> 0, 200, g % 300
from generate_series(1, 1000000) g;
```

On the machine that built this page, the insert took 14 seconds, the database grew to 132 MB, and `pg_dump --format=custom --file=side.dump` wrote 7.9 MB in 1.5 seconds. The dump holds rows, not indexes, and compresses well.

**2. Restore in three sections.** `pg_restore --section` runs one part of a dump at a time: `pre-data` creates the tables, `data` copies the rows, `post-data` builds the indexes and constraints. Time each one into an empty database `side_r`:

```sh
for s in pre-data data post-data; do
  echo "$s"
  time pg_restore -d side_r --no-owner --exit-on-error --section="$s" side.dump
done
```

One run on the same machine took 0.36 seconds for `pre-data`, 3.5 for `data` and 2.7 for `post-data`. The indexes cost three quarters of the time the rows cost: Postgres rebuilds every index of `check_results` from scratch.

**3. Add jobs.** Drop and recreate `side_r`, then run the full restore with `--jobs=1`, and again with `--jobs=4`. The same machine took about 4.3 and 3.7 seconds. `--jobs` runs whole tables and whole indexes in parallel, never parts of one: with one big table, the copy stays on one core and only the index builds overlap.

**4. Predict.** Your live `check_results` grows by one row per monitor per interval. Compute its row count a year from now, scale the times from step 2, and decide whether a restore that long fits the RTO you accept for a status page.

</SideLab>
