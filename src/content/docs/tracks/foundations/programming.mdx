Every backend program in this course moves values between functions, shares some of them through pointers, and decides what each failure means. Go makes all three explicit in the code, where TypeScript hides two of them behind the runtime. This page collects the ideas the weeks rely on, compares each one with TypeScript, and ends with one function that sorts errors into classes in both languages.

## What It Is

### Values and Types

A **type** says what a value holds and which operations work on it. Go checks types when it compiles, as `tsc` does. Go has no `as any` cast that silences the checker: a **type assertion** such as `err.(*StatusError)` checks the type again at run time, and a mismatch either panics or, in the two-result form, returns `false`. Every variable starts at the **zero value** of its type: `0`, `""`, `false`, or `nil` for pointers, slices, maps, interfaces and errors.

Go copies a value each time you assign it or pass it to a function. For an `int` that copy costs nothing. For a struct, a group of named fields, Go copies every field. TypeScript copies only primitives this way: an object variable holds a reference, and two variables can point at one object. In Go, you choose: pass the struct itself to get a copy, or pass a pointer to share it.

### Pointers, the Stack and the Heap

A **pointer** holds the memory address of a value. `&r` takes the address of `r`, and `*Result` is the type of a pointer to a `Result`. A function that receives a pointer changes the caller value. A function that receives a copy changes only its copy.

A running program keeps values in two places:

- The **stack**: a block of memory per goroutine, the Go lightweight thread, that grows and shrinks with function calls. A call pushes a frame for its local variables. The return pops the frame, and its memory is free at once, with no cleanup work.
- The **heap**: memory shared by the whole program. A value on the heap stays until nothing points at it, and then the **garbage collector**, a part of the Go runtime, frees it.

The Go compiler decides where each value lives, through **escape analysis**. A value whose address never outlives its function stays on the stack. A value whose address outlives its function, because the function returns a pointer to it or stores the pointer somewhere longer-lived, **escapes** to the heap. You never choose by hand, and `new` or `&` does not force the heap. `go build -gcflags=-m` prints each decision, such as `&Result{...} escapes to heap`. In TypeScript, the JavaScript engine makes these choices out of sight, and you never see a pointer at all.

### Methods and Interfaces

A **method** is a function attached to a type through a **receiver**, the parameter before the name: `func (e *StatusError) Error() string`. A pointer receiver works on the original value. A value receiver works on a copy.

An **interface** lists methods, and any type with those methods **satisfies** it, with no `implements` keyword. TypeScript compares object shapes the same way. A Go interface value holds two things: the concrete type and the value or pointer inside. That pair matters in the next section, because asking an error for its type means asking which concrete type sits inside the interface.

### Errors Are Values

Go has no exceptions for expected failures. A function that can fail returns `error` as its last result, and the caller checks it with `if err != nil` straight away. `error` is an interface with one method, `Error() string`. A **panic** exists too, but only for bugs, such as reading past the end of a slice.

As an error travels up, each layer adds context by **wrapping** it: `fmt.Errorf("check %s: %w", url, err)` returns a new error whose message adds the text in front and whose `Unwrap` method returns `err`. The `%w` verb keeps the original inside. The `%v` verb copies only its text, and the chain ends there. Since Go 1.20, one `fmt.Errorf` call can hold several `%w` verbs, and `errors.Join` combines a list of errors into one.

Callers inspect a chain in two ways:

- A **sentinel error** is one shared value, such as `io.EOF` or the `ErrTimeout` below. `errors.Is(err, ErrTimeout)` walks the chain and reports whether any error in it equals the sentinel.
- An **error type** carries data, such as a status code. `errors.As(err, &se)` walks the chain, finds the first error with the same type as `se`, and stores it in `se`. Go 1.26 adds `errors.AsType`, a generic form that returns the match. The examples here target Go 1.24 and use `errors.As`.

TypeScript reaches the same design through the `cause` option, standard since ES2022, short for ECMAScript 2022: `new Error('check example.com', { cause: err })` keeps the original error on `.cause`. TypeScript has no `errors.Is`, which is why the TypeScript twin below walks the chain itself.

## Common Mistakes

- **Wrapping with `%v` instead of `%w`.** The message reads the same, but the chain ends at that layer, and `errors.Is` and `errors.As` find nothing below it. Every timeout counts as `other`. Use `%w` whenever a caller can need the original error.
- **Comparing errors with `==` or by message.** `err == ErrTimeout` fails as soon as anyone wraps the error, and matching on `err.Error()` text breaks when a library rewords its message. Use `errors.Is` for sentinels and `errors.As` for types.
- **Mixing a value and a pointer form of an error type.** With a value receiver on `Error`, code can return `StatusError{Code: 503}` while `Classify` asks `errors.As` for a `*StatusError`. The types differ, the search finds nothing, and a `503` counts as `other`. Give `Error` a pointer receiver, as `StatusError` does: the compiler then rejects a plain value where an error goes.
- **Returning a typed nil pointer as an error.** A function that returns `var se *StatusError` as its `error` result returns an interface that holds a type and a nil pointer. That interface is not `nil`, and the caller sees a failure that never happened. Return the literal `nil` on success.
- **Sharing a struct by copying it.** A function that takes `Result` instead of `*Result` changes its own copy, and the caller never sees the change. When a function has to change the value, take a pointer.
- **Expecting `try` and `catch` behavior.** A TypeScript habit is to let errors fly to one handler at the top. In Go, an unchecked error is silently ignored. Check every `err` where it comes back, and handle it, wrap it or return it.

## Going Deeper

- **Generics:** Go 1.18 added type parameters, and functions such as `slices.Sort` and `errors.AsType` use them. Learn them to read the standard library and to avoid writing the same helper for each type.
- **Escape analysis in practice:** run `go build -gcflags=-m` on a package and read why each value escapes. It explains most allocation counts in a benchmark.
- **The Go memory model:** it defines when a write in one goroutine becomes visible to another. Week 5 relies on it every time it uses a channel or a mutex.
- **Interface internals:** an interface value is a type and a pointer, which explains the typed nil mistake above and the cost of calling a method through an interface.
- **Iterators:** Go 1.23 added range over functions. The `iter` package and the `maps` and `slices` helpers return them.
