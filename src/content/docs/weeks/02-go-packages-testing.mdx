## Concepts

### Modules, Packages and Import Paths

Week 1 introduced modules and packages. This week, you use both, and import one package from another:

- A **module** is your whole project, named by the first line of `go.mod`: `module github.com/your-user/your-monitor`. The name is the **module path**.
- A **package** is one folder of `.go` files. Every file in the folder starts with the same `package` line, and the files share one namespace: a function in `list.go` calls a function in `check.go` with no import.
- An **import path** finds a package: the module path plus the folder. The `check` folder in your module has the import path `github.com/your-user/your-monitor/check`. Standard library packages have short paths, such as `net/http`, because they belong to Go itself.

The `package` line names the package. By convention, the name is the last part of the import path: the files in `check/` start with `package check`. Code that imports the package uses that name as a prefix, as in `check.URL`. The prefix is part of the name every caller reads, which is why Go code avoids stutter: `check.URL` reads well, and `check.CheckURL` repeats itself.

From outside a package, you reach only its **exported** names, the ones that start with a capital letter. Week 1 named the function `checkURL` because it lived in `package main` and nothing else called it. Moved into `check`, it becomes `URL`, exported, because `main` calls it from another package. A lowercase helper such as `valid` stays private: a call to `check.valid` from `main.go` stops the build with `undefined: check.valid`.

Imports run in one direction. `main` imports `check`, and `check` never imports `main`. Go refuses an import cycle at build time, with `import cycle not allowed`. That rule keeps the packages a tree you can read from the top down.

### Methods

A **method** is a function attached to a type. In `func (r Result) Up() bool`, the extra parameter before the name, the **receiver**, names the value the method works on. Call it as `r.Up()`, like a method on a TypeScript class. Go has no classes: any type you define can have methods, and each method is declared next to the type, not inside a class body. A receiver written `(r Result)` gets a copy of the value. A receiver written with a pointer, such as `(b *spyBody)`, works on the original and can change it. You write one of each this week.

### Interfaces

An **interface** type lists methods. Any type that has those methods, with the same names, parameters and results, **satisfies** the interface. The type never mentions the interface: Go has no `implements` keyword. TypeScript works the same way, because it also compares shapes instead of declarations. Two differences matter. A Go interface lists only methods, never fields. And the Go compiler checks the match where you pass or assign a value, and stops the build when a method is missing.

You have used one interface since Week 1: `error` is an interface with one method, `Error() string`. Three more come up this week:

| Interface | Method | Types that have it |
| --- | --- | --- |
| `io.Reader` | `Read(p []byte) (n int, err error)` | an open file, a response body, `strings.NewReader("...")` |
| `fmt.Stringer` | `String() string` | your `Result`: `fmt.Println` calls `String` to print it |
| `check.Getter` | `Get(url string) (*http.Response, error)` | `*http.Client`, and the fake in your tests |

`Getter` is yours. The `check` package defines it, and the `net/http` package has never heard of it. `*http.Client` satisfies it anyway, because its `Get` method has exactly that signature. Go code defines a small interface like this one where it is used, not where it is implemented, with only the methods the user needs. `check.URL` needs one method from a client, which makes `Getter` one method long.

That one change makes `check.URL` testable without a network. In Week 1, `checkURL` took a `*http.Client`, a concrete type: only a real client fits. `URL` takes a `Getter`, and any value with the right `Get` method fits.

### How Go Runs Tests

Tests live in files whose names end in `_test.go`, next to the code they test. `go build` ignores those files. `go test` compiles them together with the package into a separate test binary, runs it, and reports the result. Nothing needs installing: the `testing` package in the standard library is the framework.

A test is a function whose name starts with `Test` and that takes one parameter, `t *testing.T`. There is no `expect` and no assertion library. You compare with a plain `if`, and report a problem through `t`:

- `t.Errorf`: records a failure with a message and carries on, to report every broken check in one run.
- `t.Fatalf`: records a failure and stops the current test at once. Use it when the rest of the test makes no sense, such as after an unexpected error.

By convention, the message names what you got and what you wanted: `Status = 404, want 200`. A test file declares one of two packages. `package check` puts the tests inside the package: they can call unexported names such as `valid`, which makes them white-box tests. `package check_test` makes them a separate package that imports `check` as any caller does: black-box tests. This page uses `check_test`, because the exported names are the contract that `main` relies on.

`go test ./...` tests every package in and below the current folder, and runs several packages at once. Inside one package, the tests run one at a time, in the order they appear in the source files. Before it runs them, `go test` also runs a short list of `go vet` checks, which catch mistakes such as a `Printf` verb that does not match its argument. When nothing has changed since a passing run, `go test` prints the stored result with `(cached)` instead of running the tests again.

### Table-Driven Tests and Subtests

Most Go tests are **table-driven**: a slice of cases, one struct per row, and one loop that runs the same checks on each row. It is the Go form of `test.each` in Vitest and Jest. A new case is a new row, and the table reads like the equivalence classes and boundary values you design anyway.

Inside the loop, `t.Run(name, func(t *testing.T) { ... })` runs each row as a **subtest**. A subtest reports on its own line, fails on its own, and runs on its own when you ask for it by name. A `t.Fatalf` inside a subtest stops only that row: the loop carries on with the next one.

The rows use an anonymous struct type: `[]struct{ name string; ... }` declares the type and the slice in one go, because no other code needs the type. Since Go 1.22, each pass of the loop gets its own copy of the loop variable `tt`. That matters once a subtest calls `t.Parallel()`, which this page shows in Operate It: the subtest then runs after the loop has moved on, and with one shared `tt`, every subtest sees the last row. Older Go code copies the variable first, with `tt := tt`.

### Test Doubles: Test Servers and Fakes

This week tests HTTP code in two ways. The `net/http/httptest` package starts a real HTTP server inside your test process, on `127.0.0.1` and a free port that the operating system picks. `srv.URL` holds its address, such as `http://127.0.0.1:38417`. Your code sends real requests over a real connection, and the test decides what the server answers. The tests run in milliseconds and need no internet. A **fake** is a type you write that satisfies an interface, here `Getter`. The standard library has no mocking library. This page writes the fake by hand: a struct and one method. A fake reaches cases a server cannot. It returns an error without waiting for a timeout, and it hands back a response body that records whether your code closed it, which is the leak Week 1 warns about.

Two methods of `t` keep test helpers short:

- `t.Helper()`: marks a function as a test helper. When a check inside it fails, the failure message names the line in your test that called the helper, not the line inside the helper.
- `t.Cleanup(f)`: runs `f` after the test and all its subtests finish. A helper that starts a server registers `srv.Close` with it, and the caller cannot forget to stop the server.

### Step 5: Test URL with a Fake

A test server cannot tell you whether `URL` closed the response body. A fake can. Add it to `check_test.go`:

<CodeFrom file="go/week02/your-monitor/check/check_test.go" region="fake" lang="go" title="check/check_test.go" />

`fakeGetter` satisfies `Getter` with one method, `Get`, which returns whatever the test put in its fields. Its parameter `url` goes unused, which Go allows for parameters.

`spyBody` is the response body. The `Body` field of `http.Response` has the type `io.ReadCloser`, an interface with two methods: `Read` and `Close`. `spyBody` gets `Read` through **embedding**: a field with a type and no name, here `io.Reader`, whose methods become methods of the struct. It adds its own `Close`, which records the call. In test-double terms, `fakeGetter` is a stub and `spyBody` is a spy.

`Close` has a pointer receiver, `(b *spyBody)`, because it changes the struct. That is also why the test creates the body with `&spyBody{...}`. `ParseList` takes an `io.Reader`, not a file name. `main` passes it an open file, and the tests pass `strings.NewReader`, which reads from a string. Neither caller needs a change to `ParseList`, and the tests need no files on disk.

- `bufio.NewScanner(r)`: wraps the reader. Each call to `scanner.Scan()` reads the next line, and returns `false` at the end of the input. `scanner.Text()` returns the line without its line ending, whether that is `\n` or the `\r\n` of a Windows file.
- `for n := 1; scanner.Scan(); n++`: counts lines from `1` while it reads, to name them in errors.
- `strings.TrimSpace`: removes spaces, tabs and other white space at both ends. A comment after a URL on the same line does not work: `https://example.org # main site` has a space inside, and `url.Parse` rejects it. Put comments on their own lines.
- `scanner.Err()`: reports a read error after the loop ends. The scanner raises one error of its own: it refuses a line longer than 64 KiB with `bufio.Scanner: token too long`.
- `errors.Join(errs...)`: combines every line error into one `error` whose message has one line per error. The `...` passes the slice as separate arguments. The caller gets every bad line in one run, not only the first.
- `valid`: parses the line with `url.Parse` from `net/url`, and accepts it when it has an `http` or `https` scheme and a host. `example.com`, `ftp://example.com` and `https://` all fail.

When the error is not `nil`, `ParseList` returns a `nil` slice. That is the Go convention: a caller checks the error first, and ignores the other results when it is set.

### Step 9: Run Everything

Run the full suite with the race detector and coverage. On Linux and WSL, `-race` needs a C compiler. Without one, `go test` stops with `go: -race requires cgo; enable cgo by setting CGO_ENABLED=1`. Install one with `sudo apt install gcc` on Ubuntu or WSL. On macOS, `-race` needs no C compiler.

```txt
$ go test -race -cover ./...
	github.com/your-user/your-monitor		coverage: 0.0% of statements
ok  	github.com/your-user/your-monitor/check	1.130s	coverage: 100.0% of statements
```

`-race` builds the test binary with the **race detector**, which watches every memory access while the tests run. It fails a test when two goroutines, functions that run at the same time, touch the same memory and at least one writes, with no synchronization such as a mutex between them. Your code starts no goroutines of its own yet, but `net/http` and `httptest` start several. The detector finds a race only in code that a test runs, which is why you run it with every test run, not once. [Operate It](#operate-it) shows it catching a bug in test code.

`-cover` reports **statement coverage**: the share of statements that at least one test runs. `main` shows `0.0%` because it has no tests. That is a deliberate trade: `main` holds only the wiring, and everything with logic lives in `check`, at `100%`.

Then build and run the monitor. Your numbers differ from this example:

```txt
$ go build
$ ./your-monitor -file urls.txt
up url=https://example.com status=200 latency_ms=118
up url=https://example.org status=200 latency_ms=97
$ echo $?
0
```

## Operate It

<OperateIt>

**A broken URL file.** A monitor that skips a mistyped line checks fewer sites than you think, and nobody notices. Yours refuses the whole file instead:

```txt
$ cat bad.txt
# Sites your monitor checks
https://example.com
example.org

https://example.net # backup
ftp://example.com
$ ./your-monitor -file bad.txt
bad.txt:
line 3: "example.org" is not an http or https URL
line 5: "https://example.net # backup" is not an http or https URL
line 6: "ftp://example.com" is not an http or https URL
$ echo $?
2
```

You get every bad line, with its number, in one run. The comment on line 1 and the blank line 4 count toward the numbers, which makes them match the line numbers in your editor. The exit code `2` tells a script that the configuration is wrong, which is a different problem from a site that is down.

The table lists other messages you can meet this week. The monitor exits with `2` for each of the first four:

| What you see | What it means |
| --- | --- |
| `open urls.txt: no such file or directory` | The path is wrong, or you run the binary from another folder: a relative path starts from the current folder |
| `urls.txt: no URLs to check` | The file holds only comments and blank lines |
| `urls.txt:` and `bufio.Scanner: token too long` | One line is longer than 64 KiB: the file is not a URL list |
| `missing -file` and the usage text | The command has no `-file` command-line flag |
| `go: -race requires cgo; enable cgo by setting CGO_ENABLED=1` | Linux or WSL without a C compiler: run `sudo apt install gcc` |

**A pass that hides a failure.** `go test` caches a passing result, and prints `(cached)` when neither the code nor the files the tests read have changed. A test that calls a real site, such as `https://example.com`, depends on something outside the code: the site goes down, and the cache keeps showing the old pass. Run `go test -count=1 ./...` to run every test for real, and keep the tests in `check` free of the internet, as they are now. `-count=50` runs every test 50 times: a test that fails one run in ten fails at least once with a 99.5% chance.

**A server that stops before its subtests.** Call `t.Parallel()` as the first line of a subtest, and the subtests of that test run at the same time, after the parent test function returns. Add this test to `check_test.go`. It looks correct:

```go
func TestURLInParallel(t *testing.T) {
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {}))
	defer srv.Close()
	for _, name := range []string{"first", "second", "third"} {
		t.Run(name, func(t *testing.T) {
			t.Parallel()
			got := check.URL(&http.Client{Timeout: time.Second}, srv.URL)
			if !got.Up() {
				t.Errorf("got %v, want up", got)
			}
		})
	}
}
```

Every subtest fails, with a line that ends in `connect: connection refused", want up`. The `defer` runs when the parent function returns, and that happens before the parallel subtests start: the server is already closed. Replace `defer srv.Close()` with `t.Cleanup(srv.Close)`, which waits for every subtest, and the test passes. Note that `%v` prints the `Result` through its `String` method.

**A data race in test code.** Keep the parallel test, declare `checked := 0` before the loop, and add `checked++` after the `check.URL` call in the subtest. `go test ./check` passes. `go test -race ./check` fails with `WARNING: DATA RACE`, two stack traces that both point at the `checked++` line, and `race detected during execution of test`. Three subtests write the same variable at the same time. Without `-race`, nothing reports it: the test passes, and Go gives no guarantee about the final count. Delete the test when you are done.

</OperateIt>

## Side Lab

<SideLab title="Fuzz ParseList and let Go find the inputs you did not think of">

A table test checks the cases you choose. A **fuzz test** generates inputs for you: Go starts from a few seed inputs, changes them at random, and keeps every input that reaches new code. It runs until an input fails a check, or until the time limit you set runs out. Fuzzing suits a parser such as `ParseList`, which accepts any text at all.

**1. Write the fuzz test.** A fuzz test has a name that starts with `Fuzz` and takes `f *testing.F`. Create `check/fuzz_test.go` with this test, plus the imports `net/url`, `slices`, `strings`, `testing` and your `check` package:

<CodeFrom file="go/week02/your-monitor/check/fuzz_test.go" region="fuzz" lang="go" title="check/fuzz_test.go" />

A fuzz test cannot know the right answer for a random input. Instead, it checks **properties** that hold for every input: `ParseList` never panics, every URL it accepts is a valid `http` or `https` URL, and writing the accepted URLs back out gives the same list.

**2. Fuzz.** A plain `go test ./check` runs the fuzz test once per `f.Add` seed, as a normal test. The `-fuzz` command-line flag turns on the generator. It works on one package at a time, and `-fuzztime` sets the time limit. This excerpt leaves out the progress lines between the first two and the last:

```txt
$ go test -run '^$' -fuzz=FuzzParseList -fuzztime=10s ./check
fuzz: elapsed: 0s, gathering baseline coverage: 0/2 completed
fuzz: elapsed: 0s, gathering baseline coverage: 2/2 completed, now fuzzing with 4 workers
fuzz: elapsed: 11s, execs: 178829 (7232/sec), new interesting: 154 (total: 156)
PASS
```

`-run '^$'` matches no test name, which skips the normal tests. `execs` counts the inputs tried. `new interesting` counts the inputs that reached new code: Go keeps them in its cache folder as the starting point for the next run.

**3. Plant a bug.** Replace the body of `valid` with a shortcut, `return strings.HasPrefix(s, "http://") || strings.HasPrefix(s, "https://")`, and remove the `net/url` import from `list.go`. Fuzz again. In a test run for this page, the fuzzer reported:
