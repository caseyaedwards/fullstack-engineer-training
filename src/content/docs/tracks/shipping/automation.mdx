Automation turns the commands you type into files that a machine runs the same way every time. A command you run by hand lives in your shell history and your memory. A command in a script, a Makefile or a playbook lives in Git, where a colleague reviews it, and runs the same at 03:00 as at noon. As a full-stack engineer, you automate three kinds of work: the commands of a repository, the jobs that run on a schedule, and the configuration of the servers your code runs on.

## What It Is

### Steps or a State

Automation comes in two styles.

An **imperative** script lists steps: install this package, append this line, restart this service. It does exactly what it says, every time it runs. Run it twice, and it appends the line twice and restarts the service twice. When a step fails halfway, the machine sits in a state that no file describes.

A **declarative** tool takes a **desired state**. For chrony, the service that keeps the system clock in sync, that state reads: the package is present, its configuration file holds these lines, its service runs. On each run, the tool compares that state with the machine, and changes only what differs. A task that finds the machine already right does nothing and reports `ok`. That property is **idempotence**: running the automation once or ten times leaves the machine in the same state. Week 9 uses the same word for a queue job that does no harm when it runs twice.

Idempotence turns a run into a check. A second run that reports zero changes proves that the first run reached the desired state. A run that reports changes on a machine nobody touched finds **drift**: a change someone made by hand, outside the automation.

### Three Tools and When to Reach for Each

| Tool | Reach for it when | Move on when |
| --- | --- | --- |
| Shell script | You glue a few commands together on one machine, such as a backup in a container or a Git hook | It needs to know the state of the machine before it acts, or it passes 100 lines |
| Makefile | A repository needs short, shared names for its commands: `make test`, `make lint`, `make ci` | The recipes grow logic of their own: move that logic into a script and call the script |
| Ansible playbook | You configure one or more servers over SSH: packages, files, services, users | You create the servers themselves: a provisioning tool such as Terraform or OpenTofu does that |

The three combine. A Makefile target runs a script, and a playbook copies a script to a server and schedules it.

### Shell Scripts That Fail Loudly

A **shell script** is a file of commands for a shell such as `sh` or `bash`. By default, the shell runs the next line after a command fails, and a backup script that fails at the dump goes on to upload an empty file. Start every script with `set -eu`:

- `-e`: exits at the first command that fails.
- `-u`: exits when the script reads a variable that is not set, instead of reading an empty string.
- In bash, add `-o pipefail`: a pipeline such as `pg_dump | gzip` then fails when `pg_dump` fails, not only when `gzip` does.

Quote every variable, as `"$file"`: unquoted, a value with a space splits into two arguments. **ShellCheck**, a linter for shell scripts, finds these mistakes before they run.

### Makefiles as the Front Door

`make` runs commands by name. A `Makefile` holds **rules**: a target, a colon, its prerequisites, and below them the **recipe**, each line indented with one tab. Make rebuilds a file target only when it is missing or older than a prerequisite. Most targets in a Go repository name commands rather than files, and the `.PHONY` line declares them as such. Without that line, a file named `test` in the folder makes `make test` report that the target is up to date and run nothing.

A Makefile is the front door of a repository: whoever clones it, a colleague or a continuous integration runner, CI for short, types `make ci` and runs every check, in the same order, with the same options.

### Ansible in One Page

**Ansible** configures servers over SSH. It installs no agent: for each task, it copies a small Python program, called a **module**, to the server, runs it, and reads back a JSON result that says `ok`, `changed` or `failed`. The vocabulary:

- **Control node:** the machine you run `ansible-playbook` on, such as your laptop or a CI runner.
- **Inventory:** the list of servers, called **managed nodes**, sorted into groups, such as `monitor`.
- **Playbook:** a file in YAML, an indented text format for data, that holds a list of **plays**. A play maps a group of hosts to a list of **tasks**.
- **Task:** one call to one module with its arguments, such as `ansible.builtin.package` with `name: chrony` and `state: present`. A task describes a state, and the module works out the steps.
- **FQCN:** the fully qualified collection name of a module, such as `ansible.builtin.template`. Modules ship in **collections**. A short name such as `template` resolves at run time, and the full name always means one module.
- **Facts:** what Ansible learns about a host at the start of a play: the distribution, the package manager, the addresses. `ansible.builtin.package` reads the package manager fact to call `apt` on Ubuntu and `dnf` on Fedora.
- **Become:** runs the task as another user, `root` by default, through `sudo`, the Unix tool for that.
- **Template:** a file with Jinja2 placeholders such as `{{ chrony_pool }}`, which Ansible fills in from variables and writes to the host.
- **Handler:** a task that runs only when another task reports `changed` and **notifies** it by name. A handler runs once, however many tasks notify it: after the last task of its section, `pre_tasks`, `tasks` or `post_tasks`, or earlier at an `ansible.builtin.meta: flush_handlers` task.

### Check Mode and Honest Tasks

`ansible-playbook --check` is a dry run: each module that supports it reports the changes it finds necessary, and makes none. `--diff` adds the line-by-line difference for every file a task plans to write. Together they catch drift and a wrong template before either reaches the server. Check mode has two limits:

- Each task sees the server as it is, not as the earlier simulated tasks leave it. On a fresh server, the package task reports `changed` and installs nothing, and the service task then fails: no chrony service exists yet.
- `validate`, the template option that tests a new file before it replaces the old one, runs only on a real run. A template with a typo passes `--check`.

On a fresh server, run the playbook for real. Before each later change, run it with `--check --diff`, and read the diff the way you read a pull request.

A module such as `ansible.builtin.template` knows its own state: it compares a checksum of the rendered file with the file on the host. `ansible.builtin.command` and `ansible.builtin.shell` run whatever you hand them, and cannot know whether the command changed anything. They report `changed` on every run, which breaks the zero-changes check and fires every handler they notify. Make each one honest:

- `creates: /path`: skips the command when that file exists. `removes: /path` skips it when the file is missing.
- `changed_when`: decides from the result, such as `changed_when: false` for a command that only reads.

Better still, look for a module that does the job: `ansible.builtin.user` instead of `useradd`, `ansible.builtin.lineinfile` instead of `echo >>`.

## Common Mistakes

- **A `command` or `shell` task without `changed_when` or `creates`.** It reports `changed` on every run, fires its handlers every time, and hides real drift among false changes. Find a module that does the job, or add `creates`, `removes` or `changed_when`.
- **Short module names.** `package:` runs whatever module a local `library/` folder or a `collections:` keyword puts behind that name, and `ansible-lint` fails it under its `fqcn` rule. Write `ansible.builtin.package`.
- **A restart task instead of a handler.** The service restarts on every run, which drops connections for nothing. Notify a handler from the task that changes the configuration.
- **A failed run that skips its handlers.** When a later task fails, the handlers queued earlier do not run, and the new configuration waits on disk for a restart that never comes. Fix the failure and run again: the file is already in place, the template reports `ok`, and nothing notifies the handler. Set `force_handlers: true` on the play, or pass `--force-handlers`, and queued handlers run even when a later task fails.
- **`lineinfile` for a whole file.** Five `lineinfile` tasks against one configuration file leave every other line as the package wrote it, and the repository never shows the whole file the server runs with. Own the whole file with `ansible.builtin.template`.
- **Secrets in plain variables.** A password in `vars:` lands in Git. Encrypt it with `ansible-vault`, and hide its value in the output with `no_log: true` on the tasks that use it.
- **A shell script without `set -eu`.** The script carries on past a failure and reports success. Start every script with it, and run ShellCheck in CI.
- **Spaces in a Makefile recipe.** Make accepts only a tab at the start of a recipe line, and stops with `missing separator` otherwise. Set your editor to keep tabs in files named `Makefile`.

## Going Deeper

- **Roles and collections:** a role packages the tasks, handlers, templates and defaults for one service, such as chrony, for reuse across playbooks.
- **Molecule:** runs a role against a throwaway container or virtual machine, runs it twice, and fails when the second run reports changes.
- **cloud-init and ansible-pull:** a new server configures itself at first boot, without a control node reaching in.
- **Terraform and OpenTofu:** declarative provisioning of the servers, networks and DNS records that Ansible then configures.
- **systemd timers:** the systemd answer to cron, the classic Unix job scheduler, on a plain server, with logs in the journal and a status you can query.
