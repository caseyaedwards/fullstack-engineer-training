A **backup** is a copy of your data that you can restore after a mistake, a broken disk, an attacker or a lost server. Every service with a database needs one, and a backup that nobody has restored is a guess, not a backup. This page covers what to copy, where to keep it, and how to prove that it restores before the day you need it.

## What It Is

### What a Backup Protects Against

Name the failures first, because each one rules out one type of copy:

- **A broken disk or a lost server.** A copy on the same disk, or on the same virtual private server (VPS), goes with it.
- **A mistake.** A `DELETE` without a `WHERE`, a migration that drops the wrong column, a `kubectl delete namespace` in the wrong cluster. The mistake happens in the live database first, and every copy that follows it in real time copies the mistake.
- **An attacker or ransomware.** Anyone with the keys of the server can delete or encrypt the copies those keys reach.
- **A lost account.** A provider that closes or locks your account takes every copy it stores.

A **replica**, a second Postgres that applies every change of the first within milliseconds, survives a broken disk. It does not survive a mistake: it applies the `DELETE` too. A replica gives availability. A backup gives recovery. A production database needs both.

### Recovery Point and Recovery Time

Two numbers describe a backup plan. The **recovery point objective** (RPO) is how much data you accept to lose, measured in time: with one copy a night, up to 24 hours. The **recovery time objective** (RTO) is how long the service can stay down while you restore. The RPO is the interval between two copies that leave the machine. The RTO depends on the size of the data, the speed of the restore and how practiced you are, and you learn it only by timing a restore.

### Logical and Physical Backups

Postgres offers two kinds of backup, and Postgres 17 ships the tools for both.

A **logical backup** holds the schema and the rows of one database as SQL statements or in a compressed archive. `pg_dump` writes one from a single consistent snapshot while the programs keep writing, and `pg_restore` reads it back into an empty database. A logical backup restores into a newer major version of Postgres, and you can restore one table from it. It holds no index data, only the `CREATE INDEX` statements: a restore rebuilds every index, which makes it slow for a database of hundreds of gigabytes. Its RPO is the interval between dumps.

A **physical backup** copies the data files of the whole Postgres server, called a **cluster**, as they lie on disk. `pg_basebackup` takes one from a running server. Files copied one by one while Postgres writes come from different moments, which is where the write-ahead log (WAL) comes in. Postgres appends every change to the WAL before it touches the table files, in **segments** of 16 MB. With **WAL archiving**, Postgres copies each finished segment to backup storage, through the `archive_command` or `archive_library` settings. A restore takes the base backup and replays the archived WAL on top of it, up to any moment you choose. This is **point-in-time recovery** (PITR): restore to 14:31:59, one second before the bad `DELETE`. With `archive_timeout` set to 60 seconds, Postgres closes a segment at least once a minute when there are writes, which brings the RPO down to about a minute.

A physical backup restores only into the same major version, on the same CPU architecture. Since Postgres 17, `pg_basebackup --incremental` copies only the blocks that changed since an earlier backup, and `pg_combinebackup` merges the chain back into a full one. Tools such as pgBackRest, Barman and WAL-G manage base backups, WAL archives, retention and encryption for you.

| | Logical, `pg_dump` | Physical, `pg_basebackup` and WAL |
| --- | --- | --- |
| Covers | One database | The whole cluster |
| Restores to | The moment of the dump | Any moment the WAL covers |
| Restores into | The same or a newer major version | The same major version |
| Restore speed | Rebuilds every index | Copies files, replays WAL |
| Fits | Small databases, one table, upgrades | Large databases, an RPO of minutes |

### The 3-2-1 Rule

The **3-2-1 rule** sets a minimum: keep **three** copies of the data, the live one included, on **two** different kinds of storage, with **one** copy in another place. Different storage means different failure modes: a disk and an object store, not two folders on one disk. Another place means another building and, for a cloud server, another provider or at least another account.

Two additions answer the attacker. Keep one copy **immutable**: object storage with **Object Lock** refuses to delete or overwrite an object until its retention period ends, whatever key asks. And give the server only the keys it needs to add a backup, never the keys to read, list or delete the old ones.

### Encryption and Keys

A backup holds everything the database holds, password hashes and emails included, and it leaves the machine that protects the database. Encrypt it before it leaves. With **public-key encryption**, such as **age**, the server holds only the public key, which can encrypt and never decrypt. The private key stays offline. An attacker on the server cannot read the backups, and neither can the storage provider. The price: without the private key, every backup is noise. Keep two copies of the key, in different places.

### Retention

**Retention** decides how long each backup stays. Keeping only the newest copy fails when you notice a mistake a week late. A common scheme keeps seven daily backups, four weekly and 12 monthly. Retention also decides how long deleted data lives on: a row you delete on request stays in old backups until they expire.

### Verification

Two checks answer two different questions. A **checksum** proves that a copy holds the same bytes as the original: you hash every file when you write the backup, store the hashes in a **manifest**, and compare after every copy and before every restore. A **restore drill** proves that the original is worth copying: it restores the newest backup into an empty server, on a schedule, and checks what comes back. A backup that passes its checksum can still hold the wrong database or a dump that stopped halfway. Only a restore shows that.

## Example

The example writes a checksum manifest for a folder of backup files and checks a copy against it, the same job that `pg_verifybackup` does for the `backup_manifest` file that `pg_basebackup` writes.

SHA-256 is a **cryptographic hash**: it turns any file into 32 bytes, written as 64 hexadecimal characters, and changing one bit of the file changes about half the bits of the hash. Nobody has found two different files with the same SHA-256. `hashFile` streams the file through the hash with `io.Copy`, which keeps memory flat for a dump of any size. `WriteManifest` writes the result in the format of the `sha256sum` command: on a copy without Go, `sha256sum --check SHA256SUMS` checks the same files. A manifest is only as safe as its own copy: keep one where the backup files are not, or sign it.

<CodeFrom file="go/tracks/backups/backups.go" region="verify" lang="go" title="backups.go" />

`Verify` walks the folder once to find what is on disk, then reports three kinds of problem: a listed file that is gone, a file whose hash differs, and a file nobody listed. An extra file is not damage, but it means the folder is not the backup you wrote: a leftover from an earlier run, or a file someone planted. A file that cannot be read counts as changed, because the check cannot confirm its content. The sort makes the output stable for tests and for diffs.

<CodeFrom file="go/tracks/backups/backups_test.go" region="test" lang="go" title="backups_test.go" />

`b[0] ^= 0x01` flips the lowest bit of the first byte: the file keeps its size, which defeats any check that compares sizes. Two more tests check the manifest file byte for byte against a known hash and run the real `sha256sum --check` over it, which fails in CI when `sha256sum` is missing and skips elsewhere.

In the Week 17 setup, age already detects a changed `.dump.age`: it uses authenticated encryption, and decryption fails on a single changed byte. A manifest earns its place for files that travel unencrypted, such as a folder of WAL segments on an internal disk, or for checking many files at once before a long restore.

## Common Mistakes

- **A backup on the same disk.** The disk failure, the lost VPS or the deleted namespace takes it too. Copy every backup off the machine as part of the job that makes it, and measure the RPO from that copy.
- **Never restoring.** A dump that fails halfway, a CronJob that stopped in March, a backup of the test database: each one looks like a backup until the restore. Drill on a schedule, into an empty server, and fail on an old or incomplete backup.
- **Server keys that can delete.** An attacker on the server uses the same key to delete every backup. Give the server an upload key only, and turn on versioning or Object Lock.
- **One copy of the private key.** A laptop that dies takes the only key, and every encrypted backup becomes noise. Keep the key in a password manager and on offline media.
- **Copying the data folder of a running Postgres.** `cp -r` of the data folder while Postgres writes gives files from different moments, which do not form a consistent database. Use `pg_dump`, or `pg_basebackup` with the WAL.
- **No alert on a failed backup.** A backup job that fails quietly for a month leaves you with a month-old backup. Alert when the newest backup is older than one interval plus a margin, as the 26-hour limit of the drill does.

## Going Deeper

- **WAL archiving and point-in-time recovery.** The next step for your monitor: it brings the RPO from a day to a minute and undoes a mistake to the second.
- **pgBackRest.** It manages full, differential and incremental backups, WAL archives, retention, encryption and parallel restore, with its own verification.
- **Postgres 17 incremental backups.** `summarize_wal`, `pg_basebackup --incremental` and `pg_combinebackup` cut the size of each base backup to the changed blocks.
- **Object Lock in compliance mode.** Not even the account owner can delete a locked object before its date, which protects against a stolen account too.
- **Disaster recovery plans.** A written, tested runbook for restoring the whole service, not only the database: DNS, certificates, secrets and the cluster itself. The <TrackLink slug="sre">SRE and Incident Response track</TrackLink> covers runbooks.
